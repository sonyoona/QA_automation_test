# AI TC 지침 — 추후 검토 항목

> 본 문서는 [AI_TC_초안_작성_지침_통합본.md](./AI_TC_초안_작성_지침_통합본.md)에 **지금은 반영하지 않지만, 특정 조건이 되면 반영을 검토할 만한 항목**을 모아둔 백로그다. 본 지침에 넣지 않는 이유(당장 넣으면 오히려 손해인 이유)와, 그 판단이 뒤집히는 시점(재검토 트리거)을 함께 기록한다.
>
> 이 문서 자체는 지침이 아니므로 AI가 TC를 생성할 때 참고하지 않는다. **사람이 필요 시점을 판단해서 골라 쓰는 용도**다.

**문서 버전: v1.1 | 작성일: 2026-08-26 | 최근 갱신일: 2026-08-28**

## 사용법

각 항목은 다음 형식으로 기록한다.

- **무엇을**: 반영하면 되는 구체적인 규칙·구조
- **왜 지금은 아닌지**: 당장 넣지 않는 이유
- **재검토 트리거**: 이 조건이 되면 다시 꺼내본다
- **넣을 위치**: 반영 시 지침의 어느 절에 들어가는지

반영을 결정하면, 이 문서에서 항목을 지우고 지침 본문(md+html)에 옮긴 뒤 18.2 변경 이력에 기록한다.

## 1. 지침 비교 검토에서 보류했던 항목

*(2026-08-26 v4.3 지침 대조 시 "지금은 아니다"로 판단한 것들. 원본 비교는 대조 아티팩트 참조.)*

### 1.1 프로젝트별 정의 작업 + Appendix 구조

- **무엇을**: 상태값 코드, 권한 체계, 시트별 TC ID prefix, 시트 타이틀 색상, 사전조건 템플릿 등 도메인 종속 값을 지침 본문에서 분리해, 프로젝트별로 별도 Appendix 문서에 정의하고 지침 본문과 함께 AI에 입력하는 구조. 지침 앞부분에 "0절 프로젝트별 정의 작업"을 신설해 착수 시 1회 정의하도록 규정.
- **왜 지금은 아닌지**: 현재 로그인·알림설정 2개 기능뿐이라 별도 문서로 분리할 만큼 도메인 값이 많지 않다. AI개요 시트의 「작성 기준 및 전제」가 이미 같은 역할을 하고 있어 지금 도입하면 중복이다.
- **재검토 트리거**: 이 지침으로 다루는 기능/프로젝트가 3~4개를 넘어가거나, 다른 팀이 이 지침을 가져다 쓰기 시작할 때.
- **넣을 위치**: 새 "0절" 또는 0절 하위에 "프로젝트별 정의 작업" 신설, 문서 끝에 Appendix 섹션 추가.

### 1.2 개발 확인 / 라이브 확인 컬럼 분리

- **무엇을**: 현재 단일 컬럼인 `실제 결과`를 `개발 확인`·`라이브 확인` 둘로 나누어, 개발 서버 검증과 운영(라이브) 검증을 각각 PASS/FAIL/N/A/N/T로 추적.
- **왜 지금은 아닌지**: 실제 QA 프로세스가 개발서버 검증 → 라이브 검증의 2단계로 나뉘어 있지 않다. 지금 추가하면 항상 비어 있는 컬럼이 된다.
- **재검토 트리거**: 실제로 개발 환경과 라이브 환경을 나누어 순차 검증하는 프로세스가 도입될 때.
- **넣을 위치**: 14.5 컬럼 규칙의 `실제 결과` 컬럼을 두 컬럼으로 분리, 「실제 결과 입력 규칙」도 두 벌로.

### 1.3 시트별 색상 팔레트 · 열 너비 · 폰트 등 세부 엑셀 스펙

- **무엇을**: 뎁스별 배경색 hex 값, 시트 타이틀 색상 팔레트, 컬럼별 정확한 너비 수치, 폰트·행높이·그리드라인 표시 여부 등 구현 디테일을 지침 문서에 명문화.
- **왜 지금은 아닌지**: 판단 기준이 필요한 서식(실제 결과 색상, 정렬 규칙 등)과 달리 이런 값들은 "왜 이 숫자여야 하는가"에 대한 판단이 없는 순수 고정값이라, 이미 `build.ps1`이 매번 동일하게 적용하고 있다. 지침에도 적으면 코드와 문서 두 곳에 값이 존재하게 되어 불일치 위험만 늘어난다.
- **재검토 트리거**: `build.ps1` 없이 사람이 수작업으로 엑셀 서식을 맞춰야 하는 상황이 생기거나(예: 스크립트 접근 권한이 없는 사람과 공유), 신규 팀원 온보딩용으로 서식 스펙 문서가 별도로 필요해질 때.
- **넣을 위치**: 지침 본문이 아니라 `build.ps1` 옆에 별도 "서식 스펙 참조표" 문서로 분리하는 편이 더 맞을 수 있음.

### 1.4 입력 포맷 규격화

- **무엇을**: PRD·정책서·Appendix·시트 구성·뎁스 구조·TC 목표 개수·기존 TC 파일 등을 정해진 형식으로 AI에 입력하도록 규정.
- **왜 지금은 아닌지**: TC 품질 규칙이 아니라 "AI에게 무엇을 줄 것인가"에 대한 운영 프로토콜이다. 지금은 기획서를 직접 주고 대화로 요청하는 방식이라 정형화가 필요한 단계가 아니다.
- **재검토 트리거**: 여러 사람이 이 지침을 함께 사용하게 되거나, TC 생성 요청이 반복적인 배치 작업으로 바뀔 때.
- **넣을 위치**: 0절 「요청 시 확인할 사항」을 확장하거나, 별도 절 신설.

## 2. Claude가 생각하는 추가 검토 항목

*(v4.3 비교와 무관하게, 지금까지의 대화 전체를 보면서 앞으로 유용할 수 있다고 판단한 것들. 아직 지침에 없고, 논의된 적도 없는 새 제안이다.)*

### 2.1 회귀 테스트(스모크) 셋 자동 추출 규칙

- **무엇을**: `우선순위`(P0/P1/P2) 컬럼을 활용해, "P0만 모아 스모크 테스트 셋으로 돌린다" 같은 필터링 기준과 그 용도를 문서화. 예: 배포 직전엔 P0만, 정기 회귀엔 P0+P1까지.
- **왜 필요한가**: 우선순위 컬럼은 이미 도입했지만(14.5), 그 값을 "언제 어떻게 활용하는가"에 대한 규칙은 없다. 컬럼만 있고 활용 규칙이 없으면 값을 채우는 의미가 반감된다.
- **재검토 트리거**: 반복적인 회귀 테스트 사이클(스프린트마다, 배포마다)이 실제로 운영되기 시작할 때.
- **넣을 위치**: 14.5 「우선순위 입력 규칙」 하단에 활용 가이드 추가, 또는 별도 절.

### 2.2 TC 검수 상태 컬럼 (초안 / 검수 완료)

- **무엇을**: `실제 결과`(PASS/FAIL/N/A/N/T)와는 별개로, TC 자체가 "AI가 쓴 초안"인지 "사람이 검수해서 확정한 것"인지를 나타내는 상태 컬럼. 실행 결과와 TC 신뢰도는 다른 축이다.
- **왜 필요한가**: 지금은 TC 수가 적어 산출물 전체를 매번 검수하지만, 양이 늘어나면 "이 TC는 아직 검수 전이라 신뢰도가 낮다"는 걸 실행 결과와 별개로 추적할 방법이 없다. 검수 안 된 TC의 FAIL과 검수된 TC의 FAIL은 대응 우선순위가 다르다.
- **재검토 트리거**: TC 총량이 커져서 산출 직후 전체를 한 번에 검수하기 어려워질 때, 또는 검수자와 작성자가 분리될 때.
- **넣을 위치**: 14.5 컬럼 규칙에 새 컬럼 추가 검토.

### 2.3 다중 작성자 협업 규칙

- **무엇을**: 여러 명이 동시에 같은 산출물에 TC를 추가할 때의 ID 충돌 방지 규칙(예: 작성자별 ID 구간 배분, 또는 병합 시점에 순차 재부여하는 절차), 담당 기능 구간을 나누는 기준.
- **왜 필요한가**: 지금은 혼자 작성해서 "신규 TC는 항상 끝에 추가"(14.1)만으로 충분하지만, 두 명이 동시에 서로 다른 기능의 TC를 쓰면 같은 순간에 같은 다음 번호를 쓰게 되는 충돌이 생길 수 있다.
- **재검토 트리거**: QA 인력이 2명 이상이 되어 이 지침으로 동시에 TC를 작성하게 될 때.
- **넣을 위치**: 14.1 파일·시트 구성 원칙 하단에 추가.

### 2.4 접근성(Accessibility) 검증 카테고리

- **무엇을**: 스크린리더 라벨, 키보드만으로의 조작 가능 여부, 색상 대비 등 접근성 관점의 TC를 별도 카테고리로 다룰지에 대한 기준. 지금은 6절(정상/예외/경계)에 자연히 포함되지 않는 영역이다.
- **왜 필요한가**: 현재 로그인·알림설정 TC에는 접근성 요구사항이 요구사항 문서에 없어 다루지 않고 있다. 다만 접근성이 실제 요구사항으로 들어오는 시점에 대비해, "요구사항에 없으면 만들지 않는다"는 기존 원칙과 "접근성은 명시가 없어도 최소 검토는 필요하다"는 상충 가능성을 미리 정리해두면 좋다.
- **재검토 트리거**: 접근성이 실제 기획/정책 요구사항으로 명시되거나, 사내 접근성 표준이 생길 때.
- **넣을 위치**: 9절 또는 새 절.

### 2.5 TC 반복 실행 이력 추적 방식

- **무엇을**: 지금 `실제 결과`는 최신 1회 값만 담는 단일 컬럼이다. 같은 TC를 회귀 사이클마다 반복 실행하게 되면, 회차별 결과 이력을 어디에 남길지(예: 시트를 회차별로 복제, 또는 "최근 결과"만 남기고 이전 값은 변경이력목록에 흡수하는 등)에 대한 규칙.
- **왜 필요한가**: 지금은 산출 후 1회 검증을 전제로 설계되어 있어 이력 개념이 없다. 정기 회귀가 시작되면 "지난번엔 PASS였는데 이번엔 FAIL"같은 추이를 봐야 할 수 있는데, 지금 구조로는 덮어쓰면 이전 값이 사라진다.
- **재검토 트리거**: 동일 TC 셋을 여러 차례(스프린트마다 등) 반복 실행하는 운영이 시작될 때.
- **넣을 위치**: 15.2 파일 버전 관리 규칙과 연계, 또는 새 절.

## 3. STAFF/DUMP 보안인증강화 TC 비교 검토에서 나온 항목

*(2026-08-28, 참고 TC 2건과 실물 대조 시 반영 보류로 판단한 것들. 상세 비교는 세션 내 HTML 비교 리포트 참조.)*

### 3.1 선택적 "케이스 유형" 컬럼(정상/비정상/권한 등) 도입 여부 검토

- **무엇을**: 현재 TC 시트는 1/2/3뎁스로만 그룹핑한다. 참고 TC 2건은 이와 별개로 "분류"(정상/비정상/권한 등) 컬럼을 두어, TC가 정상 흐름인지 예외·권한 케이스인지를 한눈에 스캔할 수 있게 한다. 프로젝트 재량으로 14번째 컬럼을 선택적으로 추가하는 안.
- **왜 지금은 아닌지**: 지침 14.5는 TC 시트를 13개 컬럼으로 고정하고 있고, 기존 TC_로그인_알림설정 문서도 이 13개 컬럼을 그대로 쓴다. 결정 없이 신규 문서에만 컬럼을 추가하면 프로젝트 내 문서 간 컬럼 구조가 달라져 이후 통합·자동화 스크립트 재사용이 어려워진다.
- **재검토 트리거**: 여러 TC 문서를 동시에 다루면서 "정상/비정상만 빠르게 필터링"할 필요가 실제로 반복될 때, 또는 기존 문서들을 한 번에 마이그레이션할 계기가 생길 때.
- **넣을 위치**: 14.5 TC 시트 컬럼 규칙에 14번째 컬럼(선택)으로 추가.

### 3.2 회귀 테스트용 '실제 결과' 다회차 컬럼 확장 규칙

- **무엇을**: 실행 차수가 2회 이상 필요할 때(수정 후 재검증 등) '실제 결과' 컬럼을 '실제 결과(1차)', '실제 결과(2차)'… 형식으로 조건부 확장하는 네이밍 규칙. 참고 TC 중 하나가 실제로 Chrome 1차·2차 결과를 나란히 기록하는 구조를 쓰고 있었음.
- **왜 지금은 아닌지**: [[2.5 TC 반복 실행 이력 추적 방식]]과 문제의식이 겹친다. 2.5는 "회차별 이력을 어디에 남길지"를 여러 방안(시트 복제, 변경이력목록 흡수 등) 중 아직 정하지 않은 상태이고, 이번 건은 그중 구체적인 컬럼 확장 메커니즘(네이밍 규칙) 하나를 제안한 것이라 별도 항목이 아니라 2.5의 후보안으로 취급한다.
- **재검토 트리거**: 2.5와 동일 — 동일 TC 셋을 여러 차례(스프린트마다 등) 반복 실행하는 운영이 시작될 때, 이 컬럼 확장 방식을 2.5의 여러 방안 중 하나로 비교 검토.
- **넣을 위치**: 2.5와 함께 14.5 컬럼 규칙 또는 15.2 파일 버전 관리 규칙에 반영 검토.
