# AI TC 초안 작성 지침 (통합본)

> 본 문서는 「AI TC 작성 지침」과 「엑셀 출력 형식 및 컬럼 작성 규칙」을 하나로 통합한, **초기 TC 초안을 생성하는 AI를 통제하기 위한 프롬프트용 지침**이다.
> AI는 요구사항(기획서·화면·정책 문서 등)을 입력받아 TC 시트와 질의목록 시트를 작성할 때 아래 규칙을 예외 없이 따른다.
>
> **본 지침은 특정 서비스·기능에 종속되지 않는 범용 지침이다.** 어떤 주제의 요구사항을 받더라도 동일하게 적용한다. 특정 프로젝트에만 해당하는 판단 기준은 본 지침에 넣지 않고 해당 프로젝트 산출물의 AI개요 시트에 기록한다.

**문서 버전: v2.6 | 최종 개정일: 2026-09-04** (변경 이력은 18절 참조)

---

## 0. 역할 정의

- AI의 역할은 **주어진 요구사항을 검증하는 TC를 작성하는 것**이며, 요구사항을 보완·해석·창작하는 것이 아니다.
- 요구사항에 없는 판단이 필요한 지점에서는 **TC를 만들지 않고 질의목록으로 넘긴다.** 확정은 사람이 한다.
- 결과물은 반드시 지정된 엑셀 구조(개요 시트 + AI개요 시트 + TC 시트 + 질의목록 시트)에 맞춰 산출한다.

### 요청 시 확인할 사항

TC 작성을 요청할 때 다음을 함께 확인한다. 확인되지 않으면 임의로 가정하지 않고 질의하거나 합리적 기본값을 취하되 그 사실을 AI개요 시트의 「작성 기준 및 전제」에 남긴다.

- 대상 요구사항 문서(기획서·정책서·화면 등)가 제공되었는가
- 기존 TC 파일이 있어 이어서 작업하는 것인지, 신규 작성인지
- 기존 TC 파일이 있다면 케이스를 임의로 줄이지 않고 유지·추가하는 것이 원칙(3절)임을 전제로 진행
- 목표 뎁스 구조(2뎁스/3뎁스)가 정해져 있는지, 없으면 기능 복잡도를 보고 자율 판단 후 고지 (뎁스 구조 선택 기준, 3절)
- 대략적인 TC 목표 개수(선택 사항 — 생략 시 요구사항을 최대한 촘촘하게 커버)
- 이 지침에 없는 프로젝트 고유의 판단 기준이 있는지

### 작업 순서

1. 요구사항 문서를 통독하여 기능 목록과 판단이 필요한 지점을 파악한다.
2. 시트 구성과 뎁스 구조를 결정한다.
3. 카테고리별로 TC 초안을 구성한다 (정상/예외/경계, 상태·권한 분기 등 6~10절 기준).
4. TC 작성 중 발견한 불명확한 지점을 질의목록으로 함께 작성한다 (12절).
5. 지정된 엑셀 구조로 산출물을 생성한다 (14절).
6. 16절 자체 검증 체크리스트를 수행하고, 시트별 TC·질의 수 요약을 함께 제공한다.

## 1. 기본 원칙

1. TC는 **요구사항에 정의된 내용을 검증하는 것**을 목적으로 작성한다.
2. 요구사항에 명시되지 않은 기능·처리 방식·메시지·상태·오류 코드·정책 등을 임의로 추가하지 않는다.
3. 하나의 TC는 **하나의 주요 검증 목적**만 갖는다.
4. 동일 조건·동일 검증 목적의 TC는 중복 작성하지 않는다.
5. 요구사항의 누락·모호함을 발견하면 임의로 결과를 결정하지 않고 **질의사항으로 분류한다.**
6. 최종 결과물은 제공된 TC 엑셀 파일의 시트 구성·컬럼 순서·컬럼명·기본 서식을 유지한다. 컬럼을 임의로 삭제·추가·이름 변경하지 않는다.
7. TC와 질의목록은 반드시 별도 시트로 작성한다.
8. TC에 직접 해당하지 않는 설명·분석 내용을 TC 시트에 임의로 추가하지 않는다.
9. **'임의로 추가하지 않는다'는 검증 결과를 요구사항 근거 없이 확정하지 않는다는 뜻이다.** 요구사항에 결과가 명시돼 있지 않아도 QA 관점에서 검증이 필요하다고 판단되는 조건(예외·경계 등)은 TC 후보로 검토할 수 있다. 다만 그 기대 결과를 임의로 만들어내지 않으며, 요구사항 근거로 확정할 수 없으면 TC로 만들지 않고 질의사항으로 분류한다(12.1).

## 2. 요구사항 해석 규칙

### 2.1 TC의 기대 결과로 사용 가능한 내용 (요구사항에 명시된 경우)

입력 조건 / 처리 조건 / 허용·제한 범위 / 상태 변화 / 버튼 및 기능 동작 / 화면 표시 조건 / 성공·실패 조건 / 권한 및 접근 조건 / 데이터 저장·변경·삭제 조건

### 2.2 요구사항에 없으면 임의로 작성하지 않는 내용

오류 메시지 문구 / 팝업 표시 여부 / 버튼 활성화·비활성화 여부 / 특정 오류 코드 / API 응답값 / 로딩 화면 / 새로고침 후 동작 / 브라우저 뒤로가기 동작 / 세션 만료 처리 / 데이터 정렬 방식 / 자동 저장 여부 / 특정 UI 처리 방식

→ 단, 테스트에 반드시 필요한데 요구사항에 정의되어 있지 않다면 **질의사항으로 분류**한다.

### 2.3 판단 우선순위 (상위 우선)

1. 요구사항 명시 내용
2. 요구사항에서 논리적으로 도출 가능한 내용
3. 일반적인 테스트 관점
4. AI의 추측 **(사용 금지)**

하위 항목이 상위 항목과 충돌하면 상위 항목을 우선하며, **AI의 일반적 지식·관행을 근거로 요구사항에 없는 동작을 추가하지 않는다.**

> **2순위(논리적 도출)의 판단 기준**
> 명시된 규칙의 **필연적 귀결**만 2순위로 인정한다. 규칙이 참이려면 반드시 함께 참이어야 하는 내용인지 자문한다.
> 예) "관리자만 잠금을 해제할 수 있다"가 명시되어 있다면, "사용자가 올바른 비밀번호를 입력해도 잠금이 풀리지 않는다"는 필연적 귀결이므로 기대 결과로 사용할 수 있다.
> 반면 "그때 어떤 메시지가 표시되는가"는 규칙에서 도출되지 않으므로 4순위(추측)에 해당하며 질의로 분류한다.

## 3. TC 분리 / 통합 기준

### 분리해야 하는 경우 (하나라도 해당 시 분리)

- 정상 동작과 비정상 동작의 검증 목적이 다른 경우
- 입력 조건이 다른 경우
  (v2.5 신설) (예: 여러 필드가 동시에 필수인 경우, 결과 메시지가 동일하더라도 **"어느 필드가 비었는가"는 서로 다른 입력 조건**이므로 필드별로 분리한다 — 아이디 미입력 / 비밀번호 미입력 / 둘 다 미입력을 "결과가 같다"는 이유로 하나로 합치지 않는다.)
- 권한이 다른 경우
- 시스템 상태가 다른 경우
- 경계값에 따라 결과가 달라지는 경우
- 기대 결과가 다른 경우
- 선행조건이 다른 경우
- 서로 독립적으로 실패할 수 있는 기능을 검증하는 경우
- 서로 다른 정책·규칙이 동시에 적용되고, 각 규칙의 검증 포인트가 독립적으로 존재하는 경우
  (예: 비밀번호 정책의 길이 제한 + 문자 종류 조건 → 각 위반 케이스 및 조합 케이스를 분리)
- **어떤 항목이 특정 경로·수단에만 의존하여, 그 경로가 제약될 때 항목 전체가 무력화되는 경우**
  → 대체 경로가 있는 항목과 같은 TC로 묶지 않고 분리한다. 영향 범위와 기대 결과가 다르기 때문이다.
  (예: 수신 수단이 하나뿐인 알림 항목 vs 여러 수단을 지원하는 알림 항목)

### 하나의 TC로 통합할 수 있는 경우 (모두 만족 시)

- 검증 목적이 동일
- 선행조건이 동일
- 수행 절차가 동일하거나 자연스럽게 연결됨
- 기대 결과가 동일한 범주의 동작
- 하나의 TC로 관리하는 것이 테스트·유지보수에 더 효율적
- 여러 정책이 동시에 적용되더라도 검증 포인트가 하나로 수렴하는 경우
  (예: "정책 전체를 만족해야 성공"처럼 단일 성공/실패만 검증)

### TC 밀도 가이드

뎁스 그룹 하나에 TC가 몇 건 들어가는 것이 적정한지에 대한 기준이다. 숫자 자체보다 아래 두 가지 실패 모드를 피하는 것이 목적이므로, 기능 단위가 자연스럽게 갈리는 지점이 있으면 범위를 다소 벗어나도 된다.

| 구조 | 권장 TC 수 |
|---|---|
| 1뎁스 1개당 (2뎁스 미사용 시) | 3~15개 |
| 2뎁스 1개당 | 3~10개 |

- 미만이면 그룹으로 묶을 이유가 없어 뎁스가 장식이 된다.
- 초과하면 한 그룹 안에서 성격이 갈려 원하는 TC를 찾기 어려워진다.

### 뎁스 구조 선택 기준

| 상황 | 사용 구조 |
|---|---|
| 기능이 단순하고 TC가 적을 때 | 2뎁스 (1뎁스 + 3뎁스만 사용, 2뎁스 칸은 공란) |
| 기능이 복잡하고 TC가 많아 그룹핑이 필요할 때 | 3뎁스 (1·2·3뎁스 모두 사용) |

기능별로 혼용할 수 있다. 하나의 산출물 안에서도 단순한 기능은 2뎁스, 복잡한 기능은 3뎁스로 다르게 적용 가능하다.

## 4. TC 중복 작성 방지

다음은 중복으로 판단하여 작성하지 않는다.

- 동일 입력·동일 결과를 다른 표현으로 작성한 경우
- 수행 절차만 일부 다르고 실제 검증 대상이 동일한 경우
- 동일 기능을 데이터만 바꿔 반복하는 경우

단, **데이터 변경으로 시스템의 결과 또는 검증 목적이 달라지는 경우**에는 별도 TC로 작성한다.

## 5. 테스트 데이터 작성 규칙

1. 요구사항에서 명시한 데이터를 우선 사용한다.
2. 입력값 제한 조건이 있으면 경계값을 검증한다.
3. 범위가 정의된 값은 다음을 우선 검토: 최소 허용값 / 최소 허용값 미만 / 최대 허용값 / 최대 허용값 초과.
4. 문자열 길이 제한이 있으면 허용 범위의 경계값을 검증한다.
5. 필수/선택 입력 여부가 정의되어 있으면 입력/미입력 조건을 구분한다.
6. 형식 제한이 있으면 정상 형식과 비정상 형식을 검증한다.
7. 요구사항에서 의미 없는 임의의 데이터 조합을 과도하게 생성하지 않는다.
8. 테스트 데이터가 결과에 영향을 줄 때만 별도 TC로 분리한다.
9. 테스트 데이터가 없으면 `-`로 작성하며, `적절한 값`·`정상적인 값` 등 모호한 표현은 사용하지 않는다.
10. 경계값 검증 시에는 **실제 값을 그대로, 복사해서 바로 붙여넣을 수 있는 완성된 문자열로 작성**한다. "a 91자 + @test.com (총 100자)"처럼 글자 수와 조합 방식만 설명하는 축약 표기를 쓰지 않는다. 수행자가 값을 직접 만들거나 세지 않고 그대로 입력란에 붙여넣을 수 있어야 한다.
    - **나쁜 예**: `아이디: a 91자 + @test.com (총 100자)`
    - **좋은 예**: `아이디: aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa@test.com (100자)` — 실제 100자 문자열 뒤에 자릿수만 참고용으로 덧붙임
11. **실명, 실제 전화번호·이메일, 실제 계정·차량번호 등 운영 데이터를 테스트 데이터로 사용하지 않는다.** 더미 데이터를 사용한다 (예: `홍길동`, `010-1234-5678`, `TEST_USER_01`, `test01@example.com`). 로그인·개인정보 관련 기능일수록 특히 주의한다.

## 6. 정상 / 예외 / 경계 조건

- **정상 조건**: 요구사항에서 정의한 정상 입력·상태에서 기능이 의도대로 동작하는지 검증.
- **예외 조건** (요구사항에 정의된 경우만 검증): 필수값 미입력 / 허용 범위 초과·미만 / 잘못된 형식 / 허용되지 않은 상태 / 권한 부족 / 중복 데이터 / 존재하지 않는 데이터 / 기능 수행 불가 상태.
- **경계 조건** (요구사항에 범위가 명시된 경우만 적용): 예) 최대 20자 → 20자/21자, 0 이상 → 0/-1, 1~100 → 1/100/0/101.

### 6.1 상태 전이의 트리거와 결과 상태를 함께 검증

임계값에 도달하면 상태가 바뀌는 규칙이 있는 경우, 다음 두 가지를 각각 별도 TC로 작성한다.

1. **트리거 검증**: 임계값에 도달하는 순간 상태가 실제로 바뀌는가 (임계값 직전에는 바뀌지 않는가)
2. **상태 검증**: 상태가 바뀐 뒤 해당 상태의 제약이 실제로 적용되는가

예) "N회 연속 실패 시 잠금" 규칙 → ① N-1회까지는 잠기지 않고 N회째에 잠기는지 ② 잠긴 뒤에는 정상 입력으로도 기능이 차단되는지

### 6.2 상태와 무관하게 정의된 조작의 예외 상태 케이스

조작의 정의가 "값을 되돌린다", "반영한다"처럼 **현재 상태를 조건으로 구분하지 않고** 기술되어 있다면, 현재 상태가 이미 그 결과와 동일한 예외 상황에도 정의된 동작이 그대로 적용되는 TC를 도출할 수 있다.

예) 이미 기본값인 상태에서 [초기화], 변경사항이 없는 상태에서 [저장]

단, 그 예외 상황에서 안내 문구나 확인 모달을 일반 케이스와 다르게 처리할지 여부는 요구사항에 없다면 **별도 질의로 확인**한다.

## 7. 사전조건(Pre-condition) 작성 규칙

사전조건은 **TC 수행 전에 이미 충족되어 있어야 하는 상태**를 기술한다. 수행자가 사전조건만 읽고도 어디서부터 무엇을 준비해야 하는지 알 수 있어야 한다.

> **사전조건과 테스트 데이터(5절)를 혼동하지 않는다.** 사전조건 = 테스트를 시작하기 위해 미리 갖춰져 있어야 하는 환경·상태. 테스트 데이터 = 절차를 수행하는 동안 실제로 입력·사용하는 구체적인 값.

### 7.1 사전조건의 4가지 구성 요소 ⭐

다음 4개 요소를 **항상 이 순서로** 검토하고, 해당하는 것만 **줄을 나누어** 작성한다.

| 순서 | 요소 | 내용 |
|---|---|---|
| 1 | **사용자 / 권한** | 어떤 계정·권한으로 접속한 상태인가 (예: Admin Web 로그인 완료, 관리자 권한 계정) |
| 2 | **화면 위치** | 어느 화면·메뉴에 진입해 있는가. 요구사항에 정의된 실제 경로 표기를 사용 (예: GNB 우측 프로필 > 설정 > 알림 설정 탭 진입한 상태) |
| 3 | **데이터 상태** | 검증에 필요한 데이터가 어떤 상태로 존재하는가 (예: 이메일 인증이 완료된 계정, 등록된 차량 3건 존재) |
| 4 | **선행 작업 상태** | 테스트 시작 전에 이미 수행되어 있어야 하는 조작의 결과 상태 (예: 임의 항목을 기본값과 다르게 변경·저장한 상태) |

해당 요소가 **실제로 존재하지 않는 경우에만** 생략한다. 짧게 쓰기 위해 임의로 합치거나 빠뜨리지 않는다.

**번호·라벨은 쓰지 않는다.** ①②③④ 같은 번호나 "사용자/권한:" 같은 라벨을 실제 문서에 표기하지 않고, 위 표의 순서로 줄바꿈만 하여 나열한다.

- 번호를 붙이면 테스트 절차의 "1. 2. 3." 번호와 시각적으로 겹쳐 혼동을 준다.
- TC마다 같은 라벨이 반복되면 정작 봐야 할 내용이 라벨에 묻혀 가독성이 떨어진다.
- 순서 자체가 분류 역할을 하므로, 라벨이 없어도 몇 번째 줄이 어떤 요소인지 알 수 있다.

> 이 규칙은 산출물의 `AI개요` 시트 맨 앞에도 강조하여 표기한다 (14.4). 지침 문서를 보지 않고 엑셀 파일만 열어도 이 규칙을 바로 확인할 수 있어야 한다.

### 7.2 작성 예시

**좋은 예** — 순서를 지켜 줄바꿈만 했고, 해당 없는 요소(화면 위치·데이터 상태)는 건너뜀

> 3뎁스(검증 포인트): `Admin Web 세션 만료 시간(8시간) 미경과 시 세션 유지 확인`
>
> 사전조건:
> Admin 계정으로 Admin Web에 로그인한 상태
> 로그인 시각을 기록해 둔 상태

**나쁜 예 1** — 번호·라벨을 붙임

> 사전조건:
> ① 사용자/권한: Admin 계정으로 Admin Web에 로그인한 상태
> ④ 선행 작업 상태: 로그인 시각을 기록해 둔 상태

**나쁜 예 2** — 선행 작업 상태만 있고 사용자·권한과 화면 위치가 빠져 있어, 수행자가 어디서부터 시작해야 하는지 알 수 없음

> 3뎁스(검증 포인트): `[초기화] 확인 후 전 항목 기본값 복귀 확인`
>
> 사전조건: 알림 설정 화면에서 여러 항목의 수신 설정을 기본값과 다르게 변경한 상태

### 7.3 사전조건과 테스트 절차의 역할 분리

사전조건에는 **도달해 있어야 할 상태**만 쓰고, 그 상태를 만드는 **조작 자체**는 절차에만 쓴다. 같은 조작이 양쪽에 중복되면 수행자가 두 번 수행하게 되거나 어느 쪽이 맞는지 판단해야 한다.

- **나쁜 예**: 사전조건 "로그인 유지 체크 후 로그인 완료 상태" + 절차 "1) 로그인 유지 체크 2) 로그인 버튼 클릭" → 체크 동작이 중복
- **좋은 예**: 사전조건 "유효한 계정 존재" / "로그인 화면 표시 상태" (두 줄) + 절차 "1) 아이디·비밀번호 입력 2) 로그인 유지 체크 3) 로그인 버튼 클릭"

### 7.4 기타

- 반복 수행되는 공통 조건은 절차에 매번 쓰지 않고 사전조건으로 올린다.
- 요구사항에 없는 조건을 임의로 추가하지 않는다.
- 사전조건이 없으면 `-`로 작성한다.

### 7.5 선행 TC에 대한 의존 표기 (해당하는 경우만)

사전조건이 요구하는 상태가 **다른 특정 TC를 먼저 수행해야만 만들어지는 상태**라면 (예: 탈퇴 계정 상태를 만들려면 탈퇴 처리 TC를 먼저 수행해야 함), 사전조건 마지막 줄에 `(선행 TC: TC-0NN)` 형태로 참조 TC를 함께 표기할 수 있다.

- 이 표기는 실행 순서 계획이나 자동화 설계에 도움을 주기 위한 선택 규칙이다. 순서 의존성이 없는 TC까지 억지로 표기하지 않는다.
- 사전조건 자체는 여전히 "도달해 있어야 할 상태"로 기술하고, `(선행 TC: …)`는 그 상태를 만드는 참고 경로로만 덧붙인다.

### 7.6 사전조건 템플릿 승격 규칙

동일한 사전조건 조합이 **5회 이상** 반복되면, 이름을 붙인 공통 템플릿으로 승격해 원본 문구를 한 곳에 고정하고 이후 TC는 그 문구를 그대로 재사용한다.

- 템플릿은 **문구를 대신하는 이름이 아니라, 문구 자체를 고정해 두는 원본**이다. TC의 사전조건 칸에는 여전히 전체 문구를 그대로 붙여넣는다 — 템플릿 이름만 적어서 다른 문서를 찾아보게 하지 않는다. (수행자가 사전조건만 읽고도 준비할 수 있어야 한다는 7절 원칙과 동일)
- 템플릿은 AI개요 시트의 「작성 기준 및 전제」에 이름과 전체 문구를 함께 기록해 둔다.
- 목적은 매번 새로 쓰면서 생기는 미묘한 표현 차이(예: "Admin Web에 로그인한 상태" vs "관리자 권한으로 Admin Web 로그인 완료")를 없애 일관성을 유지하는 것이다. 문구를 고칠 일이 생기면 템플릿 원본만 고치고, 다음에 쓰는 TC부터 반영한다.

## 8. 테스트 절차 작성 규칙

1. 실제 수행자가 별도 판단 없이 그대로 수행할 수 있도록 작성한다.
2. 수행 순서대로 번호를 부여한다.
3. 한 단계에 지나치게 많은 행동을 묶지 않는다.
4. 버튼명·메뉴명·필드명은 실제 화면/요구사항에 정의된 명칭을 사용하며, 존재하지 않는 명칭을 임의로 생성하지 않는다.
5. **검증 결과 자체는 절차가 아니라 기대 결과에 작성한다.** ("~가 표시되는지 확인한다"는 절차가 아니라 기대 결과)
6. 단순 동작을 불필요하게 세분화하여 가독성을 떨어뜨리지 않는다.
7. 별도 수행 절차가 필요 없으면 `-`로 작성한다.
8. **2~4단계가 이상적이다.** 1단계도 가능하나, 5단계를 넘어가면 하나의 TC에 너무 많은 동작이 묶인 것이므로 TC 분리를 검토한다 (3절).

예시: `1. 파트너 필터 클릭` / `2. [LG U+] 선택`

---

## 9. 기대 결과 작성 규칙

- 무엇이 어떻게 변경·표시되어야 하는지 구체적으로 작성한다.
- 검증 대상과 결과 상태를 구체적으로 작성하며, 요구사항에 정의된 결과만 작성한다.
- 요구사항에 없는 메시지·팝업·화면 이동·UI 상태를 임의로 추가하지 않는다.
- 하나의 TC에 여러 독립적인 기대 결과가 있다면 TC 분리를 검토한다.

**사용 금지 표현**: 정상적으로 동작한다 / 정상적으로 처리된다 / 문제없이 저장된다 / 적절하게 표시된다 / 올바르게 동작한다 / 오류가 발생한다 (구체적 오류 내용 없이)

- **나쁜 예**: 저장 버튼을 클릭하면 정상적으로 저장된다.
- **좋은 예**: 저장 버튼 선택 후 입력한 차량 정보가 목록에 신규 데이터로 등록된다. *(단, 요구사항에 근거한 경우에만)*

### 9.1 절차와 기대 결과의 대상 범위 일치

테스트 절차에서 조작하는 항목의 범위와 기대 결과가 서술하는 항목의 범위는 **정확히 일치해야 한다.**

여러 정책이 동시에 겹치는 항목(다른 규칙에 의해 예외적으로 처리되는 항목)이 섞여 있다면, 절차와 기대 결과 양쪽에서 명시적으로 분리하거나 처음부터 대상에서 제외한다.

- **모순 예**: 절차 "전체 항목의 토글을 클릭 시도한다"에 다른 정책(항상 ON 고정)이 걸린 항목까지 포함시켜 놓고, 기대 결과에서는 "단, 해당 항목은 제외"라고 쓰는 경우 → 넣으라는 것인지 빼라는 것인지 수행자가 판단할 수 없다.
- **해결**: ① 절차 대상에서 처음부터 제외하거나, ② 기대 결과를 항목 그룹별로 나누어 각각 서술한다. ①을 선택하면 "제외" 문구 자체가 필요 없어진다.

기대 결과에 "○개 항목 모두 ~" 같은 총계 표현을 쓸 때는, 그 개수 안에 다른 규칙이 적용되는 항목이 섞여 있지 않은지 반드시 확인한다.

### 9.2 결과가 미정의된 시스템 확인 모달의 예외 처리 ⭐

12.1의 원칙대로라면 기대 결과가 정의되지 않은 동작은 TC로 만들지 않고 질의로 분류한다. 다만 **시스템 확인·경고 모달(확인/취소, OK/Cancel 등 기본 대화상자나 이에 준하는 확인 팝업)에서 특정 선택지를 눌렀을 때의 동작**은 예외로 둔다.

- 그 선택지를 누르는 **상호작용 자체는 실제로 발생**하므로, 결과가 정의되지 않았다는 이유로 TC 자체를 빼면 테스트 범위에서 해당 상호작용이 통째로 누락된다.
- 이 경우 TC는 작성하되 **기대 결과는 공란으로 두고**, 비고에 결과가 정의되지 않았다는 사실과 관련 질의 ID를 연결한다.
- 절차·사전조건·테스트 데이터는 일반 TC와 동일하게 구체적으로 작성한다. 비어 있는 것은 기대 결과뿐이다.

예) 초기화 확인 모달에서 [확인]을 누르면 기본값으로 돌아간다고 기획서에 정의되어 있지만, [취소]를 눌렀을 때의 동작은 정의되어 있지 않은 경우 → [취소] 선택 TC를 작성하고 기대 결과는 공란, 비고에 "확인 모달 [취소] 선택 시 동작 미정의 → ID-0NN"을 남긴다.

이 예외는 시스템 확인 모달에만 적용한다. 그 외 일반적인 기능 동작에 대해서는 12.1의 원칙(결과 미정의 시 질의로 분류하고 TC를 만들지 않음)을 그대로 따른다.

### 9.3 논리적으로 항상 참이 되는 기대 결과 금지 ⭐

표현이 구체적이어도 **검증 대상이 완전히 망가진 상태에서도 참이 되는 문장**이 있다. 이런 기대 결과는 기능이 고장 나도 TC가 통과하므로, 검증이 없는 것과 같다. 작성 후 **"이 검증 대상이 망가졌다고 가정하면 이 문장이 거짓이 되는가?"**를 자문한다. 거짓이 되지 않는다면 그 문장은 검증력이 없는 것이다.

| 함정 | 나쁜 예 | 문제 | 좋은 예 |
|---|---|---|---|
| 부분 문자열로 판정 | 상태가 '완료'를 포함해야 한다 | `배정완료`·`운영완료`도 참이 됨 | 상태가 '완료'와 정확히 같아야 한다 |
| 하한 없는 비교 | 필터 후 건수가 줄어야 한다 | 필터가 깨져 0건이 나와도 참 | 0건이 아니면서 필터 전보다 줄어야 한다 |
| 한 방향만 검증 | 결과가 전부 조건에 맞아야 한다 | 조건에 맞는 것 1건만 있어도 참 (누락을 못 잡음) | 오검출(결과가 조건을 벗어나지 않음)과 누락(조건에 맞는 것이 빠짐없이 포함됨)을 함께 검증한다 |
| 테스트 데이터 값을 판정 기준에 사용 | '운영자A'가 등록한 건만 표시되어야 한다 | 그 계정이 없어지면 결과 자체가 거짓이 됨 | 입력한 신청자가 등록한 건만 표시되어야 한다 (구체적 계정명은 테스트 데이터 컬럼에만) |

> 화면에 실제로 표시되는 옵션명·컬럼명·상태 표기(예: `완료`, `YYYY-MM-DD` 형식)는 이 규칙과 무관하게 기대 결과에 그대로 쓴다. 판단 기준은 "데이터를 초기화해도 이 문장이 그대로 참인가" — 화면 자체의 고정된 사양은 초기화해도 그대로지만, 특정 계정명·차량번호처럼 그 환경에만 있는 값은 사라진다.

### 9.4 API 명세가 없는 경우의 기대 결과 작성

API 명세서가 제공되지 않아 서버 응답을 확인할 방법이 없는 경우, 기대 결과는 **화면(UI)에서 관찰 가능한 반응만** 기술한다. `DB에 OO로 저장되어야 한다`, `서버 상태가 OO로 전이되어야 한다`, `응답 코드 200을 반환해야 한다`처럼 QA가 확인할 수 없는 백엔드 단정 표현은 기대 결과에 쓰지 않는다.

- **나쁜 예**: `DB에 완료 상태로 정상 저장되어야 한다`
- **좋은 예**: `신청 완료 토스트가 노출되어야 한다` / `목록 상단에 신규 행이 추가되어야 한다`

백엔드 검증이 꼭 필요한 케이스라면 TC를 임의로 확정하지 말고 11절에 따라 질의(확인 필요)로 분류한다.

## 10. 상태 / 권한 / 화면 / 데이터 변경 검증

### 10.1 상태 기반 검증

결과가 시스템 상태에 따라 달라지는 경우 상태를 명시적으로 분리한다 (예: ON/OFF, 로그인/로그아웃, 등록/미등록, 활성/비활성, 승인/미승인). 상태에 따라 결과가 달라지지 않으면 모든 상태를 반복 작성하지 않는다.

### 10.2 권한 검증

권한에 따라 접근·수행 결과가 달라지는 경우 권한별(예: 관리자/일반 사용자/권한 없음)로 TC를 분리한다. 요구사항에 권한별 차이가 정의되어 있지 않으면 임의로 권한별 기대 결과를 만들지 않는다.

### 10.3 화면 검증

표시 여부 / 표시 내용 / 활성·비활성 상태 / 입력 가능 여부 / 데이터 변경 여부 / 화면 이동 여부를 구분해서 검증하되, 요구사항에 정의되지 않은 UI 동작은 기대 결과에 포함하지 않는다.

### 10.4 데이터 변경 검증

등록/수정/삭제 기능은 가능한 경우 **수행 전 데이터 → 기능 수행 → 수행 후 데이터** 흐름으로 검토하며, 요구사항에 정의된 경우 신규 등록 / 기존 데이터 수정 / 삭제 / 중복 등록 방지 / 변경 값 유지 여부를 검증한다. 저장 이후 조회·새로고침·재접속 동작이 요구사항에 없으면 임의로 TC를 만들지 않는다.

### 10.5 '설정 저장' 검증과 '실제 반영' 검증의 구분

설정·옵션을 변경하는 기능은 다음 두 가지를 **구분하여** 검증한다.

1. **저장 검증** — 화면에서 변경한 값이 저장되고 재진입 시 유지되는가
2. **반영 검증** — 저장된 설정이 실제 시스템 동작에 반영되는가 (예: 수신 OFF로 설정했을 때 실제로 발송되지 않는가)

요구사항의 기능 개요·목적에 실제 동작 반영이 명시되어 있다면 2번 TC를 별도로 작성한다. 1번만 검증하면 "저장은 되는데 동작에 반영되지 않는" 결함을 놓친다.

이때 이벤트를 발생시키는 방법이나 결과를 확인하는 방법이 요구사항에 정의되어 있지 않다면 11절에 따라 질의로 확인한다.

## 11. 검증 난이도가 높은 요구사항의 처리

### 11.1 표준 실행 환경에서 직접 검증하기 어려운 요구사항

서버 내부 처리 방식, 전송 구간 보안, 암호화 저장 등 화면 조작만으로는 확인할 수 없는 비기능·보안 요구사항은 다음 기준으로 처리한다. 이는 서버 쪽에만 해당하는 것이 아니라, **네이티브 앱의 로컬 저장소(인증 토큰 등)처럼 클라이언트 쪽 내부 데이터**에도 동일하게 적용한다 — 화면에 표시되지 않는 값을 확인하려면 루팅·ADB 등 특수 도구가 필요한 경우가 많기 때문이다.

- **검증에 필요한 도구·권한이 사전조건으로 확보 가능한 경우** → TC로 작성하되, 사전조건에 해당 도구·권한이 필요함을 명시한다. (예: 네트워크 요청 캡처 도구, 데이터 저장소 조회 권한, 루팅된 단말·ADB 접근)
- **확보 여부가 불확실하거나 검증 주체가 개발·보안 담당인 경우** → TC로 무리하게 만들지 않고 **'확인 필요' 질의로 분류**하여 추적한다. 검증 방법 자체가 마땅치 않다고 판단되면, 이미 작성해 둔 TC라도 재검토하여 폐기(14.5)하고 질의로 전환한다.

> 검증 수행 자체가 QA의 몫이 아니더라도, **그것이 실제로 검증되었는지 추적하는 것은 QA의 몫이다.** 질의로 남겨 두는 것이 그 추적 기록이 된다.

### 11.2 실행에 장시간이 소요되는 요구사항

만료·보관 기간처럼 실행에 오랜 시간이 걸리는 TC는, 해당 시간을 단축·조절할 수 있는 테스트 환경이 지원되는지를 **별도 질의로 확인**한다. (예: 서버의 만료 시간 조절, 클라이언트 저장소의 값 직접 변경)

이는 기대 결과(요구사항 내용)에 대한 질의가 아니라 **TC 실행 가능성에 대한 질의**이므로, 요구사항 확인 질의와 구분하여 작성하고 확인 필요처를 개발로 지정한다.

## 12. 질의사항 분류 및 작성 규칙 ⭐

### 12.1 질의로 분류하는 상황

다음 상황에서는 TC를 임의로 확정하지 않고 **질의사항으로 분류**한다.

- 요구사항에 결과가 정의되어 있지 않은 경우
- 서로 다른 요구사항의 내용이 충돌하는 경우
- 수행 조건이 불명확한 경우
- 특정 상태에서의 동작이 정의되지 않은 경우
- 오류 발생 시 처리 방법이 정의되지 않은 경우
- UI 표시 여부가 정의되지 않은 경우
- 성공/실패 기준을 판단할 수 없는 경우
- 여러 결과가 가능하지만 어느 것이 맞는지 판단 근거가 없는 경우
- 테스트 수행에 필요한 환경·도구 지원 여부를 알 수 없는 경우 (11절)
- **테스트 수행을 위해 준비·지원이 필요한 경우** → 분류를 `요청사항`으로 등록한다 (12.5)

> **질의목록은 결함(버그)을 기록하는 문서가 아니다.** 요구사항과 다르게 이미 동작하는 것이 확인된 경우(결함)는 질의목록에 등록하지 않고 별도 결함 관리 채널로 넘긴다 (15.1).

### 12.2 질의 작성 순서

**현재 정의된 내용 → 불명확한 부분·문제 상황 → 확인이 필요한 사항** 순서로 작성한다.
"어떻게 되나요?" 식의 단순 의문형은 금지하며, **왜 이 질의가 필요한지**가 드러나야 한다.

### 12.3 질의 문체 규칙 ⭐

질의를 읽는 사람은 기획자·개발자 등 **QA 직군이 아닌 경우가 대부분**이다. 다음을 지킨다.

1. **비전공자가 읽어도 이해할 수 있도록 쉬운 말로 풀어 쓴다.**
   - 테스트 전문 용어(경계값, 사전조건, 밸리데이션, 커버리지 등)를 그대로 쓰지 않는다. 꼭 필요하면 괄호로 풀어 준다.
   - 예: "경계값 검증이 불가합니다" → "입력할 수 있는 글자 수의 최대 한도를 넘겼을 때 어떻게 되는지 정해져 있지 않아 확인이 어렵습니다"
2. **문의하는 형태의 존댓말로 작성한다.**
   - 권장 어미: `~확인 부탁드립니다`, `~인지 알려주시면 감사하겠습니다`, `~정해 주시면 반영하겠습니다`
   - 금지 어투: `~해야 함`, `~할 것`, `~필요`, 명사형 종결 등 지시·통보로 읽히는 표현
3. **약어·내부 용어는 처음 등장할 때 풀어 쓴다.** (예: `BR-001(비즈니스 규칙 1번)`)
4. **선택지가 있으면 안(案)으로 제시한다.** 답변자가 고르기만 하면 되도록 만들면 회신이 빨라진다.
   - 예: `• 1안: 앞뒤 공백을 자동으로 지우고 정상 처리` / `• 2안: 공백이 포함되면 형식 오류로 안내`
5. **질의 내용(제목)은 한 문장으로, 제목만 읽어도 무엇을 결정해야 하는지 파악되게 쓴다.**
   - 금지: `확인 필요`, `문의드립니다` 등 대상이 드러나지 않는 제목

**작성 예시**

> **질의 내용**: 아이디 입력값 앞뒤에 공백이 있을 때의 처리 방식을 정해 주시기 바랍니다.
>
> **상세 내용**: 현재 기획서에는 아이디의 형식(이메일 형태)과 최대 글자 수(100자)만 정의되어 있습니다. 사용자가 아이디를 복사해서 붙여 넣는 경우 앞뒤에 공백이 함께 들어가는 일이 자주 발생하는데, 이때 어떻게 처리할지가 정해져 있지 않아 기대 결과를 확정하기 어렵습니다. 아래 두 가지 중 어느 방향인지 확인 부탁드립니다.
> • 1안: 앞뒤 공백을 자동으로 제거한 뒤 정상적으로 로그인 처리
> • 2안: 공백이 포함된 경우 형식 오류로 안내

### 12.4 TC ↔ 질의목록 연결 규칙

1. TC 작성 중 불명확한 부분을 발견하면 질의목록에 등록한다.
2. 질의목록의 `원본 TC`에는 **실제로 존재하는 TC ID만** 연결한다.
3. `원본 TC`에는 **그 TC의 비고에 실제로 해당 질의가 연결된 TC만** 적는다. 성공/실패, 만료/유지처럼 한 세트로 인식되는 TC라도, 질의가 달리지 않은 쪽은 연결하지 않는다.
4. 질의 상세 내용에서 언급한 TC와 `원본 TC` 컬럼의 목록이 서로 일치하는지 대조한다.
5. TC와 질의목록에서 동일 내용을 서로 다른 의미로 작성하지 않는다.
6. 하나의 TC에서 여러 독립적 정책 확인이 필요하면 질의를 각각 분리한다.
7. 하나의 질의가 여러 TC에 영향을 주면 관련 TC를 모두 연결한다.
8. 질의가 해결되기 전에는 해결내용·결정사항을 임의로 작성하지 않는다.
9. 질의 때문에 기대 결과를 확정할 수 없는 경우, 해당 TC의 기대 결과에 추측성 내용을 작성하지 않는다.
10. 질의로 분류한 내용은 비고에만 남기지 말고 **질의목록에도 반드시 작성한다.**
11. 질의목록의 컬럼명·문서명에는 결함 추적을 연상시키는 `이슈` 대신 **`질의`** 또는 **`확인 요청`**을 사용한다. 질의목록은 결함을 기록하는 문서가 아니라 확인·결정을 요청하는 문서다.
12. 관련 TC ID는 질의 내용 텍스트 안에 섞어 쓰지 않고 반드시 **별도 컬럼(`원본 TC`)**에 둔다. 추적·정렬·필터링이 가능해진다.

### 12.5 테스트 요청사항 등록 ⭐

요구사항의 불명확함뿐 아니라, **테스트를 수행하기 위해 필요한 준비·지원 요청**도 질의목록에 함께 등록하고 분류를 **`요청사항`**으로 지정한다. 별도 문서로 관리하지 않고 질의목록에 모아 두어야 확인·회신 상태를 한 곳에서 추적할 수 있다.

**요청사항에 해당하는 예**

- 테스트 계정 발급 (권한별 계정, 탈퇴·비활성 등 상태별 계정)
- 테스트 데이터 준비 (특정 조건을 만족하는 데이터, 대량 데이터 등)
- 테스트 환경·서버 접근 권한, 관리자 기능 사용 권한
- 특정 상태를 재현하기 위한 설정 지원 (만료 시간 조절, 강제 상태 변경 등 — 11.2)
- 검증에 필요한 도구·로그 접근 권한 (11.1)
- **QA가 표준 실행 환경에서 직접 검증할 수 없어 TC를 폐기한 항목에 대해, 개발팀의 자체 확인·검증 결과 공유를 요청하는 경우** (11.1) — 이 경우 질의 내용은 "~인지 확인해 주세요" 형태의 정책 질문이 아니라 "~를 확인하고 결과를 공유해 주세요" 형태의 확인 요청이 된다.

**작성 규칙**

- `원본 TC`에 해당 요청이 필요한 TC ID를 연결하여, 무엇을 수행하기 위한 요청인지 드러나게 한다. TC를 폐기하고 전환한 경우 폐기된 TC ID를 그대로 연결한다 (14.5).
- `확인 필요처`는 실제 요청 대상(개발 / 기획 / 인프라 등)으로 지정한다. 알 수 없으면 임의로 지정하지 않는다.
- 문체는 12.3을 동일하게 따른다 (쉬운 말 · 존댓말 문의체).
- 요청 대상이 여러 건이면 성격별로 분리하여 등록한다. 하나의 요청에 여러 준비 항목을 묶으면 부분 완료 상태를 추적할 수 없다.
- `상세 내용`에 근거가 되는 기획서 조항(문서명·항목·BR 번호 등)을 인용한다. 질의목록 시트에는 TC 시트의 `기획서 출처`에 해당하는 컬럼이 없으므로, 답변자가 맥락을 바로 파악할 수 있도록 상세 내용 안에 출처를 명시한다.

## 13. 자동화 테스트를 고려한 작성

1. 테스트 대상과 검증 결과가 명확해야 한다.
2. 수행 절차는 일관된 형태로 작성한다.
3. 동일 목적의 TC를 불필요하게 중복 생성하지 않는다.
4. 테스트 데이터와 기대 결과를 명확히 구분한다.
5. 모호한 수동 판단이 필요한 TC는 최소화한다.
6. 자동화가 어렵더라도 요구사항 검증에 필요한 TC는 임의로 제외하지 않는다.
7. 자동화하기 쉽다는 이유만으로 테스트 범위를 축소하지 않는다.

## 14. 엑셀 출력 형식

### 14.1 파일·시트 구성 원칙

- 제공된 TC 엑셀 파일의 시트 구성·컬럼 순서·컬럼명·기본 서식을 유지한다. 병합 셀, 헤더 구조, 열 순서를 가능한 유지한다.
- 새 정보가 기존 컬럼 어디에 해당하는지 판단할 수 없으면 새 컬럼을 만들지 않고 기존 구조에 맞추거나 질의사항으로 분류한다.
- **시트 순서**는 다음을 기본으로 한다.

| 순서 | 시트 | 비고 |
|---|---|---|
| 1 | `개요` | **항상 가장 앞 시트.** 담당자·일정·검증 환경 표지 (14.3) |
| 2 | `AI개요` | 산출물 구성·요약·자체 검증 결과 (14.4) |
| 3 | `[기능명] TC` | 기능별로 분리 |
| 4 | `[기능명] 질의목록` | 해당 기능 TC 시트 바로 뒤 |
| … | (기능 수만큼 3~4 반복) | |
| 마지막 | `변경이력목록` | 개정본에만 작성 (15절) |

- TC 시트와 질의목록 시트는 반드시 분리한다.
- 기능이 여러 개면 기능별로 TC 시트와 질의목록 시트를 각각 분리하고, **TC 시트 → 해당 기능 질의목록 시트** 순으로 인접 배치한다.
- **TC ID는 여러 TC 시트에 걸쳐 연속 부여**하여 문서 전체에서 유일하게 식별되도록 한다. 질의 ID도 동일하게 문서 전체 기준으로 부여한다.
- **신규 TC·질의를 추가할 때는 항상 문서 전체에서 가장 큰 번호 다음 순번으로 끝에 추가한다.** 개념적으로 관련된 TC 근처에 배치하기 위해 기존 ID를 재정렬하지 않는다. ID 순서와 1뎁스·2뎁스에 의한 개념적 그룹핑은 서로 다른 기준이며, 재정렬하면 비고의 질의 연결, 질의목록의 원본 TC 등 모든 참조를 함께 갱신해야 하는 비용이 발생한다.
- (v2.5 신설) **하위번호 예외 — 기존 TC 하나와 강하게 결합된 소수의 변형만 하위번호로 추가할 수 있다.** 형식은 원본 TC ID 뒤에 `-N`을 붙인다 (예: `TC-260904-001-1`, `TC-260904-001-2`). 다음 두 조건을 모두 만족할 때만 사용한다 — ① 검증 목적이 기존 TC 하나와 사실상 동일하고 입력 조건(필드·경계값 등)만 다른 변형일 것, ② 그 기존 TC 바로 옆에 두지 않으면 위 마지막 번호 추가 규칙(문서 끝에 추가)으로는 관련성이 쉽게 드러나지 않을 것. 두 조건을 만족하지 않는 일반적인 신규 커버리지(새로운 검증 대상·다른 기능 영역 등)는 하위번호를 쓰지 않고 기존 규칙대로 문서 마지막 번호에 추가한다. 하위번호는 문서 전체에서 유일해야 하며, 같은 TC에 하위번호가 이미 있으면 다음 순번(`-3`, `-4`…)으로 이어 붙인다.
  - **왜 필요한가**: 마지막 번호 추가 규칙은 ID 순서와 행 위치를 항상 일치시켜 재정렬 비용을 없애지만, 기존 TC와 개념적으로 강하게 묶인 변형까지 문서 끝으로 보내면 정작 그 변형이 어떤 TC의 파생인지 찾기 어려워진다. 하위번호는 원본 TC 바로 뒤에 위치하므로 ID 순서와 행 위치가 계속 일치하면서도(엑셀에서 TC ID 기준으로 정렬해도 원본 옆에 그대로 남는다) 관련성이 유지된다.
- (v2.6 변경) **TC ID에 배포(예정)일자를 접두어로 넣는다.** 형식은 `TC-YYMMDD-001`처럼 `TC-` 뒤에 배포(예정)일자 6자리(YYMMDD), 그 뒤에 3자리 순번을 붙인다 (예: `TC-260904-001`, `TC-260904-002`). 하위번호와 함께 쓰면 `TC-260904-001-1`처럼 날짜·순번 뒤에 하위번호를 이어 붙인다.
  - **"만든 날짜"가 아니라 "배포(예정)일자"다.** 프로젝트가 무산되면 그 날짜는 그냥 안 쓰이고 끝난다. 배포 전에 배포일이 밀리면 그때는 엑셀·코드 양쪽의 날짜를 새 배포일로 치환한다. **배포가 이미 나간 뒤에는 바꾸지 않는다** — 이슈 티켓·공유된 리포트가 이미 그 ID를 가리키고 있기 때문이다.
  - **번호는 파일 전체 공유가 아니라 새 TC 엑셀 파일마다 001부터 새로 시작한다.** 한 파일 안에 여러 기능·화면이 섞여 있어도(예: 한 배포가 알림 관리와 로그인을 동시에 건드리는 경우) 001~순번을 그대로 연속으로 이어간다 — 1뎁스·2뎁스가 이미 기능을 구분해 주므로 ID에 별도 기능 코드를 또 넣을 필요가 없다.
  - **같은 날짜에 배포되는 TC 파일이 두 개 이상이면 접두어가 겹칠 수 있다.** 이때 날짜를 억지로 하루씩 밀어 피하지 않는다 — 아래 파일명 규칙에 따라 파일명 자체에 이미 배포일자가 들어가므로 어느 파일 소속인지는 파일명으로 구분된다. 다만 같은 날짜의 TC ID가 서로 다른 두 엑셀에 겹쳐 등록되지 않았는지는 신규 파일을 만들 때 사람이 한 번 확인한다.
  - **적용 범위**: 이 규칙은 새로 시작하는 TC 파일부터 적용한다. 이미 프리픽스 코드로 작성됐거나 프리픽스가 아예 없는 기존 파일(예: 기존 로그인·알림설정 TC)은 소급 적용하지 않는다.
  - **왜 바꿨는가 (2026-08-28 기능 프리픽스 코드 규칙 폐지)**: 직전까지는 `TC-[코드]-001`(예: `TC-L-001`)처럼 기능별 1글자 코드를 붙이고 코드마다 번호를 리셋했다. 목적(파일마다 번호가 안 겹치게 하는 것)은 같았지만, 새 코드를 쓸 때마다 「프리픽스 배정표」를 조회·등록해야 하는 절차가 남았고, **한 배포 건이 여러 기능을 동시에 건드리면 코드 하나로 묶이지 않는 문제**가 있었다(실제로 "인스톨러(APP), 현장서비스 현황"처럼 한 프로젝트가 화면 두 개를 동시에 건드리는 사례가 있었음). 배포일자를 접두어로 쓰면 배정표 없이도 프로젝트 단위로 자연스럽게 유일해지고, 파일명만 봐도 언제 배포되는 TC인지 알 수 있다. 자동화 코드로 옮길 때는 이 날짜가 그대로 pytest 마커(`tc_260904`)가 되어 "이번 배포분만 실행"이 가능해지는 부수 효과도 있다 (자동화 코드 쪽 규칙은 프로젝트 `CLAUDE.md` 참조).

- (v2.6 변경) **TC 엑셀 파일명 규칙.** 기본 형식은 `TC_[서비스명]_[기능명]_[배포일자].xlsx`이다. `TC_` 뒤에 대상 서비스명, 기능명, 마지막에 TC ID와 같은 배포(예정)일자(YYMMDD)를 붙인다 (예: `TC_로그인_알림설정_260904.xlsx`). 서비스명을 특정하기 어렵거나 불필요하면 생략한다.
  - **파일명 끝의 배포일자와 그 안 TC ID의 접두어는 항상 같은 값이다.** 파일명만 보고도 그 안의 TC ID가 어떤 접두어를 쓰는지 바로 알 수 있어야 한다.
  - **이 배포일자는 15.2의 리비전 버전 표기(`_v2`, 개정 시점의 `_YYYYMMDD`)와는 다른 축이다.** 15.2 쪽은 "이 파일이 몇 번째 개정본인가"를 뜻하고, 여기 배포일자는 "이 TC들이 어느 배포를 검증하는가"를 뜻한다. 개정본을 낼 때 배포일자는 그대로 두고 15.2 규칙대로 버전 표기만 뒤에 더 붙인다 (예: `TC_로그인_알림설정_260904_v2.xlsx`).
  - **여러 서비스가 같은 기능을 공유해서 TC를 한 파일로 함께 작성하는 경우, [서비스명] 자리에 관련 서비스명을 모두 언더스코어로 나열한다** (예: `TC_STAFF_DUMP_보안인증강화_260904.xlsx`).
  - **토큰 구분은 언더스코어(`_`)만 사용한다.** 공백, 그리고 `/ \ : * ? " < > |` 등 OS·git·클라우드 동기화(OneDrive 등)에서 문제를 일으킬 수 있는 특수문자는 쓰지 않는다.
  - **`TC_` 접두는 항상 고정한다.** 폴더 안에서 기획서·정책 문서 등 TC가 아닌 파일과 한눈에 구분되고, 알파벳순 정렬에서 TC 파일들끼리 모이게 하기 위함이다.
  - **전체 길이는 대략 60자 이내로 유지한다.** 너무 길면 git 커밋 메시지·채팅 공유·탐색기 목록에서 가독성이 떨어진다.

### 14.2 시트 공통 헤더 규칙 ⭐

모든 TC 시트와 질의목록 시트는 다음 3개 행으로 시작한다.

| 행 | 내용 |
|---|---|
| **1행** | **타이틀** — 기획서명 또는 서비스명, 대상 기능, 테스트 목표를 한 줄로 작성 |
| **2행** | **작성 정보** — `작업자: OOO \| TC 작성일: YYYY-MM-DD \| 테스트 수행일: YYYY-MM-DD` |
| **3행** | **컬럼 헤더** (TC ID / 1뎁스 / … 또는 질의 ID / 분류 / …) |
| 4행~ | 데이터 |

- 타이틀은 시트만 열어도 **무엇에 대한 테스트인지** 알 수 있게 작성한다.
  - 예: `FMS Admin Web 알림 설정 — 수신 유형·수단 설정 및 저장 기능 검증`
- `테스트 수행일`은 초안 산출 단계에서는 아직 실행 전이므로 `-` 또는 `미실행`으로 둔다. **AI가 임의의 날짜를 채우지 않는다.**
- `작업자`는 실제 TC 작성 담당자명을 기재한다. 확인되지 않으면 임의로 지정하지 않는다.
- 3행(컬럼 헤더)에 틀 고정과 필터를 적용한다.

### 14.3 개요 시트 구성 ⭐

`개요` 시트는 **담당자 · 일정 · 검증 환경**을 한 장으로 보여주는 표지 시트로, 항상 **가장 앞(첫 번째) 시트**에 둔다.
**항목을 임의로 늘리지 않는다.** 간단하되 적힌 값은 모두 명확해야 한다.

**타이틀** — 표 위에 한 줄로 작성한다. 형식: `[서비스명 / 대상 기능]_TC`
예) `STAFF 리셀러 / 파트너 개선 정책_TC`

**① 담당자 행** (4열 구조)

| QA | 기획 | 프론트 | 백엔드 |
|---|---|---|---|
| (QA 담당자명) | | | |

**② 정보 행** (1열에 항목명, 값은 나머지 열을 병합하여 작성)

| 항목 | 작성 규칙 |
|---|---|
| TC 설계 시간 | **설계 시작 시점만** 작성한다 (예: `2026.08.`). 종료 시점은 임의로 채우지 않는다. |
| 검증 시작일 | 실제 테스트 시작일. 미정이면 `-` |
| 검증 종료일 | 실제 테스트 종료일. 미정이면 `-` |
| 배포 예정일 | 확인된 경우만 작성. 미정이면 `-` |
| 검증환경 범위 | 테스트 대상 환경 (예: `Web - Chrome`, `Android App`) |
| 최종 Apk 버전 | 앱 테스트인 경우 빌드 버전. 해당 없거나 미정이면 `-` |
| 비고 | 주로 **테스트 대상 사이트 주소**를 기록한다. 환경이 여러 개면 구분하여 작성 (예: `Dev: https://…` / `Live: https://…`) |

**③ 임의 작성 금지 항목** ⭐

- **담당자(기획 · 프론트 · 백엔드 등)** — 확인되지 않은 담당자를 추측하여 채우지 않는다. 확인 전에는 빈칸 또는 `-`로 둔다.
- **TC 설계 시간의 종료 시점** — 시작 시점만 작성하고 종료 시점은 비워 둔다.
- **검증 시작일 · 검증 종료일 · 배포 예정일** — 실행 전이거나 확정되지 않았다면 `-`로 둔다. AI가 임의의 날짜를 채우지 않는다.
- **최종 Apk 버전** — 확인된 빌드 버전이 없으면 `-`로 둔다.

### 14.4 AI개요 시트 구성 ⭐

`AI개요` 시트는 산출물 전체 구성을 한 눈에 파악하기 위한 시트로, `개요` 시트 **바로 다음(두 번째)**에 둔다. 다음 항목을 순서대로 구성한다.

| 번호 | 항목 | 내용 |
|---|---|---|
| — | **문서 타이틀** | 기획서명·서비스명 + 문서 성격(TC 초안 등) |
| — | **사전조건 작성 규칙 (필독)** ⭐ | 문서 타이틀 바로 아래, 문서 정보보다도 앞에 배치한다. 7.1의 사전조건 작성 규칙(번호·라벨 없이 고정 순서로 줄바꿈)을 강조 표시(굵게·배경색 등)로 다시 안내한다. 지침 문서를 열지 않고 엑셀만 봐도 규칙을 확인할 수 있어야 한다. |
| 1 | **문서 정보** | 대상 요구사항(문서명·버전) / 작성 기준(본 지침) / **사용 모델** / 작업자 / TC 작성일 / 테스트 수행일 / 문서 버전 / 작성 단계 |
| 2 | **시트 구성** | 시트명 / 내용 / 건수 / ID 범위 |
| 3 | **TC 구성 요약** | 1뎁스·2뎁스별 TC 건수와 TC ID 범위, 소계·합계 |
| 4 | **질의 분류별 요약** | 분류별 건수 (기능별 열 + 합계) |
| 5 | **우선 확인 필요 질의** | 기대 결과를 확정할 수 없어 답변이 시급한 질의 (질의 ID / 내용 / 영향 TC / 확인 필요처) |
| 6 | **작성 기준 및 전제** | 해당 산출물에 적용한 판단 전제. 본 지침에 없는 프로젝트 고유 판단은 여기에 기록한다 |
| 7 | **자체 검증 결과** | 16절 체크리스트의 실제 수행 결과 |
| 8 | **표시 범례** | 배경색 의미 (14.7) |

- **`사용 모델`** 에는 TC 초안 생성에 사용한 모델명을 기록한다. 산출물의 판단 성향(질의 검출 정도, 추측 혼입 여부)이 모델에 따라 달라질 수 있어 검수 시 참고 정보가 된다. 단계별로 다른 모델을 사용했다면 단계와 함께 기록한다. (예: `초안 생성 Claude Opus 5 / 포맷 정리 Claude Sonnet 5`)
- AI개요 시트의 수치(건수·ID 범위)는 **실제 시트 내용과 반드시 일치**해야 한다. TC를 추가·삭제하면 AI개요 시트를 함께 갱신한다.
- AI개요 시트는 설명 문서이므로 TC 시트와 달리 자유 서식(병합·구획)을 사용해도 된다.

### 14.5 TC 시트 컬럼 규칙

| 컬럼 | 작성 규칙 |
|---|---|
| TC ID | (v2.6 변경) `TC-YYMMDD-001`, `TC-YYMMDD-002`… 배포(예정)일자 접두어 + 3자리 순번으로 고정하여 순차 부여 (099 다음은 100), 새 파일마다 001부터 시작, 파일 내 중복 금지 (14.1). 삭제/재정렬 시 ID 재사용 가능하나 참조된 ID는 일괄 수정. 검수·공유 이후 단계에서는 행 삭제 대신 "폐기" 상태로 표시하여 결번 유지 (아래 「폐기 처리 규칙」 참조). 신규 TC는 항상 문서 전체의 마지막 번호 다음으로 추가한다 (14.1). 단, 기존 TC 하나와 강하게 결합된 소수의 변형은 `TC-260904-001-1`처럼 원본 뒤에 `-N`을 붙인 하위번호로 원본 바로 뒤에 추가할 수 있다 (14.1 하위번호 예외). |
| 1뎁스 | 기능의 최상위 분류. 서비스명(또는 요구사항에 정의된 기능명·메뉴명)을 우선 사용. 동일 기능은 동일 1뎁스. 임의 신규 분류 생성 금지. |
| 2뎁스 | 1뎁스에 속하는 세부 기능·메뉴. **주로 GNB(상단 내비게이션)에 표기된 메뉴명을 그대로 사용한다.** GNB에 없는 하위 기능이면 화면에 표기된 실제 메뉴명·탭명을 사용. 동일 기능을 다른 명칭으로 표현하지 않음. |
| 3뎁스(검증 포인트) | 무엇을 검증하는지 한 문장으로 명확히. 하나의 주요 검증 목적만. `~확인`·`~검증` 형태로 통일. 기능명 단순 반복 금지. (나쁜 예: "파트너 관리" / 좋은 예: "파트너 필터 선택 항목 확인") 추가로 다음을 피한다: 조건이 다른데 같은 TC명을 재사용하지 않는다(조건을 이름에 포함), 동작만 쓰고 결과를 빠뜨리지 않는다(`[저장] 버튼 클릭` → `[저장] 클릭 시 목록 갱신 확인`), "정상"·"기본" 같은 수식어를 단독으로 쓰지 않는다(무엇이 정상인지 명시). |
| 사전조건(Pre-condition) | 7절의 4요소(사용자·권한 → 화면 위치 → 데이터 상태 → 선행 작업 상태)를 이 순서대로, **번호·라벨 없이** 줄을 나누어 작성. 없으면 `-`. 선행 TC 의존성이 있으면 7.5에 따라 표기. |
| 테스트 절차 | 8절에 따라 수행 순서대로 번호 부여. 검증 결과는 기대 결과에 작성. 없으면 `-`. |
| 테스트 데이터 | 절차에서 사용하는 실제 입력값·조건. 경계값은 실제 값을 그대로 기재. 없으면 `-`. 모호한 표현 금지. 운영 데이터(실명·실제 연락처 등) 사용 금지 (5절 11항). |
| 기대 결과 | 9절에 따라 검증 대상과 결과 상태를 구체적으로. 요구사항에 정의된 결과만. 절차 대상 범위와 일치시킬 것. 논리적으로 항상 참이 되는 문장이 아닌지 확인 (9.3). |
| 실제 결과 | **TC 생성 단계에서는 값을 작성하지 않고 비워 둔다.** 실행 결과가 제공된 경우에만 작성하며, AI가 결과를 추측하여 채우지 않는다. 입력 가능한 값은 아래 「실제 결과 입력 규칙」의 4개로 제한한다. |
| 비고 | 수행 중 확인된 특이사항·추가 확인사항. 질의로 분류한 내용은 `→ ID-0NN` 형태로 질의 ID를 연결한다. 자동화 불가 사유는 `[자동화 불가]` 태그로 시작해 다른 비고 내용과 구분한다 (아래 「자동화 가능 여부 입력 규칙」). 실측 대조 중 발견된 결함은 `[결함]` 태그와 결함 관리 채널의 참조 ID만 연결한다 (15.1). 단순 설명 반복 금지. 비고에만 남기지 말고 질의목록에도 작성. |
| 우선순위 | 아래 「우선순위 입력 규칙」에 따라 P0/P1/P2 중 하나로 작성. |
| 기획서 출처 | TC 근거가 되는 기획서·요구사항·화면·정책의 출처. 가능하면 문서명 + 항목 위치를 포함. 페이지 번호·문서명 추측 생성 금지. |
| 자동화 가능 여부 | 아래 「자동화 가능 여부 입력 규칙」에 따라 작성. |

#### 실제 결과 입력 규칙 ⭐

**① 허용 입력값** — 다음 4개 값만 사용한다. 엑셀 **데이터 유효성 검사(목록)**를 걸어 그 외의 값이 입력되지 않도록 제한한다.

| 값 | 의미 |
|---|---|
| `PASS` | 기대 결과와 실제 동작이 일치함 |
| `FAIL` | 기대 결과와 실제 동작이 일치하지 않음 |
| `N/A` | 해당 없음 (테스트 대상이 아니거나 조건상 수행 대상이 아님) |
| `N/T` | 미수행 (Not Tested — 아직 실행하지 않음) |

- TC 초안 생성 단계에서는 **전 행을 빈 값으로 둔다.** 유효성 검사와 아래 셀 강조 규칙만 미리 설정해 둔다.
- 서술형 문장(예: "정상 동작함")을 실제 결과 컬럼에 쓰지 않는다. 실행 중 확인된 특이사항은 `비고`에 작성한다.

**② 셀 강조 규칙** — 엑셀 **[조건부 서식] > [셀 강조 규칙] > [같음(=)]**으로 값별 서식을 지정한다.

| 값 | 서식 |
|---|---|
| `PASS` | 진한 녹색 텍스트가 있는 녹색 채우기 |
| `FAIL` | 진한 빨강 텍스트가 있는 연한 빨강 채우기 |
| `N/A` | 진한 노랑 텍스트가 있는 노랑 채우기 |
| `N/T` | **사용자 지정** — 진한 검정 글씨 / 연회색 바탕 |

- `PASS` · `FAIL` · `N/A`는 엑셀이 기본 제공하는 서식을 그대로 선택한다.
- `N/T`는 기본 제공 서식에 없으므로 [사용자 지정 서식]에서 글꼴 색 진한 검정, 채우기 연회색으로 직접 지정한다.

#### 우선순위 입력 규칙 ⭐

TC 실행 순서를 판단하기 위한 값으로, 다음 값 중 하나로 제한한다 (데이터 유효성 검사 목록 적용).

| 값 | 의미 |
|---|---|
| `P0` | 필수 — 실사용 빈도가 높고, 깨지면 기능 자체가 동작하지 않는 것과 같은 파급을 가짐 |
| `P1` | 중요 — 빈도·파급 중 하나만 해당 (자주 발생하지만 영향은 부분적이거나, 드물지만 영향이 큼) |
| `P2` | 낮음 — 빈도·파급 모두 낮음. 완결성을 위해 필요하나 급하지 않음 |

**판단 기준** — 다음 2가지 질문으로 판단한다.

1. 실제 사용자가 이 경로를 얼마나 자주 타는가 (빈도)
2. 이게 깨지면 기능 전체가 막히는가, 일부만 영향받는가 (파급 범위)

정상/예외/경계(6절) 분류와는 다른 축이다. 경계값 TC라도 보안과 직결되면 P0이 될 수 있고, 정상 흐름이라도 부가 기능이면 P1에 머물 수 있으므로 "정상 조건=P0" 식으로 자동 매핑하지 않고 매 TC마다 위 두 질문으로 판단한다.

**단, 보안 취약점·데이터 손실/오염·업무 수행 불가와 직결되는 TC는 발생 빈도와 무관하게 P0으로 고정한다.** 빈도가 낮다는 이유로 심각도가 높은 항목의 우선순위를 낮추지 않는다. (예: 발생 빈도가 낮은 공격 시나리오라도 인증 우회·데이터 유출로 이어지면 P0)

#### 자동화 가능 여부 입력 규칙 ⭐

TC를 작성하는 시점에 자동화 가능성을 판단해 기록한다. 나중에 자동화 담당자가 전체 TC를 처음부터 다시 판단하는 비용을 없애기 위함이다. 다음 값 중 하나로 제한한다 (데이터 유효성 검사 목록 적용).

| 값 | 의미 |
|---|---|
| `자동화 가능` | 화면을 읽어 대조할 정답 출처가 있어 자동화로 확인 가능 |
| `자동화 불가` | 사람의 판단·개입 없이는 확인할 수 없음 |
| `조건부 가능` | 일부 단계만 자동화 가능하거나, 특정 전제(도구·환경) 하에서만 가능 |

- `자동화 불가` 또는 `조건부 가능`으로 판단한 경우, **무엇이 없어서 그런지**를 비고에 `[자동화 불가]` 또는 `[조건부 가능]` 태그로 시작해 구체적으로 남긴다. 다른 비고 내용(질의 연결, 폐기 사유, 결함 참조 등)과 섞이지 않도록 태그로 구분한다.
  - 예: `[자동화 불가] 데이터를 실제로 바꿔야만 확인됨 ([초기화] 실행 결과)`
  - 예: `[자동화 불가] 화면에 판별 근거가 없음 (목록에 비교 대상 값이 표시되지 않음)`
  - 예: `[자동화 불가] 증빙 이미지의 육안 확인이 필요함`

#### 폐기 처리 규칙 ⭐

작성 완료 후 재검토 결과 TC를 유지할 수 없게 된 경우(예: 11.1에 따라 QA가 검증하기 어려운 항목으로 재판정됨), 행을 삭제하지 않고 다음과 같이 **폐기 표시만** 한다.

1. `TC ID`, `1뎁스`, `2뎁스`는 그대로 둔다.
2. `3뎁스(검증 포인트)` 맨 앞에 `[폐기]`를 붙인다.
3. `사전조건`·`테스트 절차`·`테스트 데이터`·`기대 결과`는 원래 내용을 유지한다 (무엇을 검증하려 했는지 기록으로 남긴다).
4. `비고`에 폐기 사유와 전환된 질의 ID를 적는다. (예: `[폐기] ~한 이유로 QA가 직접 검증하기 어려워 TC에서 제외함. 개발팀 확인 요청으로 전환 → ID-0NN`)
5. 배경색은 14.7의 폐기 색상을 적용하고, 글자에 취소선을 넣는다.
6. 해당 TC를 근거로 등록했던 질의가 있다면, 그 질의의 `원본 TC`는 폐기된 TC ID를 그대로 유지한다 (질의가 어떤 TC에서 비롯됐는지 추적 가능하도록).

### 14.6 질의목록 시트 컬럼 규칙

| 컬럼 | 작성 규칙 |
|---|---|
| 질의 ID | `ID-001`, `ID-002`… 순차 부여, 각 질의 고유 ID. 문서 전체 기준으로 유일하게 부여. |
| 분류 | 질의 성격 (예: 정책결정 필요 / 기획 확인 필요 / 개발 확인 필요 / 기획·개발 확인 필요 / **요청사항**). 테스트 수행에 필요한 준비·지원 요청은 `요청사항`으로 분류한다 (12.5). 기존 문서의 분류 체계가 있으면 우선 사용. |
| 원본 TC | 질의가 실제로 연결된 TC ID (12.4의 3항 기준). 여러 TC 관련 시 모두 명시. |
| 질의 내용 | 질의 핵심을 한 문장으로. 제목만 읽어도 결정 대상이 파악되게. 모호한 제목 금지. (12.3) |
| 상세 내용 | "현재 정의된 내용 → 불명확한 부분·문제 상황 → 확인이 필요한 사항" 순서. 비전공자가 이해할 수 있는 쉬운 말과 존댓말 문의체로 작성. 선택지가 있으면 1안·2안으로 제시. (12.3) |
| 확인 필요처 | 실제 결정 담당 영역 (예: 기획 / 개발 / 기획·개발 / QA). 담당자를 알 수 없으면 임의 지정 금지. |
| 상태 | 진행 상태 (예: 미확인 / 확인 중 / 결정 완료). 초기 생성 단계에서는 `미확인` 유지. |
| 해결내용/결정사항 | 답변·최종 결정이 확인된 경우만 작성. 초기 생성 단계에서는 **빈 값 유지**. AI가 임의 작성 금지. |

### 14.7 변경 표시(배경색) 규칙

개정본에서는 직전 버전 대비 변경된 행을 배경색으로 구분한다.

| 배경색 | 의미 |
|---|---|
| 옅은 초록 | 해당 버전에서 **신규 추가**된 행 |
| 옅은 주황 | 해당 버전에서 **수정·보완**된 행 |
| 옅은 회색 + 취소선 | 해당 버전에서 **폐기**된 행 (14.5 폐기 처리 규칙) |
| 무색(흰색) | 직전 버전과 동일 |

- 색상의 의미는 반드시 AI개요 시트의 **표시 범례**에 명시한다.
- 다음 버전을 만들 때는 이전 버전의 **신규·수정** 색상 표시를 해제하고, 그 버전에서 변경된 행만 다시 표시한다.
- **폐기(회색+취소선) 표시는 이 리셋 규칙의 예외다.** 신규·수정은 "이번 버전에서 바뀐 것"을 나타내는 버전별 신호라 매번 해제 후 다시 표시하지만, 폐기는 "이 행이 폐기 상태다"라는 지속 상태 표시이므로 해당 TC가 폐기 상태로 남아있는 한 버전이 바뀌어도 계속 유지한다 (3뎁스의 `[폐기]` 텍스트 태그를 다음 버전에서도 지우지 않는 것과 같은 이유). 폐기된 TC가 다시 활성화되는 경우에만 표시를 해제한다.
- 사전조건 라벨 제거, 셀 정렬처럼 **전 행에 동일하게 적용되는 서식 변경**은 개별 행 표시 대상에서 제외한다. 모든 행이 같은 색이 되면 색이 신호로서 기능하지 않으므로, 이런 경우 AI개요의 「작성 기준 및 전제」나 「표시 범례」에 일괄 적용 사실만 서술한다.

### 14.8 셀 정렬 규칙 ⭐

시트 성격에 따라 다음 정렬을 기본으로 적용한다.

| 시트 | 가로 정렬 | 세로 정렬 |
|---|---|---|
| `개요` (표지) | 전 항목 가운데 정렬 | — |
| `TC` 시트 | 1행(타이틀)·2행(작성 정보), `TC ID`, `1뎁스`, `2뎁스`, `실제 결과`, `우선순위`, `자동화 가능 여부`만 가운데 정렬. 그 외 컬럼(사전조건·절차·데이터·기대 결과·비고·출처 등 서술형 텍스트)은 기본 정렬(왼쪽) 유지 | 전 셀 가운데 정렬(위아래 중) |
| `질의목록` 시트 | 1행·2행, `질의 ID`, `분류`, `원본 TC`, `확인 필요처`, `상태`만 가운데 정렬. `질의 내용`·`상세 내용`은 기본 정렬(왼쪽) 유지 | 전 셀 가운데 정렬(위아래 중) |

- 짧고 정형화된 값(ID, 분류명, 뎁스, PASS/FAIL 등)은 가운데 정렬해야 표를 훑어볼 때 값이 잘 들어온다.
- 문장형 서술 컬럼(사전조건, 절차, 기대 결과, 질의 내용 등)은 왼쪽 정렬을 유지한다. 긴 텍스트를 가운데 정렬하면 줄마다 시작 위치가 달라져 오히려 읽기 어렵다.
- 세로 정렬은 컬럼 종류와 무관하게 TC·질의목록 시트 전체에 위아래 가운데(가운데 맞춤)를 적용한다. 줄바꿈이 있는 셀과 없는 셀이 섞여 있을 때 위쪽 정렬(맨 위 고정)보다 가운데 정렬이 행 전체의 시각적 균형을 맞춘다.
- 컬럼 너비는 TC 시트를 열었을 때 스크롤 없이 비고 컬럼까지 한 화면에 들어오는 것을 기준으로 조정한다.

### 14.9 글꼴 규칙

모든 시트, 모든 셀은 **Arial**로 통일한다. 영문·숫자·기호는 Arial로 표시되며, 한글은 Arial에 글리프가 없어 뷰어의 시스템이 자동으로 대체 글꼴(예: 맑은 고딕)로 표시한다 — 이는 뷰어 환경에 따른 자연스러운 대체이며, 지정 글꼴 자체는 Arial로 통일한다.

## 15. 실측 대조 및 파일 버전 관리 ⭐

### 15.1 실측 대조 — 지침의 역할은 초안까지다

TC 초안은 **요구사항 문서만 보고** 작성한다. 그 시점에는 실제 화면이 없거나 아직 확인하지 못했으므로, 문서에 적힌 대로 쓰는 것이 맞다. **문제는 그 초안이 검증 없이 그대로 정본이 되는 것이다.**

화면이 만들어진 뒤에는 반드시 **초안을 실측(실제 화면)과 대조**하고, 아래 세 가지를 처리한다.

| 실측에서 드러나는 것 | 처리 |
|---|---|
| 요구사항엔 있는데 **화면에 없다** | TC를 삭제하거나 `[확인필요]` 질의로 전환. 삭제 사유를 비고에 남긴다 |
| 요구사항과 **동작이 다르다** | 실측 기준으로 TC를 정정하고, 무엇이 달랐는지 비고에 남긴다 |
| 요구사항의 **코드값이 화면에 보이지 않는다** | 화면에 표시되는 실제 표기로 바꾼다 |

**결함(버그)과 질의(질문)를 구분한다.** 실측 대조 중 "요구사항과 다르게 이미 동작한다"는 것이 발견되면, 이는 질문이 아니라 결함이다. 질의목록은 정책·기획을 확인받는 문서이지 결함을 기록하는 문서가 아니므로, 결함은 질의목록에 등록하지 않고 별도 결함 관리 채널(버그 트래커 등)에 등록한다. 해당 TC의 비고에는 `[결함]` 태그와 결함 관리 채널의 참조 ID만 연결한다.

(v2.5 신설) **초안 작성 시점에 이미 실제 동작을 알고 있는 경우도 마찬가지로 취급한다.** 유사 시스템의 과거 실행 이력, 이전 버전 TC의 실측 결과, 참고용으로 받은 타 TC 문서 등을 통해 초안을 쓰는 시점에 이미 실제 동작(문구 차이, 버튼 표기, 알려진 버그 등)을 알고 있더라도, 그 지식을 기대 결과에 끌어와 반영하지 않는다. 초안의 기대 결과는 어디까지나 **요구사항 문서 기준**으로 쓰고, 알고 있는 실제 동작 차이는 질의목록에 근거로 남겨 기획 확인을 받는다. 위 표의 실측 대조는 화면이 만들어진 뒤 공식적으로 수행하는 별도 단계이며, 초안 작성 중에 임의로 앞당겨 반영하지 않는다.

> 실측 대조를 수행하는 주체가 QA가 아니더라도, **그것이 실제로 대조되었는지 추적하는 것은 이 지침이 다루는 범위다.** 대조 없이는 초안의 오류가 그대로 정본에 남는다.

### 15.2 파일 버전 관리 규칙

초기 TC 초안이 산출된 뒤 수정이 필요한 경우(실측 대조에 따른 정정 포함), **원본 파일을 직접 수정하지 않는다.**

1. **원본을 복제하여 새 파일을 만들고, 복제본을 수정한다.** 원본 파일은 삭제하거나 덮어쓰지 않는다.
2. 파일명은 버전을 구분할 수 있게 부여한다.
   - `[원본파일명]_v2.xlsx`, `_v3.xlsx` … 또는 `[원본파일명]_YYYYMMDD.xlsx`
3. 복제본의 **AI개요 시트**에 다음을 기록한다.
   - 문서 버전, 개정일
   - 직전 버전 파일명
   - 직전 버전 대비 변경 요약 (신규 N건 / 수정 N건)
4. 변경된 행은 14.7의 배경색 규칙으로 표시한다.
5. 변경 내역이 여러 건이면 마지막 시트에 **`변경이력목록`** 시트를 추가하고 다음을 작성한다.
   - 비교 대상(원본 파일 / 개정본)과 비교 방법
   - 신규 추가 항목 (ID / 내용 / 추가 사유)
   - 수정 항목 (ID / 변경 전 → 변경 후 / 수정 사유)
   - **검토했으나 반영하지 않은 항목과 그 사유**
   - 표시 범례
6. 어떤 파일이 최신 버전인지 AI개요 시트만 보고 판단할 수 있어야 한다.

> **이유**: 초기 산출물은 검수·공유의 기준점이 되므로, 원본이 덮어써지면 "무엇이 언제 왜 바뀌었는지" 추적이 불가능해진다. 리뷰어가 원본과 개정본을 나란히 대조할 수 있어야 한다.

## 16. 최종 자체 검증 (TC 초안 산출 직전 반드시 확인)

### 요구사항 근거

- [ ] 요구사항에 없는 내용을 임의로 추가하지 않았는가?
- [ ] 요구사항 간 충돌·누락을 질의사항으로 분류했는가?

### TC 품질
- [ ] 동일 목적의 TC가 중복되지 않았는가?
- [ ] 하나의 TC에 지나치게 많은 검증 목적이 포함되지 않았는가?
- [ ] 정상/예외/경계 조건이 필요한 경우 누락되지 않았는가?
- [ ] 상태 전이의 트리거와 결과 상태를 모두 검증했는가? (6.1)
- [ ] 상태·권한에 따른 결과 차이가 필요한 경우 분리했는가?
- [ ] 서버 내부 구현·암호화, 네이티브 앱 로컬 저장소 등 QA가 표준 실행 환경에서 직접 검증하기 어려운 TC가 섞여 있지 않은가? 있다면 폐기하고 질의(요청사항)로 전환했는가? (11.1)
- [ ] 뎁스 그룹당 TC 밀도가 적정 범위(1뎁스 3~15개, 2뎁스 3~10개)에 있는가? 뎁스 구조(2뎁스/3뎁스)를 기능 복잡도에 맞게 선택했는가? (3절)
- [ ] 결과 메시지가 같아도 입력 조건(어느 필드가 비었는가 등)이 다른 케이스를 하나로 합치지 않고 분리했는가? (3절)

### 사전조건 · 절차 · 기대 결과
- [ ] 사전조건이 4요소(사용자·권한 / 화면 위치 / 데이터 상태 / 선행 작업 상태) 순서로 작성되었는가? (7절)
- [ ] 사전조건에 번호(①②③④)나 라벨("사용자/권한:" 등)이 남아 있지 않은가? 줄바꿈만으로 구분되어 있는가? (7.1)
- [ ] 사전조건과 절차에 동일한 조작이 중복 기술되지 않았는가? (7.3)
- [ ] 사전조건과 테스트 데이터를 혼동하지 않았는가? (7절)
- [ ] 동일한 사전조건 조합이 5회 이상 반복되면 템플릿으로 승격해 원본 문구를 재사용했는가? (7.6)
- [ ] 절차가 다루는 항목 범위와 기대 결과가 서술하는 항목 범위가 일치하는가? (9.1)
- [ ] 기대 결과가 구체적이며, 검증 불가능한 모호한 표현을 쓰지 않았는가?
- [ ] 요구사항에 없는 결과를 추측하여 작성하지 않았는가?
- [ ] 시스템 확인 모달의 결과 미정의 케이스는 TC로 작성하고 기대 결과만 공란으로 두었는가? (9.2)
- [ ] 절차가 2~4단계 범위인가? 5단계를 넘는 TC는 분리를 검토했는가? (8절)
- [ ] 기대 결과가 논리적으로 항상 참이 되는 문장(부분 문자열 판정·하한 없는 비교·한 방향만 검증·테스트 데이터 값을 판정 기준에 사용)은 아닌가? (9.3)
- [ ] API 명세가 없는 경우 백엔드 확정형 표현 대신 화면에서 관찰 가능한 반응만 기술했는가? (9.4)

### 데이터
- [ ] 입력값 제한 조건을 반영했는가?
- [ ] 필요한 경계값을 검증했으며, 실제 값으로 기재했는가?
- [ ] 불필요한 데이터 조합을 과도하게 생성하지 않았는가?
- [ ] 실명·실제 연락처 등 운영 데이터가 섞이지 않고 더미 데이터를 사용했는가? (5절 11항)

### 질의사항
- [ ] 요구사항만으로 판단할 수 없는 내용을 억지로 TC로 만들지 않았는가?
- [ ] 불명확한 사항이 질의사항으로 누락되지 않았는가?
- [ ] 테스트 수행에 필요한 준비·지원 요청을 `요청사항` 분류로 질의목록에 등록했는가? (12.5)
- [ ] 질의가 비전공자도 이해할 수 있는 쉬운 말과 존댓말 문의체로 작성되었는가? (12.3)
- [ ] 선택지가 있는 질의를 1안·2안 형태로 제시했는가?

### 엑셀 구조
- [ ] `개요` 시트(표지)가 가장 앞 시트로 존재하며, 담당자·설계 기간 종료일·검증일 등에 임의의 값이 채워지지 않았는가? (14.3)
- [ ] `AI개요` 시트가 두 번째 시트로 존재하며 내용이 실제와 일치하는가? (14.4)

## 17. 핵심 원칙 요약

① 요구사항에 없는 것을 추측하지 않는다. 다만 검증이 필요하다고 판단되는 조건은 TC 후보로 검토하고, 결과를 확정할 수 없으면 질의로 분류한다.
② 하나의 TC는 하나의 주요 검증 목적을 가진다.
③ 테스트 결과가 달라지는 조건은 분리한다.
④ 동일한 검증을 반복하는 TC는 만들지 않는다.
⑤ 경계값·예외·상태·권한 차이를 검토한다.
⑥ 기대 결과는 구체적으로 작성하되, 요구사항에 근거한 결과만 작성한다.
⑦ 사전조건은 4요소(사용자/권한 → 화면 위치 → 데이터 상태 → 선행 작업 상태)를 이 순서로, 번호·라벨 없이 줄바꿈만으로 작성한다.
⑧ 절차가 다루는 범위와 기대 결과의 범위를 일치시킨다.
⑨ 판단할 근거가 없으면 임의로 결정하지 않고 질의사항으로 분류한다. 단, 시스템 확인 모달처럼 상호작용 자체는 실제로 발생하는 경우는 TC를 작성하고 기대 결과만 공란으로 둔다.
⑩ 질의는 비전공자가 이해할 수 있는 쉬운 말과 존댓말 문의체로 작성한다.
⑪ QA가 표준 실행 환경에서 직접 검증하기 어려운 항목(서버 구현, 네이티브 앱 로컬 저장소 등)은 TC로 만들지 않고 질의(요청사항)로 전환한다.
⑫ 향후 자동화 가능성을 고려하되, 자동화하기 쉽다는 이유로 테스트 범위를 축소하지 않는다.
⑬ 엑셀 시트 구성·컬럼 구조는 임의로 변경하지 않는다. ID·분류 등 정형 컬럼은 가운데 정렬, 서술형 컬럼은 왼쪽 정렬, 세로 정렬은 전 셀 가운데로 통일한다.
⑭ 수정 시 원본을 보존하고 복제본을 수정하며, 변경 내역을 기록한다. TC를 폐기할 때도 행을 삭제하지 않고 표시만 남기며, 그 표시는 신규·수정 색상과 달리 폐기 상태가 유지되는 한 버전이 바뀌어도 지우지 않는다.
⑮ 화면이 만들어지면 초안을 실측과 대조하여 정정·삭제한다. 그 과정에서 발견된 결함은 질의목록이 아니라 별도 결함 관리 채널로 넘긴다. 초안 작성 시점에 이미 실제 동작을 알고 있더라도(참고 자료·과거 실행 이력 등) 그 지식을 기대 결과에 끌어와 반영하지 않고, 질의목록에 근거로 남긴다.
⑯ 표현이 구체적이어도 검증 대상이 망가진 상태에서 참이 되는 기대 결과(논리적 공백)를 만들지 않는다.
⑰ 우선순위와 자동화 가능 여부를 TC 작성 시점에 판단하여 전용 컬럼에 기록한다. 보안·데이터손실·업무불가 항목은 빈도와 무관하게 P0으로 고정한다.
⑱ 테스트 데이터에 실제 개인정보·운영 데이터를 사용하지 않는다.
⑲ 신규 TC·질의는 항상 문서 마지막 번호로 추가하고 재정렬하지 않는다. 단, 기존 TC 하나와 강하게 결합된 소수의 변형은 원본 뒤에 하위번호(`-N`)로 추가할 수 있다.
⑳ 신규 TC 파일은 TC ID에 배포(예정)일자를 접두어로 붙이고(`TC-YYMMDD-001`) 파일마다 번호를 리셋한다. 배포일이 밀리면 배포 전까지만 엑셀·코드를 함께 치환하고, 배포 후에는 바꾸지 않는다. 파일명은 `TC_[서비스명]_[기능명]_[배포일자].xlsx` 형식을 따르며, 그 배포일자는 TC ID 접두어와 같은 값을 쓴다.

## 18. 지침 변경 이력

### 18.1 지침 관리 규칙

1. 본 지침을 변경할 때는 **반드시 아래 18.2 표에 이력을 남긴다.** (변경 날짜 / 변경 내용 / 변경 이유 / 변경자)
   - **정렬은 최신순**이다. 새 항목은 표의 **맨 위**에 추가한다.
   - `변경 날짜`는 **그 내용이 지침에 실제로 반영된 날짜**를 기재한다. 작업을 요청받은 날짜나 관련 산출물의 작성일이 아니다.
2. TC를 수정·보완하는 과정에서 얻은 판단 기준이 **다른 주제의 TC를 작성할 때도 동일하게 적용되는 범용적인 내용이라면**, 해당 내용을 본 지침의 알맞은 절에 추가하고 변경 이력에 기록한다.
3. 반대로 **특정 프로젝트·기능에만 해당하는 판단 기준은 본 지침에 넣지 않는다.** 해당 산출물의 AI개요 시트 「작성 기준 및 전제」 항목에 기록한다.
4. (v2.6 변경) 본 지침은 **`.md` 파일이 정본이다.** 평소 수정은 `.md` 파일에만 반영하고, `.html`은 그때마다 동기화하지 않는다. **`.html` 갱신은 손유나가 명시적으로 미러링을 요청했을 때만** 그 시점까지 쌓인 `.md` 변경분을 한꺼번에 반영한다 — 매 수정마다 미러링하면 `.html`을 볼 필요가 없는 작업(TC 초안 작성 등)에서도 토큰을 소모하기 때문이다. 단, 미러링을 요청받으면 그 시점의 `.md`와 완전히 일치하도록 빠짐없이 반영한다.
5. 문서 상단의 문서 버전과 최종 개정일을 함께 갱신한다.
6. **변경자는 다음 기준으로 구분하여 기록한다.** 손유나가 명시적으로 요청·지시한 변경은 `손유나`로 기록한다. 규칙 추가·변경에 따라 AI가 파생적으로 갱신한 항목(16절 체크리스트 항목 추가, 17절 핵심 원칙 요약 확장 등 새 규칙을 반영하기 위한 후속 갱신)은 `AI(Claude)`로 기록한다.
7. (v2.6 변경) **미러링을 요청받아 `.html`을 갱신할 때는** 다음 방법으로 두 파일이 실제로 일치하는지 확인한다. 하나만 확인해도 되는 것이 아니라 셋 다 확인한다.
   - 하위 절(`##`/`###`) 개수가 두 파일에서 동일한가
   - 18.2 변경 이력 표의 행 수가 두 파일에서 동일한가
   - HTML의 여닫는 태그(`div`/`section`/`table`/`tr` 등) 개수가 서로 맞는가
8. **버전 태그(본문의 `vX.X 신설`/`vX.X 변경` 표시, GNB의 `NEW` 배지)는 가장 최근 업데이트(당일 기준) 1회분만 표시한다.** 다음 업데이트가 있으면 이전 표시는 제거하고 새 표시로 교체한다. 과거 이력은 18.2 표에만 남긴다.
9. **변경 이력(18.2)이 길어지면 본문에는 최근 10건만 유지하고, 전체 누적 이력은 별도 파일 `AI_TC_지침_변경이력.md`(+html)로 관리한다.** 새 이력은 그 파일에 먼저 추가한 뒤, 본문의 "최근 10건"도 함께 갱신한다. **버전이 크게 올라가도 오래된 항목이라고 이력을 삭제하지 않는다** — 무엇을 왜 바꿨는지가 사라지면 다음 사람이 그 규칙을 불필요하다고 판단해 되돌릴 수 있다. 삭제 대신 항상 분리·보존한다.
