QA 자동화 · 시작 가이드

QA 자동화 시작하기

Playwright 가 뭔지부터, 첫 테스트 한 줄을 쓰고, 파일을 어떻게 나눌지까지. 답을 옮겨 적는 대신 직접 부딪혀 보는 순서로 정리했습니다.

이 문서를 읽는 법

규칙 목록이 아니라 길 안내입니다. 각 장 끝의 직접 해보기 를 먼저 해보고, 막히면 그 아래 설명을 보세요. 한 번 깨져 본 다음에 읽으면 이해가 훨씬 빠릅니다.

중간중간 함정 표시가 있습니다. 거기 적힌 건 대부분 실제로 겪고 나서 알게 된 것들이라, 미리 읽어도 좋고 밟은 뒤에 읽어도 좋습니다.

01무엇을 자동화하는 건가

도구 이야기 전에, 무엇을 대신하려는 건지부터.

지금 TC 를 손으로 검증할 때 하는 일을 그대로 적어 보면 이렇습니다.

1. 브라우저를 연다
2. 로그인한다
3. 메뉴를 눌러 화면에 들어간다
4. 버튼을 누르거나 값을 입력한다
5. 화면에 나온 결과가 예상결과와 같은지 본다   ← 여기가 검증

1~4번은 조작이고, 5번만 검증입니다. 자동화는 이 다섯 단계를 코드로 옮기는 것이고, 5번을 코드가 판정하게 만드는 게 핵심입니다.

그래서 이런 TC 는 자동화가 안 됩니다

5번에서 사람 눈이 필요한 것 — 증빙 사진이 제대로 찍혔는지, 색상이 어울리는지. 그리고 화면에 판별 근거가 없는 것 — 비교할 값이 화면에 안 나오면 코드도 볼 수 없습니다.

TC 를 쓸 때 "이건 코드가 판정할 수 있나" 를 함께 생각해 두면 나중에 자동화할 때 다시 판단하지 않아도 됩니다.

02Playwright 가 하는 일

한 줄로 — 브라우저를 코드로 조작하는 도구입니다.

사람이 하는 조작마다 대응하는 명령이 있습니다.

사람이코드로
주소창에 URL 입력page.goto("https://...")
입력칸에 타이핑page.get_by_placeholder("아이디").fill("...")
버튼 클릭page.get_by_role("button", name="로그인").click()
화면에 뭐가 보이는지 확인expect(요소).to_be_visible()

비슷한 도구들 중에 왜 Playwright 인가

Selenium 이 오래 쓰였고 Cypress 도 많이 씁니다. Playwright 를 고른 이유는 하나가 큽니다 — 기다리는 걸 알아서 해줍니다.

# Selenium 식 — 요소가 나타날 때까지 직접 기다려야 한다
wait.until(EC.element_to_be_clickable((By.ID, "save")))
driver.find_element(By.ID, "save").click()

# Playwright — click() 이 알아서 기다린다
page.get_by_test_id("save").click()

이 차이가 왜 중요한지는 04장(함정: 대기) 에서 다시 나옵니다. 자동화가 깨지는 원인의 절반쯤이 여기 있습니다.

pytest 와 같이 쓰는 이유

Playwright 는 브라우저를 조작할 뿐입니다. 그걸 테스트로 만들어 주는 건 pytest 입니다.

Playwrightpytest

요소 찾기통과·실패 판정과 집계
—준비 작업 공유 (fixture)
—리포트 생성
직접 해보기

  • --headed 옵션을 붙여 브라우저가 실제로 뜨는 걸 눈으로 보세요

03테스트 하나의 뼈대 — GIVEN / WHEN / THEN

TC 문서의 사전조건·절차·예상결과와 정확히 같은 구조입니다.

TC 문서테스트 코드담는 것
사전 조건GIVEN이 검증을 하기 전에 갖춰져 있어야 할 상태
테스트 절차WHEN실제로 하는 조작
예상 결과THEN코드가 판정하는 것
 
def test_search_by_plate(page):
    """
    GIVEN  로그인한 뒤 목록 화면에 있고, 건이 여러 개 있을 때
    WHEN   차량번호로 검색하면
    THEN   결과 행의 차량번호가 전부 검색어를 포함한다
    """
    # WHEN
    page.get_by_test_id("search-input").fill("77")
    page.get_by_test_id("search-button").click()

    # THEN — 여기가 유일한 판정
    rows = page.locator('[data-testid^="row--"]')
    for i in range(rows.count()):
        plate = rows.nth(i).locator("td").nth(2).inner_text()
        assert "77" in plate, f"[FAIL] 검색어와 무관한 행: {plate}"
왜 굳이 셋으로 나누나

깨졌을 때 어디가 문제인지 바로 알기 위해서입니다. GIVEN 에서 실패하면 준비가 안 된 것(데이터·로그인)이고, THEN 에서 실패해야 진짜 기능 결함입니다. 섞여 있으면 매번 코드를 읽어야 합니다.

함정 — 실패 메시지에 값이 없으면 리포트를 봐도 모른다 
assert len(rows) > 0
   → 리포트: "assert 0 > 0"  ... 그래서 뭐가 문제였지?

assert len(rows) > 0, f"[FAIL] 검색 결과 0건 — 검색어: {keyword!r}"
   → 리포트: "[FAIL] 검색 결과 0건 — 검색어: '77테'"
직접 해보기
  • 손으로 검증하던 TC 하나를 골라 GIVEN/WHEN/THEN 으로 먼저 글로 써 보세요
  • 그 다음에 코드로 옮기세요. 글이 안 써지면 코드도 안 써집니다
  • 일부러 assert 를 틀리게 만들어 실패 메시지가 읽히는지 확인하세요

04반드시 밟는 함정 네 개

순서대로 겪게 됩니다. 미리 알아도 한 번은 밟습니다.

함정 1 — 시간을 기다리면 느리면서 동시에 불안정해진다

화면이 아직 안 그려져서 실패하면, 처음엔 이렇게 고치고 싶어집니다.

page.click("저장")
page.wait_for_timeout(2000)   # 2초 기다리면 되겠지
assert ...
왜 나쁜가

이건 "2초 안에 될 것"이라는 도박입니다. 빠른 날엔 1.9초를 낭비하고, 느린 날엔 그대로 깨집니다. TC 가 100개면 낭비도 100배입니다.

시간이 아니라 상태를 기다려야 합니다.

page.click("저장")
expect(page.get_by_test_id("toast")).to_be_visible()   # 뜨면 즉시 통과

expect() 는 조건이 될 때까지 계속 다시 확인합니다. 되면 즉시 넘어가고, 안 되면 정해진 시간 뒤 실패합니다. 빠르면서 안정적입니다.

함정 2 — 통과하는데 아무것도 검증하지 않는 테스트

이게 가장 위험합니다. 실패하는 테스트는 고치면 되지만, 검증 안 하면서 통과하는 테스트는 "여긴 확인됐다"는 잘못된 안심을 줍니다.

이렇게 쓰면왜 항상 통과하나
assert "완료" in status"배정완료"·"운영완료" 도 참
assert after < before필터가 깨져 0건이 나와도 참
assert name in titlename 이 빈 문자열이면 항상 참
if not value: continue값이 비었다는 게 버그의 증거인데 그걸 버림
수집만 하고 printassert 가 아예 없음
판별하는 자문 한 줄

"이 검증 대상이 망가졌다고 가정하면, 이 테스트가 빨간불이 되나?"

답이 "아니오"면 그 테스트는 없는 것만 못합니다. 말로 자문하지 말고 실제로 망가뜨려 보세요 — 값을 일부러 틀리게 넣고 빨간불이 뜨는지.

함정 3 — 화면 글자로 요소를 찾으면 곧 깨진다

page.click("text=저장")        # 버튼 이름이 '저장하기' 로 바뀌면 깨진다
page.get_by_test_id("save-btn").click()   # 이름이 바뀌어도 안 깨진다

data-testid 는 테스트를 위해 붙이는 표식입니다. 화면에는 안 보이고, 디자인이 바뀌어도 그대로입니다. 없으면 프론트에 요청해서 붙이는 게 맞습니다 — 그게 장기적으로 훨씬 쌉니다.

글자로 찾을 때의 또 다른 함정

"완료" 로 찾으면 "배정완료" 도 같이 잡힙니다. 글자로 찾아야만 할 때는 시작 지점을 고정하세요 — 정규식 ^완료 처럼.

함정 4 — skip 은 초록불이 아니다

데이터가 없어서 검증을 못 할 때 pytest.skip() 을 씁니다. 문제는 skip 이 통과처럼 보인다는 것입니다.

노란불 뒤에 버그가 숨는다

매번 skip 되는 테스트는 검증이 한 번도 안 돌았다는 뜻입니다. "데이터가 없다"고 단정하기 전에 볼 수 있는 만큼 봤는지 확인하세요 — 1페이지 10행만 보고 없다고 한 건 아닌지.

skip 은 "데이터가 없다" 일 때만. "구조가 깨졌다"는 실패여야 합니다.

05파일을 어떻게 나눌까

처음부터 완벽한 구조를 만들려 하지 마세요. 아파야 나눌 자리가 보입니다.

먼저 겪게 되는 것 — 로그인이 계속 반복된다

테스트를 5개쯤 쓰면 이렇게 됩니다.

def test_1(page):
    page.goto(URL); page.fill("아이디",...); page.click("로그인")   # 반복
    ...
def test_2(page):
    page.goto(URL); page.fill("아이디",...); page.click("로그인")   # 반복
    ...

pytest 는 이걸 위해 fixture 라는 걸 줍니다. conftest.py 파일에 준비 작업을 적어 두면, 테스트는 인자 이름으로 요청만 하면 됩니다.

# conftest.py — 준비 작업이 사는 곳
@pytest.fixture
def logged_in_page(page):
    page.goto(URL)
    page.get_by_placeholder("아이디").fill(ID)
    page.get_by_placeholder("비밀번호").fill(PW)
    page.get_by_role("button", name="로그인").click()
    yield page          # 여기서 테스트 본문이 실행된다

# 테스트 — 인자에 이름만 적으면 pytest 가 넣어준다
def test_1(logged_in_page):
    ...   # 이미 로그인된 상태로 시작
한 걸음 더 — 로그인을 한 번만 하기

위 방식은 테스트마다 로그인합니다. 100개면 100번이고, 로그인이 5초면 8분입니다.

로그인은 실행당 한 번만 하고, 그 결과(쿠키)를 저장해서 각 테스트가 이미 로그인된 상태로 시작하게 만들 수 있습니다. Playwright 의 storage_state 와 pytest 의 scope="session" 을 찾아보세요.

폴더는 "나중에 갈릴 축"을 따라 나눈다

지금 화면이 하나여도, 앞으로 무엇이 늘어날지를 생각해 두면 나중에 안 뒤집습니다.

프로젝트/
├── conftest.py              # 모든 테스트가 공유하는 설정
├── pytest.ini               # 실행 옵션
├── .env.example             # 환경변수 템플릿 (실제 .env 는 커밋 금지)
│
├── {서비스}/                 # ← 서비스가 늘면 여기서 갈린다
│   └── {권한·앱}/            # ← 어드민/앱처럼 사용자가 다르면 여기서
│       ├── conftest.py      # 이 범위에서만 쓰는 fixture (로그인 등)
│       └── {화면}/           # ← 화면별
│           └── test_*.py
└── tools/                   # 리포트·검사 스크립트
conftest.py 는 여러 개 둘 수 있습니다

pytest 는 가까운 conftest 부터 위로 찾아 올라갑니다. 전체 공통은 루트에, 그 폴더에서만 쓰는 건 그 폴더에 두면 됩니다. 로그인 fixture 는 권한 단위로 두는 게 자연스럽습니다.

함정 — 파일을 너무 일찍 쪼개지 마세요

TC 가 10개일 때 기능별로 파일을 나누면, 어떤 단위로 나눠야 할지 모르는 상태에서 나누게 됩니다. 잘못 나눈 걸 되돌리는 건 합치는 것보다 어렵습니다.

한 파일에 쓰다가 섹션 주석으로 구분해 두고, 전체가 보인 뒤에 그 경계로 나누는 편이 안전합니다.

계정 정보는 코드에 넣지 않는다

LOGIN_PW = "mypassword123"      # 커밋되면 그대로 노출된다

LOGIN_PW = os.getenv("LOGIN_PW")  # .env 에서 읽는다 (.gitignore 에 추가)

.env.example 에 키 이름만 넣어 커밋하고, 값이 든 .env 는 커밋하지 않습니다.

06순서대로 해볼 것

한 번에 다 하려 하지 말고, 하나씩 돌아가는 걸 확인하면서 늘려가세요.

1

브라우저를 띄우고 닫기

아무 사이트나 열고 제목을 확인하는 테스트 하나. --headed 로 눈으로 보세요.

확인 — 테스트가 실패하는 것도 봤나요? 제목을 일부러 틀리게 해보세요.
2

로그인하기

계정 정보는 .env 에서 읽습니다. 로그인 후 메뉴가 보이는 것까지 확인하세요.

확인 — 비밀번호를 틀리게 넣으면 테스트가 실패하나요? 통과한다면 검증이 잘못된 겁니다.
3

화면에 들어가서 값 하나 읽기

메뉴를 눌러 목록 화면까지 가고, 표의 첫 행에서 값 하나를 읽어 출력해 보세요.

막히는 지점 — 요소를 못 찾는다면 화면이 아직 안 그려진 것일 수 있습니다. expect().to_be_visible() 로 기다려 보세요.
4

TC 하나를 온전히 옮기기

손으로 검증하던 TC 를 골라 GIVEN/WHEN/THEN 으로 쓰고 코드로 옮깁니다. 결과 행의 값까지 전수 검사하세요 — 행 수만 세면 부족합니다.

자문 — 이 기능이 망가지면 빨간불이 되나요? 실제로 망가뜨려 확인하세요.
5

로그인을 fixture 로 빼기

TC 가 3~4개 되면 반복이 눈에 보입니다. 그때 conftest.py 로 옮기세요.

순서 — 아프고 나서 빼는 게 맞습니다. 미리 빼면 잘못된 단위로 묶입니다.
6

리포트 보기

pytest --html=report.html 이나 allure 로 결과를 문서로 뽑아 보세요. TC ID 와 한글 제목이 리포트에 나오게 하면 팀에 공유할 수 있습니다.

여기까지 오면 — TC 문서의 ID 와 코드가 어떻게 이어질지 고민이 시작됩니다. 그게 다음 단계입니다.
