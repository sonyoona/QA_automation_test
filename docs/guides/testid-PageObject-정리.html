1testid란 무엇인가

프론트엔드가 HTML에 붙여두는 "자동화 전용 이름표"다. 화면에는 보이지 않고, 스타일이나 동작에도 영향을 주지 않는다. 오직 테스트가 요소를 찾기 위해서만 존재한다.

<button data-testid="fs-filter__search-btn">조회</button>
# Playwright 는 이 속성을 전용 함수로 찾는다
page.get_by_test_id("fs-filter__search-btn").click()

QA가 혼자 도입할 수 없다. data-testid는 제품 코드(HTML)에 있어야 하므로, 프론트엔드 개발팀이 붙여야 한다. 없는 화면이라면 요청하는 것부터가 첫 단계다.

지금 화면에 있는지 확인하는 법

브라우저 개발자도구 → Console 에서:

document.querySelectorAll('[data-testid], [data-qa], [data-test]').length

0이 아니면 이미 붙어 있다. 목록까지 보려면:

console.table([...document.querySelectorAll('[data-testid]')]
  .map(e => ({tag: e.tagName, testid: e.getAttribute('data-testid')})))

콘솔에 붙여넣기가 막혀 있으면 allow pasting 이라고 직접 타이핑하고 Enter를 치면 그 뒤로 풀린다.

2testid의 장점 — 우리 코드에서 실제로 아픈 곳

① 같은 이름 버튼이 여러 개인 문제가 사라진다

test_vehicle_company_transfer.py의 세 곳이 전부 같은 코드다.

나쁨 — 확인 / 완료 / 실패 알럿의 OK 를 코드가 구분하지 못한다
ok_button = page.get_by_role("button", name="OK", exact=True)

좋음 — 무엇의 OK 인지가 이름에 있다
page.get_by_test_id("transfer-confirm__ok").click()
page.get_by_test_id("transfer-complete__ok").click()

다이얼로그가 겹쳐 뜨는 순간 엉뚱한 걸 누르거나 strict mode violation 에러가 난다. "가끔 깨지는 테스트"의 전형적인 원인이다.

② 구조·클래스 의존이 없어진다

지금 쓰는 셀렉터깨지는 조건
page.locator("div.column", has_text="리셀러")레이아웃 클래스명을 바꾸면
page.locator(".spinner")로딩 컴포넌트 교체
pagination.locator('a[type="pageItem"].active')페이지네이션 라이브러리 교체
page.locator('button[id="2"]')이미 위험 — id="2"는 의미 없는 값이라 순서만 바뀌어도 다른 버튼

③ 텍스트 변경에 안 흔들린다

"조회"가 "검색"으로 바뀌거나, 다국어가 붙거나, "완료 217"처럼 건수가 붙으면 텍스트 기반 셀렉터는 전부 깨진다. testid는 그대로다.

④ 실패 메시지가 읽힌다

Timeout … locator("div.column").locator("input, [role=combobox]").first
Timeout … locator("[data-testid=fs-filter__reseller-select]")

3testid의 단점 — 정답이 아닌 이유

단점내용
접근성을 검증하지 않는다get_by_role("button", name="로그인")은 "스크린리더가 이걸 버튼으로 인식하는가"까지 검증한다. testid는 <div>에 붙여도 통과 — 접근성이 깨져도 초록불
사용자가 보는 것과 다르다사용자는 testid를 볼 수 없다. "화면에 '저장' 버튼이 있다"가 TC 의도인데 testid로 잡으면 버튼 글자가 undefined여도 통과
제품 코드가 지저분해진다개발팀 저항 포인트 — "테스트용 속성을 프로덕션 번들에 넣어야 하냐"
관리 부담이 FE로 넘어간다컴포넌트 리팩터링하며 testid를 지우면 조용히 깨진다

그래서 이렇게 나눈다

사용자가 읽는 것 (버튼 글자, 라벨, 에러 메시지)  →  get_by_role / get_by_text
사용자가 못 보는 구조 (다이얼로그, 행, 스피너)   →  get_by_test_id
그것도 안 되면                                  →  CSS / XPath (최후 수단)

Playwright 공식 권장 순서도 role/label이 먼저, testid는 그게 안 될 때다.

4testid 말고 다른 방법들

① 회사가 다른 속성명을 쓰면 Playwright 쪽을 맞춘다

get_by_test_id()는 data-testid라는 이름만 찾도록 기본 설정돼 있다. 회사가 data-qa·data-cy를 쓴다면, 제품 코드를 바꾸라고 요구할 게 아니라 Playwright에 알려주면 된다.

# conftest.py — 이 한 줄이면 회사 속성명을 그대로 쓴다
playwright.selectors.set_test_id_attribute("data-qa")

# 이제 이게 [data-qa="save-button"] 을 찾는다
page.get_by_test_id("save-button")

② testid 대신 aria-label 추가를 요청한다

접근성이 개선되는 지점 — 스크린리더는 HTML을 읽어서 음성으로 말해준다. 아이콘만 있는 버튼은 읽을 텍스트가 없어서 "버튼" 이라고만 말한다.

<button class="btn-icon"><svg>...</svg></button>            → "버튼"
<button class="btn-icon" aria-label="차량 삭제"><svg>...</svg></button>  → "차량 삭제, 버튼"

data-testid는 스크린리더가 아예 무시하는 속성이라, 아무리 붙여도 시각장애인에게는 여전히 "버튼"이다.

자동화 쪽 이득 — 코드 모양은 그대로 get_by_role인데, 이름이 달라져서 구분이 된다.

요청이 통하는 난이도가 다르다는 게 실무적 이유다.

요청개발자 반응
"테스트용 data-testid 붙여주세요""그거 프로덕션 코드에 왜 넣어요?" → 설득 필요
"아이콘 버튼에 aria-label이 없어 접근성 검사에 걸립니다"원래 지켜야 할 것 → 반박 여지 없음

③ 행 식별에는 PK가 담긴 속성을 요청한다

텍스트로 행을 찾으면 세 가지가 깨진다.

  • 부분 일치 — "12가3456"으로 찾는데 "112가34567" 행도 걸린다
  • 다른 컬럼에 같은 문자열 — 비고란에 그 번호가 적혀 있어도 걸린다
  • 텍스트가 완전히 같은 행 — 같은 날 같은 업체 건이면 글자까지 같을 수 있다
요청 결과
<tr data-testid="fs-table__row--10679">  ← DB 의 PK 가 들어간다
# 표시되는 글자가 아니라 데이터의 신원으로 행을 잡는다
row = page.get_by_test_id(f"fs-table__row--{vehicle_id}")

④ 네트워크 / API 레벨 검증을 곁들인다

브라우저가 화면을 그리는 순서는 이렇다.

[조회] 클릭
   ↓
브라우저 → 서버 요청        GET /api/monitor?reseller=커넥트
   ↓
서버 → JSON 응답            { "total": 217, "items": [ … ] }
   ↓
브라우저가 그 JSON 으로 표를 그림   ← 지금은 여기만 본다

Playwright는 중간의 JSON을 가로채서 볼 수 있다.

with page.expect_response(lambda r: "/api/monitor" in r.url) as res_info:
    page.get_by_role("button", name="조회").click()

data = res_info.value.json()

# ① 서버가 말하는 총 건수와 대조
assert data["total"] == expected_total

# ② 서버 응답 자체가 조건에 맞는지 (화면 그리기 전 단계)
wrong = [x for x in data["items"] if x["reseller"] != "커넥트"]
assert not wrong, f"[FAIL] 서버 응답에 다른 리셀러가 섞임: {wrong}"

왜 필요한가 — 지금 TC-086이 반쪽이다

방향지금안 보면 생기는 일
결과 ⊆ 조건 (오검출)✅ 보고 있음—
조건 ⊆ 결과 (누락)❌ 못 봄커넥트 차량이 500대인데 필터가 3대만 보여줘도 통과

뒷방향을 보려면 "원래 몇 대인지"라는 정답이 필요한데, 화면만 봐서는 알 수 없다. API가 그 정답을 준다.

추가로 얻는 것 — 버그의 소재가 갈린다

API 응답화면진단
커넥트만 217건커넥트만 217건정상
커넥트만 217건다른 리셀러 섞임프론트 버그 — 서버는 잘 줬는데 잘못 그림
다른 리셀러 섞임다른 리셀러 섞임백엔드 버그 — 필터 쿼리가 잘못됨

API 검증은 화면 검증을 대체하는 게 아니라 보완한다. API만 보면 "서버는 잘 줬는데 화면이 안 그려짐"을 놓친다.

팝업은 열어야 측정된다

6Page Object — 처음부터 풀어서

testid를 찾았다면 다음 질문은 "그 문자열을 어디에 적을 것인가"다.

0단계 — 아무것도 안 나눈 상태

def test_a(page):
    page.get_by_test_id("fs-filter__plate-input").fill("12가3456")
    page.get_by_test_id("fs-filter__search-btn").click()

def test_b(page):
    page.get_by_test_id("fs-filter__plate-input").fill("99너9999")
    page.get_by_test_id("fs-filter__search-btn").click()

# … 이하 28개 더, 전부 같은 두 줄로 시작

흔히 "이름 바뀌면 30곳 고쳐야 하잖아"라고 하는데, 그건 사실 약한 이유다 — 찾아 바꾸기 한 번이면 된다. 진짜 문제는 아래 7장에 있다.

1단계 — 함수로 빼기 (이미 하고 있는 것)

test_monitor_reseller_filter.py의 _goto_monitor·_open_reseller_dropdown· _get_real_row_count가 바로 이 단계다. Page Object의 8할은 이미 하고 있다.

def _search_by_plate(page, plate):
    page.get_by_test_id("fs-filter__plate-input").fill(plate)
    page.get_by_test_id("fs-filter__search-btn").click()

나중에 스피너 대기를 추가해야 하면 함수 안에 한 줄만 넣으면 30개 TC에 전부 적용된다.

2단계 — Page Object

함수가 늘어나면 한 파일 안에 "화면 조작법"과 "무엇을 검증하는가"가 섞인다. Page Object는 그 함수들을 화면별로 다른 파일에 모아두는 것이다. 그게 전부다.

pages/
  field_service_page.py       현장서비스 화면 조작법만
test_field_service.py         검증만

왜 class를 쓰나 — page를 매번 넘기기 귀찮아서다

# 함수 방식 — page 를 계속 들고 다녀야 함
_search_by_plate(page, "12가3456")
_get_row_count(page)

# 클래스 방식 — 한 번만 넘기면 나머지가 기억함
fs = FieldServicePage(page)
fs.search_by_plate("12가3456")
fs.row_ids()

class는 "관련된 함수들 + 공통으로 쓰는 값(page)을 한 묶음으로 담은 상자" 정도로 보면 된다.

언제 만들지 않는가

상황판단
TC 한두 개짜리 화면안 만듦. 테스트 안에 그냥 씀
같은 조작이 3번 넘게 반복함수로 뺌 (1단계)
헬퍼가 5개 넘고 다른 파일도 그 화면을 씀Page Object로 옮김 (2단계)

미리 만들지 않는다. 어떻게 쓰일지 모르는 상태에서 묶으면 잘못된 단위로 묶이고, 나중에 푸는 게 더 어렵다. 기존 test_monitor_reseller_filter.py· test_vehicle_company_transfer.py는 잘 돌아가고 있으므로 굳이 뜯어고치지 않는다.

7테스트에 testid가 안 보이는 게 왜 좋은가

"testid가 안 보이는 것" 자체는 목적이 아니라 결과다. 진짜 이유는 셋이고, 세기가 다르다.

① 제일 센 이유 — 조작 방법이 TC마다 갈리는 걸 막는다

검색 버튼을 눌러도 결과 테이블은 즉시 갱신되지 않는다. 서버 응답을 기다려야 한다. 그런데 testid를 테스트마다 직접 쓰면 이렇게 갈린다.

TC-A — 검색하고 바로 읽음
    page.get_by_test_id("fs-filter__search-btn").click()
    rows = page.locator('[data-testid^="fs-table__row--"]')
    assert rows.count() > 0        # ← 아직 이전 검색 결과가 남아 있는 상태를 읽음

TC-B — 다른 날 다른 사람이 씀. 대기를 넣었다
    page.get_by_test_id("fs-filter__search-btn").click()
    expect(page.get_by_test_id("fs-table__root")).to_be_visible()
    rows = page.locator('[data-testid^="fs-table__row--"]')
    assert rows.count() > 0

TC-A가 위험하다. 검색이 아예 동작하지 않아 이전 결과가 남아 있어도 rows.count() > 0이라 통과한다. 검증을 안 하면서 초록불인 상태 — 위양성이다. 그런데 코드만 봐서는 안 보인다. TC-A도 TC-B도 각각은 멀쩡해 보인다.

그냥 하면 되는 조작과 알고 해야 되는 조작의 차이. 요령은 화면을 직접 겪어봐야 알 수 있는, 코드만 봐서는 안 보이는 처리다.

11위양성 — 통과하는데 검증 안 하는 테스트

앞의 10개 장은 "요소를 어떻게 잡을 것인가"였다. 이 장은 층이 다르다 — testid로 잡든 Page Object로 묶든, 검증 자체가 헛돌면 아무 소용이 없다. 셀렉터 전략은 이 문제를 하나도 막아주지 않는다.

11-1실패보다 나쁜 이유

실패하는 테스트는 고치면 된다. 검증 안 하면서 통과하는 테스트는 "여긴 확인됐다"는 잘못된 안심을 준다.

더 나쁜 건 통과율로는 영원히 안 보인다는 점이다. 리포트가 초록불이니 아무도 열어보지 않는다. 원인은 거의 항상 하나다 — 검증이 까다로울 때 조건을 느슨하게 만들어 초록불을 만든 것. 통과율이 목표가 되면 반드시 이렇게 된다.

TC를 쓴 뒤 반드시 자문한다
"이 검증 대상이 망가졌다고 가정하면, 이 테스트가 빨간불이 되나?"

답이 "아니오"면 그 TC는 없는 것만 못하다.

11-2실제로 걸리는 9가지 형태

#형태나쁜 코드왜 통과하나
①부분 문자열assert "완료" in status"배정완료"·"운영완료"도 참
②하한 없음assert after < beforeafter == 0이어도 참 — 필터가 죽어도 통과
③빈 값 건너뛰기if not v: continue값이 비었다는 게 버그의 증거인데 그걸 버림
④항진명제assert x == sorted(x)원소가 전부 같으면 오름·내림 둘 다 참
⑤자기충족find(조건="A") 후 assert "A" in txt있는 것만 골라와서 있는지 확인
⑥빈 문자열assert name in titlename == ""이면 항상 참
⑦라벨만 확인to_contain_text("현재 로그인 계정")화면에 항상 박힌 안내 문구라 값이 비어도 참
⑧수집만 하고 안 봄found = ... 후 print(len(found))assert가 아예 없다
⑨0회 루프for r in rows: assert ...행이 0개면 검증이 통째로 사라짐

고치는 법 — before / after

# ① 부분 문자열
- assert "완료" in status
+ assert status == "완료", f"[FAIL] '완료' 아닌 상태가 섞임: {status!r}"

# ② 하한 없음 — 필터가 죽어 0건이 나와도 "잘 좁혀졌다"며 통과
- assert after < before
+ assert 0 < after < before, f"[FAIL] 결과 이상: {before}건 -> {after}건 (0건이면 회귀 의심)"

# ③ 빈 값 건너뛰기 — 그 빈 값이 곧 '필터 미적용'의 증거다
- if not completed:
-     continue
+ if not completed:
+     blanks.append(i); continue
+ assert not blanks, f"[FAIL] 완료일 빈 행 {blanks} - 필터 미반영 의심"

# ④ 항진명제 — 값이 전부 같으면 어떤 정렬이든 참
+ if len(set(before)) < 2:
+     pytest.skip(f"값이 모두 동일({before[:1]}) - 순서 검증 불가")
  assert before == sorted(before, reverse=True)

# ⑨ 0회 루프
  rows = ...
+ assert rows, "[FAIL] 검사할 행이 0건 - 검증이 수행되지 않았다"
  for r in rows: ...

11-3★ 부정 검증은 방향이 반대다 — 제일 위험하다

"없어야 한다"를 확인할 때는, 덜 읽을수록 통과한다.

# 긍정 검증 — 덜 읽으면 실패한다. 금방 드러남
assert "커넥트" in options

# 부정 검증 — 덜 읽으면 통과한다. 영원히 안 드러남
assert "LG U+" not in options       # options 가 [] 여도 통과

목록이 채워지기 전에 읽으면 기능이 완전히 망가져도 초록불이다. 긍정 검증이면 덜 읽었을 때 실패해서 금방 드러나는데, 부정 검증은 그 반대라 회귀가 나도 통과율에 아무 흔적이 남지 않는다.

규칙 — 목록으로 "없어야 한다"를 볼 때는 둘을 같이 건다
① 목록이 안정된 뒤 읽는다  ·  ② 목록이 비면 실패로 본다.
②가 없으면 하한이 사라져 위 ②번(하한 없음)과 같은 구멍이 된다.

opts = _settled_options(page, timeout_ms=8000)
assert opts, "[FAIL] 옵션을 읽지 못했다 - 제외 여부를 판정할 수 없다"
assert not [p for p in active if any(p in o for o in opts)]

11-4구조적 원칙 4개

① assert를 쓰기 전에 "정답을 어디서 가져올지"부터 정한다

정답 출처가 없으면 쓸 수 있는 검증은 assert x(비어 있지 않다) 정도뿐이고, 그건 거의 항상 통과한다.

나쁨 — 정답이 없으니 '비어 있지 않다' 밖에 못 쓴다
assert filled and filled != "업체를 선택하세요"

좋음 — 표에서 정답을 읽어두고 일치를 본다
plate, owner = _row_pair(page, "차량번호", "업체명")
...
assert filled == owner, f"[FAIL] 차량 {plate!r} 소속은 {owner!r} 인데 {filled!r} 로 채워짐"

정답 출처는 대개 화면 안에 있다 — 표 컬럼 짝, 다른 탭의 같은 데이터, 목록 요약 vs 상세. 그것도 없으면 API 응답이다.

② 필터·검색은 양방향을 본다

방향무엇을 막나안 걸면
결과 ⊆ 조건오검출 — 조건에 안 맞는 게 섞임필터가 전부 반환해도 통과
조건 ⊆ 결과누락 — 맞는데 빠짐필터가 아무것도 안 넣어도 통과

확인할 수 없는 방향은 못 했다고 docstring에 적는다. 안 적으면 다음 사람이 "이미 다 봤네" 하고 넘어간다.

③ 검증 대상을 탐색 조건에 넣지 않는다

나쁨 — '검증 결과가 있는 건'만 골라와서 '있는가'를 확인 = 실패 불가능
dlg, txt = _find(..., require_substring="검증 결과")
assert "검증 결과" in txt

좋음 — 탐색은 전제(상태·유형)까지만, 검증은 본문 assert 로
dlg, txt = _find(page, "인스톨러 앱 (APP)", svc_type="설치")
assert "검증 결과" in txt, f"[FAIL] ... 팝업 앞부분: {txt[:300]!r}"

탐색 조건에 넣으면 회귀가 났을 때 "못 찾음 → skip"으로 노란불에 묻힌다.

④ skip은 초록불이 아니다

  • skip은 "데이터가 없다"일 때만. "구조가 깨졌다"는 fail이어야 한다
  • 필터 결과가 0건인 것은 skip 대상이 아니다 — assert filtered > 0으로 실패시킨다
  • "없다"고 단정하기 전에 볼 수 있는 만큼 본다 — 1페이지 10행만 보고 포기하지 않는다
  • 환경 장애가 skip으로 위장한다 — 세션이 끊겨도 "데이터 없음"처럼 보인다

🟡 test_TC085 — 한 방향만 봤다 (원칙 ②)

"기대 항목이 다 있나"(조건 ⊆ 결과)만 확인하고 있었다. 드롭다운에 제거되어야 할 옛 파트너가 남아 있어도 통과한다.

# 방향 ①  조건 ⊆ 결과 — 기대 항목이 빠지지 않았는가 (원래 있던 것)
for option in RESELLER_OPTIONS:
    expect(reseller_dropdown.get_by_role("option", name=option, exact=True)).to_be_visible()

+ # 방향 ②  결과 ⊆ 조건 — 기대 목록에 없는 항목이 섞이지 않았는가
+ actual_options = [t.strip() for t in reseller_dropdown.get_by_role("option").all_inner_texts()]
+ assert actual_options, "[FAIL] 리셀러 옵션을 하나도 읽지 못했습니다 - 목록이 비면 '섞인 게 없다'고 판정할 수 없습니다"
+
+ unexpected = [o for o in actual_options if o not in RESELLER_OPTIONS]
+ assert not unexpected, f"[FAIL] 기대 목록에 없는 리셀러가 노출됩니다: {unexpected} / 전체: {actual_options}"

여기서 순서가 중요하다. 방향 ②는 all_inner_texts() — 재시도가 없는 즉시 읽기라, 그것만 있으면 11-3의 함정에 그대로 빠진다. 방향 ①의 expect() 루프가 목록이 다 그려진 것을 보장하는 대기 역할을 겸하고, assert actual_options가 하한을 건다.

🟡 같은 것을 읽는 방법이 두 가지였다

_get_real_row_count()가 "조회 결과가 없습니다" 안내 행(colspan)을 걸러주는데, _assert_all_rows_have_reseller는 rows.count()로 직접 세고 있었다. 셀렉터 이름은 멀쩡했다 — 깨진 건 "이 표의 행을 어떻게 세야 하는가"라는 지식이 한 곳에 없었다는 점이다. 위 수정으로 함께 정리됐다.

6장에서 Page Object의 이유로 "이름 바뀌면 한 곳만 고친다"를 들었는데, 진짜 이유는 이쪽이다 — 읽는 방법이 한 곳에 없으면 TC마다 다른 방법을 골라 쓰게 되고, 그중 하나가 위양성이 되어도 이름은 멀쩡해서 아무도 눈치채지 못한다.

✅ 잘 되어 있던 곳 — 참고용

test_TC087은 부정 검증인데 안전하다.

header_texts = page.locator("table").first.locator("thead th").all_inner_texts()

assert "리셀러" in header_texts, ...      # ← 이 긍정 assert 가 하한 역할을 한다
assert "파트너" not in header_texts, ...  # ← 헤더를 못 읽으면 위에서 이미 실패

부정 검증 앞에 긍정 검증을 두는 것 — 이게 하한을 거는 가장 간단한 방법이다. test_TC084도 같은 구조(리셀러 보임 확인 → 파트너 안 보임 확인)라 안전하다.

11-6체크리스트 — TC 쓴 뒤 8가지

  1. 망가졌다고 가정하면 빨간불이 되나?
  2. in / <을 썼다면 — 하한이 있나? (0 < after < before)
  3. 루프를 돌린다면 — 0회 돌 수 있나?
  4. 부정 검증("없다")이라면 — 안정된 뒤 읽고, 비면 실패로 보나?
  5. 정답 출처가 있나, 아니면 "비어 있지 않다"만 확인하고 있나?
  6. 필터·검색이라면 — 양방향을 다 봤나?
  7. 검증할 것을 탐색 조건에 넣지 않았나?
  8. skip이 "검증 불가"인가, "결과 0건"을 감추고 있나?

11-7자가 점검은 뚫린다

이 체크리스트를 쓴 사람이 스스로 하면 못 잡는다. 자기가 그렇게 쓴 이유를 알고 있으니 다시 봐도 같은 결론이 나온다.

  • 코드를 안 쓴 사람에게 리뷰를 부탁하거나
  • 서브에이전트에게 "이 파일에서 통과하는데 검증 안 하는 곳을 찾아라"라고 시키거나
  • 최소한 하루 지나서 다시 본다

매번 skip되는 TC를 찾는 검사를 도구로 두는 것도 방법이다 — 매번 skip된다는 건 그 검증이 한 번도 안 돌았다는 뜻이고, 그 뒤에 진짜 버그가 숨는다.

12넷을 어떻게 조합할 것인가

4장에서 testid · aria-label · PK 속성 · API를 하나씩 봤고, 6장에서 Page Object를 봤다. 그럼 실제로는 뭘 골라야 하나? 이 장은 그 질문에 답한다 — 이상적인 답과 실무의 답이 다르고, 그 차이에 이유가 있다.

12-1먼저 — 넷은 서로 대체재가 아니다

"testid를 쓸까 Page Object를 쓸까"는 질문 자체가 성립하지 않는다. 층이 다르기 때문이다.

기법무엇을 푸는가사는 곳
aria-label요소에 의미 있는 이름을 준다화면 (HTML)
data-testid요소에 안 바뀌는 이름표를 준다화면 (HTML)
PK 속성어느 데이터인지 구분한다화면 (HTML)
Page Object그 이름들을 어디에 적을지 정한다우리 코드

앞의 셋은 "무엇으로 잡는가", Page Object는 "어디에 적는가"다. 그래서 Page Object는 나머지 셋 중 무엇을 쓰든 항상 같이 쓴다. 고르는 게 아니라 겹쳐 쌓는 것이다.

12-2이상적인 조합

  1. 사람이 보는 이름으로 잡을 수 있으면 그것부터 — get_by_role("button", name="차량 삭제"). 아이콘 버튼에 이름을 주는 게 aria-label이다
  2. 그걸로 구분이 안 되면 testid — 같은 이름이 여럿이거나, 이름이 자주 바뀌는 자리
  3. 행·데이터 식별은 PK — 표시 텍스트로는 같은 건을 구분할 수 없다
  4. 전부 Page Object 안에 — 테스트 본문에는 셀렉터가 안 나온다
  5. 정답 출처가 화면에 없으면 API — 누락 방향(조건 ⊆ 결과)은 대개 여기서만 확인된다

왜 "사람이 보는 이름"이 1순위인가

testid로 잡으면 테스트가 사용자와 다른 것을 본다. testid는 화면에 보이지 않는 속성이라, 라벨이 통째로 사라져도 testid만 남아 있으면 통과한다.

# 버튼 글자가 "" 로 비어도, 아이콘이 안 그려져도 통과한다
page.get_by_test_id("fs-filter__search-btn").click()

# 사람이 읽는 이름이 사라지면 실패한다 — 사용자가 겪는 것과 같은 것을 본다
page.get_by_role("button", name="조회").click()

이게 11장(위양성)과 이어진다. testid만으로 잡는 화면은 "보이는 것"에 대한 검증이 저절로 약해진다. 그래서 노출 검증 TC에서는 expect(...).to_be_visible()처럼 보이는가를 따로 확인해야 한다 — testid로 찾았다는 사실 자체는 아무것도 보장하지 않는다.

12-3현실 — 넷 중 셋은 우리가 통제할 수 없다

기법누가 만드나QA가 할 수 있는 것
aria-label프론트엔드❌ 요청만
data-testid프론트엔드❌ 요청만 (지금은 시범 몇 페이지뿐)
PK 속성프론트엔드❌ 요청만
Page ObjectQA✅ 전적으로 우리 것

이상적인 모델에서 1순위였던 것들이, 실무에서는 우리 손에 없다. 요청해도 다음 스프린트로 밀리고, 밀리는 동안에도 자동화는 굴러가야 한다. 그래서 투자 우선순위가 뒤집힌다.

12-4실무의 답 — 순서가 이렇게 바뀐다

① Page Object부터 만든다 (유일하게 우리 것이므로)

흔히 드는 이유는 "이름 바뀌면 한 곳만 고친다"인데, 진짜 이유는 따로 있다. 지금 CSS로 잡아둔 곳이 나중에 testid로 바뀔 때, Page Object가 있으면 고칠 곳이 한 파일이다. 없으면 27곳을 찾아 바꾸다가 한 곳을 놓친다.

# 지금 — testid 가 없어서 CSS 로 잡는다
@property
def spinner(self): return self.page.locator(".spinner")

# 나중에 FE 가 붙여주면 이 한 줄만 바뀐다. 테스트 파일은 손 안 댄다
@property
def spinner(self): return self.page.get_by_test_id("fs-page__spinner")

Page Object는 testid가 있어서 쓰는 게 아니라, testid가 없을 때 더 필요하다.

② 있는 화면은 testid로, 없는 화면은 role/label → CSS 순으로

상황쓰는 것
testid가 붙어 있다testid — 이미 있으면 공짜다
testid는 없고 사람이 읽는 이름은 있다get_by_role / get_by_label
둘 다 없다CSS — 단, TODO(testid): 주석과 함께

③ 그 TODO 목록이 FE 요청의 근거가 된다

요청이 통하고 안 통하고는 말하는 방식에서 갈린다.

이렇게 말하면이렇게 들린다
"testid 좀 붙여주세요""테스트용 속성을 왜 프로덕션 코드에?" → 설득 필요
"이 27곳이 CSS로 잡혀 있어서 화면이 바뀔 때마다 깨집니다"구체적 비용 → 우선순위 매길 근거가 생김

④ aria-label은 자동화가 아니라 접근성 이슈로 올린다

같은 요청인데 명분이 다르면 결과가 다르다. 자동화 편의로 요청하면 "우리 우선순위 아님"으로 밀리고, 접근성으로 올리면 원래 지켰어야 할 것이라 반박 여지가 없다 (4장 ② 참고). 그리고 통과하면 자동화도 같이 좋아진다.

12-5우리 화면들의 실제 답

화면상황답
차량관리 > 현장 서비스testid 59개 + PK 짝까지 완비testid + Page Object로 끝. FE 요청 불필요
단말기 > 모니터testid 0개 — div.column, .spinner, a[type="pageItem"]role/텍스트 우선 + CSS는 TODO(testid):로 축적

현장 서비스는 예외적으로 좋은 케이스다. 시범 배포라서 잘 붙어 있는 것이지, 회사 전체에 이런 컨벤션이 있는 게 아니다 — 다른 화면은 정반대다. 이 화면 기준으로 "우리는 testid를 쓴다"고 일반화하면 안 된다.

12-6aria-label — 이 화면에 있는지 아직 모른다

정직하게 적어둔다. testid는 59개를 직접 세어봤지만, aria-label은 한 번도 세어보지 않았다. "요즘 프레임워크면 있겠지"는 추측이지 측정이 아니다.

관찰과 증명은 다르다. 확인하지 않은 것은 "있을 것이다"라고 적지 않고, 모른다고 적는다. 안 그러면 다음 사람이 이 문장을 근거로 판단한다.

확인하는 법 (DevTools 콘솔)

// ① 전체 개수 — testid 59개와 비교해볼 수 있다
document.querySelectorAll('[aria-label]').length

// ② 진짜 궁금한 것 — 글자 없는 버튼에 이름이 붙어 있나
console.table([...document.querySelectorAll('button')]
  .filter(b => !b.innerText.trim())
  .map(b => ({ aria: b.getAttribute('aria-label'), html: b.outerHTML.slice(0, 70) })))

②에서 aria가 null인 줄들이 나오면, 그게 그대로 FE 요청 목록이다 — "접근성 검사에 걸리는 아이콘 버튼 N개"라는 형태로 올릴 수 있다.
