# 자동화 테스트 노트

Codegen, pytest, fixture, conftest.py, .env 까지 — 자동화 테스트를 짜면서 질문하거나 헷갈렸던 개념들을 그때그때 압축해서 모았습니다.

## 용어 — 먼저 알아둘 단어들

앞으로 계속 나오는 단어라 한 번 정리해두면 이후가 편합니다.

| 용어 | 설명 |
|---|---|
| **Playwright** | 코드로 브라우저를 조작하는 자동화 라이브러리. 클릭·입력·이동을 사람 대신 코드가 함. |
| **pytest** | 파이썬 테스트 실행 프레임워크. `test_`로 시작하는 함수들을 찾아서 실행하고 결과를 리포트함. |
| **pytest-playwright** | pytest와 Playwright를 연결하는 플러그인. 테스트 함수마다 브라우저를 자동으로 열고 닫아줌. |
| **venv (가상환경)** | 프로젝트 전용 파이썬 패키지 공간. 다른 프로젝트와 라이브러리 버전이 안 섞이게 함. |
| **Codegen** | 브라우저에서 클릭·입력하는 대로 파이썬 코드를 자동으로 뽑아주는 Playwright 도구. |
| **Inspector** | Codegen 실행 시 뜨는 창. 기록되는 코드가 실시간으로 보이고, 검증 버튼·Pick locator가 여기 있음. |
| **Locator (셀렉터)** | 화면의 특정 요소를 코드가 찾아내는 방법. `get_by_role(...)`, `get_by_test_id(...)` 등. |
| **fixture** | pytest가 테스트 함수에 자동으로 넣어주는 준비된 객체. 여기선 `page`(열려 있는 브라우저 탭)가 그 예. |
| **assert / expect** | "이 상태가 맞는지" 확인하는 코드. 틀리면 그 자리에서 테스트가 실패로 멈춤. |
| **storage state** | 로그인 세션(쿠키 등)을 파일로 저장한 것. 예: `auth.json` — 매번 로그인 안 해도 되게 해줌. |
| **conftest.py** | pytest가 예약어처럼 인식하는 파일명. import 안 해도 같은 폴더의 테스트를 실행하기 전에 pytest가 자동으로 먼저 불러옴. 공용 fixture·설정을 두는 곳. |
| **.env / .env.example** | `.env`는 실제 비밀값(코드가 읽음, git 제외). `.env.example`은 키 이름만 있는 템플릿(git에 커밋, 값은 비움). |
| **headless / headed** | 브라우저 창을 안 보이게(headless) / 실제로 보이게(headed) 실행하는 모드. |
| **data-testid** | 개발자가 테스트를 위해 화면 요소에 붙여둔 전용 식별자. 텍스트·역할보다 안 깨짐. |

## 개념 — 라이브러리 · 프레임워크 · 플러그인

이 셋의 차이를 알면 왜 pytest, Playwright, pytest-playwright를 같이 쓰는지 정리가 됩니다.

| 구분 | 정의 | 이 프로젝트의 예 |
|---|---|---|
| **라이브러리** | 내가 필요할 때 갖다 쓰는 도구. **내 코드가** 함수를 호출함 | `Playwright` |
| **프레임워크** | 큰 뼈대가 이미 있고, **그것이** 내 코드를 자기 타이밍에 호출함 | `pytest` |
| **플러그인** | 프레임워크에 꽂아 쓰는 부속품. 그 프레임워크 없이는 무의미함 | `pytest-playwright` |

> **비유**
>
> pytest(프레임워크)는 공장의 컨베이어 벨트, 내 `test_` 함수들은 벨트 위 부품, Playwright(라이브러리)는 작업자가 손에 든 공구, pytest-playwright(플러그인)는 그 공구를 벨트 시스템에 자동으로 쥐어주는 장치입니다. 벨트가 없어도 공구 자체는 손에 들고 혼자 쓸 수 있지만, 장치는 벨트가 있어야만 의미가 있습니다.

> **모든 라이브러리가 Playwright처럼 독립적인 건 아닙니다**
>
> 라이브러리 중에서도 **처음부터 특정 프레임워크 안에서만 쓰이도록 만들어진 것**이 있습니다. `pytest-playwright`가 바로 그 예입니다 — 이름은 "라이브러리"지만 pytest 없이는 아무 동작도 안 합니다. 독립형(Playwright)과 프레임워크 전용 부속품(pytest-playwright)이 같은 "라이브러리"라는 이름으로 불려서 헷갈리기 쉽습니다.

**꼬리질문 — 그럼 플러그인 = 의존적인 라이브러리를 부르는 말인가?**

비슷하지만 조건이 하나 더 붙습니다. 그냥 의존하는 것과 플러그인은 다릅니다 — 플러그인은 "의존적인 라이브러리" 중에서도, 프레임워크가 미리 정해놓은 **확장 지점(hook)**에 맞춰 등록되어 프레임워크가 알아서 찾아 호출해주는 것만 가리킵니다.

| | 그냥 의존 관계 (requests ↔ urllib3) | 플러그인 (pytest ↔ pytest-playwright) |
|---|---|---|
| 어떻게 연결되나 | 코드 안에서 직접 `import`해서 씀 | 프레임워크가 정한 규칙에 맞춰 등록, 자동 인식됨 |
| 호출 방식 | 내가 명시적으로 호출 | 프레임워크가 알아서 찾아서 호출 |

**한 문장으로**: 플러그인은 "의존적인 라이브러리"의 부분집합입니다 — 의존적이면서, 동시에 그 프레임워크의 공식 확장 시스템에 맞춰 등록된 것만 플러그인이라고 부릅니다.

**꼬리질문 — codegen은 "라이브러리 내부 도구"인가?**

정확히는 Playwright 패키지와 같이 배포되는 별도의 커맨드라인 도구입니다. Playwright는 두 가지를 같이 제공합니다:

- **라이브러리(API)** — 내 코드가 `import`해서 쓰는 것 (`from playwright.sync_api import ...`)
- **CLI 도구 모음** — 터미널에서 명령어로 실행하는 것 (`playwright install`, `playwright codegen` 등)

codegen은 두 번째에 속합니다. 내 테스트 코드가 codegen을 호출하는 일은 없고, 개발자가 코드를 짤 때 터미널에서 직접 실행하는 보조 프로그램이에요.

## Q&A — 헷갈렸던 것들

### 1. pytest로 실행 vs python으로 실행

`python 파일.py`는 스크립트를 그냥 위에서 아래로 실행 — 브라우저를 여닫는 코드가 파일 안에 직접 있어야 합니다. `pytest 파일.py`는 `test_`로 시작하는 함수들을 찾아 각각 실행하고, 브라우저는 pytest-playwright가 `page`를 통해 자동으로 열고 닫습니다.

**꼬리질문 — fixture는 정확히 뭔가? 열린 브라우저 객체? 아니면 이름?**

둘 다 아니고, **"준비하고 → 건네주고 → 끝나면 정리하는" 흐름을 담은 함수**입니다.

```python
@pytest.fixture
def page(browser):
    page = browser.new_page()   # 브라우저 탭을 새로 만듦
    yield page                  # ← 이 객체를 테스트 함수에 건네줌
    page.close()                # ← 테스트 끝나면 자동으로 정리
```

- **fixture 자체** = 이 코드 전체, 즉 준비/정리 절차
- 테스트 안에서 실제로 쓰는 `page` = 이 fixture가 실행되면서 만들어낸 **결과물**(Page 객체)

브라우저에만 국한된 개념도 아닙니다 — pytest 자체의 일반 개념이라, DB 연결·테스트용 데이터 등 테스트에 필요한 무엇이든 같은 방식(준비 → 전달 → 정리)으로 다룰 수 있습니다. 지금 쓰는 `page`는 그 대상이 마침 브라우저 탭인 경우일 뿐입니다.

**꼬리질문 — conftest.py는 뭘 의미하고, 왜 있는가? `pytest test_login.py`만 실행하는데 왜 관여하나?**

`conftest.py`는 pytest가 예약어처럼 특별 취급하는 파일명입니다("configuration for test"의 줄임). 어디서도 `import conftest`라고 안 적어도, pytest가 테스트를 실행하기 전에 **같은 폴더(및 상위 폴더)의 conftest.py를 자동으로 먼저 읽어 들입니다.**

그래서 `pytest test_login.py`라고 그 파일만 지목해도, 내부적으로는:

```
1. conftest.py 자동 로드      # load_dotenv() 실행 → .env 값들을 환경변수로 등록
2. test_login.py 로드         # os.getenv("STAFF_ADMIN_EMAIL") 등이 실행됨
3. 테스트 함수들 실행
```

이 순서가 중요한 이유는, `test_login.py` 맨 위의 `ADMIN_EMAIL = os.getenv(...)`가 파일이 로드되는 순간 바로 실행되기 때문입니다. 그 시점에 `.env` 값이 아직 환경변수로 안 들어와 있으면 `None`만 읽힙니다. conftest.py에 `load_dotenv()`를 넣어두면, 테스트 파일이 몇 개로 늘어나도 매번 반복 안 해도 자동으로 먼저 적용됩니다.

**한 줄로**: 실행 명령엔 이름이 안 보이지만, pytest가 뒤에서 항상 먼저 불러오는 "공용 준비 파일"입니다.

### 2. Inspector가 뭔가요

Codegen 실행 시 뜨는 별도 창으로, 기록·디버깅 도구입니다. 행동을 코드로 실시간 변환해서 보여주고, 검증 버튼과 Pick locator도 여기 있습니다. 이미 짠 테스트에 `page.pause()`를 넣으면 그 지점에서 같은 창이 열려 디버깅용으로도 씁니다.

**꼬리질문 — codegen 실행하면 이미 Inspector가 켜져 있는데, 왜 `page.pause()`가 또 필요한가?**

이 둘은 완전히 다른 브라우저 세션입니다. `codegen`은 로그인도 안 되어있고 어떤 화면 진입 상태도 없는 백지 상태로 새 브라우저를 띄웁니다.

`page.pause()`는 이미 짜놓은 테스트를 실제로 실행해서 로그인하고, 몇 단계 화면을 넘어간 그 상태에 도달한 다음 멈춰서 Inspector를 엽니다. "로그인하고 3번째 화면까지 들어간 상태에서 이 셀렉터가 왜 안 잡히지"를 확인하려면 내 테스트가 만들어내는 그 상태 안에서 봐야 하기 때문에, codegen을 새로 켜는 건(로그인 전 백지 상태라) 의미가 없습니다.

### 3. 클릭 기록 vs Pick Locator, 왜 나눠 쓰나

**Record 클릭**은 실제 클릭 "행동"까지 기록됩니다(`.click()`) — 화면이 실제로 바뀝니다. **Pick Locator**는 마우스만 올려도 셀렉터만 뽑아줍니다 — 클릭이 발생하지 않아 화면 상태가 안 바뀝니다. 검증 코드를 짤 땐 "클릭"이 아니라 "셀렉터"만 필요하므로, 화면을 건드리지 않고 싶을 때 Pick Locator를 씁니다.

꼭 써야 하는 건 아닙니다. 클릭해도 문제없는 요소 하나만 필요하면 그냥 클릭해서 셀렉터를 뽑아 써도 됩니다. Pick Locator가 진짜 필요해지는 상황은 따로 있어요:

- 클릭하면 **화면이 넘어가버리는 경우** — 같은 화면에서 셀렉터 여러 개를 연속으로 뽑아야 할 때
- 애초에 **클릭 이벤트가 없는 요소** — 상태 뱃지, 텍스트, 테이블 셀처럼 클릭해도 코드가 안 생기는 것들

### 4. Codegen으로 실제 테스트를 짜는 흐름

1. **pytest 형식으로 코드 뽑기 (아직 실행 아님)** — 이 단계는 pytest를 실행하는 게 아니라 codegen을 실행하는 겁니다. `--target python-pytest`는 "코드를 뽑을 때 `test_` 함수 모양으로 뽑아달라"는 옵션일 뿐입니다.
   ```bash
   # 이건 codegen 명령어 — 브라우저를 열어서 기록을 시작함
   playwright codegen --target python-pytest 주소
   ```
   기록이 끝나면 코드를 `test_example.py` 같은 파일로 저장하고, 그 다음 단계에서 따로 `pytest test_example.py`로 실행합니다. "코드 뽑기"와 "실행"은 서로 다른 단계예요.

2. **로그인 세션 저장** — 매번 로그인 안 하도록 한 번만 저장 후 재사용
   ```bash
   --save-storage auth.json   # 최초 1회
   --load-storage auth.json   # 이후 재사용
   ```

3. **화면에서 행동 기록** — 실제로 클릭·입력하며 액션 코드 생성

4. **검증 지점엔 assert 먼저** — 아이콘을 먼저 누르고 그다음 요소 클릭. 순서 바뀌면 그냥 클릭으로 기록됨

5. **뽑힌 코드는 그대로 쓰지 않기** — 숫자·텍스트는 정규식으로, 타임아웃 조정, 여러 행 검증은 직접 루프 작성

**꼬리질문 — `assert`와 `expect`, 뭐가 다른가?**

`assert`는 파이썬 자체 문법입니다 — 그 순간 딱 한 번만 확인하고, 조건이 거짓이면 바로 실패합니다. 재시도가 없습니다.

`expect`는 Playwright가 제공하는 전용 검증 함수입니다 — 조건이 맞을 때까지 최대 5초간 반복해서 재확인합니다 (기본값, `timeout`으로 조정 가능).

```python
# assert — 그 순간 화면에 아직 안 떠 있으면 바로 실패
assert page.get_by_role("heading").is_visible()

# expect — 최대 5초간 계속 확인, 그 사이에 뜨면 통과
expect(page.get_by_role("heading")).to_be_visible()
```

웹 화면은 데이터가 비동기로 늦게 로드됩니다. 코드는 화면보다 빠르게 실행되기 때문에, `assert`는 그 찰나에 요소가 없으면 바로 실패해버립니다. `expect`는 이런 로딩 지연을 자동으로 기다려주기 때문에 UI 테스트에서는 거의 항상 expect를 씁니다.

참고로 `assert`는 UI가 아닌 일반 파이썬 값 비교에도 씁니다 (`assert x == 5`). `expect`는 Playwright의 페이지·요소(locator) 전용입니다.

### 5. `.env`와 `.env.example`, 왜 둘 다 있나

역할이 다릅니다:

| | `.env` | `.env.example` |
|---|---|---|
| 내용 | 실제 값 (진짜 비밀번호 포함) | 키 이름만, 값은 비워둠 |
| git에 올라가나 | ❌ (`.gitignore`에 있음) | ✅ 커밋됨 |
| 용도 | 코드가 실제로 읽는 파일 | "어떤 값을 채워야 하는지" 알려주는 템플릿 |

혼자 쓸 땐 체감이 안 되는데, 이게 필요한 이유는 다른 사람(또는 나중의 나)이 이 저장소를 새로 받았을 때입니다. `.env`는 git에 없으니, 저장소를 새로 클론하면 그 컴퓨터엔 `.env`가 아예 없습니다 — 그럼 어떤 키 이름이 필요한지조차 알 수 없습니다. `.env.example`이 커밋되어 있으면, 그걸 복사해서(`cp .env.example .env`) 값만 채우면 바로 시작할 수 있습니다.

내용이 겹쳐 보이는 건 의도된 겁니다 — 키 이름은 똑같이 맞추고, 값만 비우는 게 템플릿의 역할이라서요.

### 6. session scope fixture가 왜 `page`를 직접 못 받나 — "오래 사는 게 짧게 사는 걸 담을 수 없다"

시간 축으로 그리면 이렇습니다:

```
세션(session) 전체 ─────────────────────────────────────────►
                    │←test_1→│←test_2→│←test_3→│  ...
page(function)는    [만듦-씀-버림]
                              [만듦-씀-버림]
                                        [만듦-씀-버림]
```

`page`(function scope)는 **test_1이 시작할 때 만들어지고, test_1이 끝나면 그 자리에서 버려집니다.** test_2가 시작하면 완전히 새로운 `page`가 또 만들어졌다가 또 버려집니다.

그런데 세션 스코프 fixture(`auth_state` 등)는 **"세션 전체(test_1부터 끝까지) 동안 계속 살아있겠다"**고 선언한 것입니다. 여기서 만약 세션 스코프 fixture가 `page`를 그 안에 담아두려 하면, "test_1에서만 잠깐 살고 사라질 물건"을 "세션 내내 살아야 하는 상자" 안에 넣으려는 셈이 됩니다. test_1이 끝나는 순간 그 `page`는 버려지는데, test_2가 그 상자를 열어보면 **이미 닫힌(죽은) page**만 들어있습니다 — 열어봤자 아무것도 못 하는 깨진 참조만 남는 것입니다.

pytest는 이 상황을 실행해보기도 전에 미리 감지해서 `ScopeMismatch` 에러로 막습니다.

**그래서 나온 해결책 — 두 fixture로 역할을 나눈다:**

| | `auth_state` | `logged_in_page` |
|---|---|---|
| 스코프 | session (전체에서 1번) | function (테스트마다) |
| 하는 일 | 실제 로그인(+OTP) 수행 → 결과를 **파일로 저장** | 저장된 파일을 불러와 **새 탭만** 엶 |
| 반환하는 것 | 파일 경로(문자열, 그냥 데이터) | 살아있는 `page` 객체 |

핵심은 **"상태"(쿠키 데이터)는 여러 테스트가 복사해서 나눠 가질 수 있지만, "살아있는 page 객체"는 나눠 가질 수 없다**는 것입니다. 테스트 A가 페이지를 이동시켜 놓은 상태를 테스트 B가 그대로 물려받으면 테스트끼리 서로 영향을 주게 되어(독립성이 깨짐) 안 되기 때문에, `auth_state`는 "탭"이 아니라 데이터(쿠키 값)만 저장하고, `logged_in_page`가 테스트마다 그 데이터로 새 탭을 하나씩 엽니다. **"로그인 자체"는 비싸서 세션당 한 번만, "탭"은 싸서 테스트마다 새로**라는 원칙입니다.

### 7. "session"은 브라우저를 의미하나? scope는 "참조되는 함수"인가?

둘 다 오해입니다.

**"session" ≠ Playwright의 브라우저.** session은 순수하게 pytest 개념으로, **"터미널에서 `pytest` 명령어를 한 번 실행해서, 그게 끝날 때까지의 전체 과정"**을 가리킵니다. 이 프로젝트에서 마침 pytest-playwright의 `browser` fixture도 세션 스코프로 만들어져 있어서 헷갈리기 쉽지만, 이건 pytest-playwright가 그렇게 설계했을 뿐이지 "session"이라는 단어 자체가 브라우저를 뜻하는 게 아닙니다. 브라우저와 전혀 상관없는 DB 연결 fixture도 얼마든지 세션 스코프로 만들 수 있습니다.

**scope ≠ "참조되는 함수".** scope는 **"이 fixture가 만든 결과물을 얼마나 오래 재사용할지"**를 정하는 설정일 뿐, fixture는 scope와 무관하게 항상 그냥 파이썬 함수입니다.

| scope 값 | 언제 새로 만드나 |
|---|---|
| `function` (기본값) | 테스트 함수마다 매번 새로 |
| `class` | 같은 클래스 안 테스트들끼리 공유 |
| `module` | 같은 파일 안 테스트들끼리 공유 |
| `session` | 전체 실행(pytest 한 판) 동안 딱 한 번 |

브라우저와 무관한 예:
```python
@pytest.fixture(scope="session")
def db_connection():
    conn = connect_to_database()   # 전체 실행에서 딱 1번만 연결
    yield conn
    conn.close()
```
`db_connection`이라는 함수 자체는 그대로고, `scope="session"`은 "이 함수를 매 테스트마다 다시 부르지 말고 전체 실행에서 1번만 불러서 결과를 나눠 써라"는 **재사용 주기 설정**일 뿐입니다.

### 8. `browser_type` · `context` · `headless=False` vs `--headed`

**`browser_type`** — pytest-playwright가 주는 fixture. "어떤 브라우저 엔진(chromium/firefox/webkit)을 쓸지"를 나타내는 발사대 같은 것으로, `.launch()`를 부르면 **새 브라우저 프로세스를 하나 더** 띄울 수 있습니다. `browser` fixture는 이미 켜져 있는 기본 브라우저를 그냥 건네주는 것이고, `browser_type`은 그 틀을 벗어나 **직접 원하는 설정으로 브라우저를 하나 더 켜고 싶을 때** 씁니다.

**자동으로 주는 `page`를 왜 안 쓰고 직접 만드나** — 자동 `page`는 기본(보통 headless) 브라우저에 속한 탭입니다. 로그인 순간처럼 완전히 다른(headed) 별도 브라우저가 필요할 땐, `browser_type`부터 시작해서 직접 만들어야 합니다.

**`context`** — `browser`(프로그램 자체) 안에 여러 개 만들 수 있는 독립된 세션("시크릿 창" 같은 것)입니다.
```
browser (브라우저 프로그램 하나)
 └─ context (독립된 세션 — 쿠키·로그인 상태가 서로 안 섞임)
     └─ page (탭 하나)
```
`storage_state`(쿠키)를 적용하는 단위가 바로 `context`입니다 — `browser.new_context(storage_state=auth_state)`처럼 **context를 만드는 시점에** 저장된 로그인 정보를 밀어 넣습니다.

**`headless=False` vs `--headed`** — 효과(창이 보임)는 같지만 작동 층이 다릅니다.

| | `--headed` | `headless=False` |
|---|---|---|
| 어디서 주나 | 터미널 명령어 옵션 | 코드 안 `browser_type.launch(...)` 파라미터 |
| 영향 범위 | 그 실행에 포함된 **모든** 테스트 | **그 코드로 직접 켠 브라우저 하나**만 |

`_login_and_save`에 `headless=False`를 코드로 박아둔 이유가 이것입니다 — 다른 테스트들이 headless로 돌아가고 있어도, 로그인 순간만큼은 터미널 옵션과 무관하게 항상 화면이 뜨도록 강제한 것입니다.

### 9. `auth.json` 방식 vs 세션 스코프 fixture 방식, 뭐가 더 나은가

한쪽이 무조건 나은 게 아니라 서로 다른 걸 최적화합니다.

| | **`auth.json` 고정 파일 방식** | **`tmp_path_factory` (문서 권장 버전)** |
|---|---|---|
| 언제 로그인하나 | 그 테스트를 직접 실행할 때만 | fixture를 쓰는 테스트가 있으면 세션당 자동 1번 |
| 실행마다 OTP 다시 쳐야 하나 | ❌ 파일이 안 만료됐으면 안 쳐도 됨 | ✅ 실행 끝나면 파일 자동 삭제 → 매 실행마다 다시 쳐야 함 |
| 파일 안전성 | 고정 파일이라 `.gitignore` 직접 관리 필요 | 임시 폴더 → 실행 끝나면 자동 정리, 더 안전 |
| 다른 테스트 자동 연결 | 직접 연결하는 코드를 따로 짜야 함 | fixture로 자동 연결됨 |

**절충안**(지금 conftest.py에 적용한 방식): `auth_state`/`logged_in_page`처럼 fixture로 자동 연결하되, 저장 경로를 임시 폴더 대신 `auth.json`처럼 **고정 경로**로 하고, 파일이 있고 안 만료됐으면 로그인을 건너뛰는 방식입니다.

다만 이건 "장점만 가져오는" 공짜가 아니라 **트레이드오프를 하나 다시 가져오는 것**입니다 — 자동 연결이라는 장점은 얻지만, "파일이 실행 끝나면 자동으로 안전하게 지워진다"는 장점은 포기하고 `.gitignore`로 직접 관리해야 하는 책임을 다시 지게 됩니다.

**꼬리질문 — `test_login.py`의 TC-114도 이 절충안에 자동으로 얹었는데, 뭐가 바뀌나?**

처음엔 TC-114가 `_login_and_save`를 **직접** 호출해서, `auth_state`(신선하면 건너뜀)와 다르게 **항상 무조건 실제 로그인을 검증**하도록 일부러 분리해뒀습니다. 그런데 `pytest test_login.py`를 자주 돌리다 보니 매번 인증번호를 다시 쳐야 하는 게 번거로워서, TC-114도 `auth_state` fixture를 그대로 받아 쓰도록 바꿨습니다.

```python
def test_TC114_login_success_and_refresh_session(auth_state):
    assert os.path.exists(auth_state)
```

**의미가 살짝 바뀐 것**을 알고 계셔야 합니다:

| | 이전 | 지금 |
|---|---|---|
| TC-114가 확인하는 것 | "로그인이 실제로 되는가" (매번 실제 로그인 수행) | "유효한 세션이 준비되어 있는가" (신선하면 로그인 자체를 건너뜀) |
| `auth.json`이 신선할 때 | 그래도 다시 로그인해서 검증 | 로그인 안 하고 바로 통과 |

**로그인 로직 자체가 진짜 잘 되는지 다시 확실히 확인하고 싶으면**, `auth.json`을 지우고 나서 이 테스트를 돌리면 됩니다 — 그러면 파일이 없으니 무조건 실제 로그인을 수행하게 됩니다.

### 10. `assert`는 조건을 통과하면 PASS를 만드는 건가

정확히는 조금 다릅니다 — `assert`는 **"불통과일 때만 반응"**하는 구조입니다.

```python
assert 조건, "실패 메시지"
```

- 조건이 **참**이면 → 아무 일도 안 일어남. 그냥 다음 줄로 넘어갑니다. (합격 표시가 뜨는 게 아니라 그냥 조용히 통과)
- 조건이 **거짓**이면 → `AssertionError`를 **던집니다.** 이때 뒤에 적은 메시지가 에러 내용으로 딸려 나갑니다.

**PASS/FAIL을 정하는 건 assert 자신이 아니라 pytest**입니다. pytest 규칙은 단순합니다:

- 테스트 함수가 **에러 없이 끝까지 실행되면** → PASSED
- 테스트 함수 실행 중 **어떤 예외든 튀어나오면**(assert가 던진 AssertionError 포함) → FAILED

`test_vehicle_register_reseller.py`의 TC-043 예시:

```python
assert partner_field.get_attribute("aria-disabled") == "true", (
    "[FAIL] 파트너 항목이 수정 가능한 상태입니다 (수정 불가여야 함)"
)
```

- `aria-disabled`가 `"true"`면 → assert는 조용히 통과 → 테스트 함수 끝까지 무사히 실행 → pytest가 **PASSED** 표시
- `"true"`가 아니면 → assert가 에러를 던짐 → 테스트 함수가 중간에 멈춤 → pytest가 그 에러를 잡아서 **FAILED** 표시하고 메시지 출력

**한 줄로**: `assert`는 "합격 판정 도장"이라기보다 **"틀리면 경보 울리는 트립와이어"**에 가깝습니다. 조건이 참일 땐 존재감이 없다가, 거짓일 때만 존재를 드러냅니다.

## 필수 — 이 4가지는 꼭 기억

가이드 전체에서 실제로 테스트가 깨지는 원인이 되는 부분만 추렸습니다.

> **① 부분 일치의 함정**
>
> `name="완료"`는 "완료"뿐 아니라 "배정완료", "운영완료"까지 다 잡습니다. 시작 지점을 고정하려면 정규식을 씁니다: `re.compile("^완료")`. 텍스트 검증도 마찬가지로 `to_contain_text`(포함) 대신 정확히 같아야 하면 `to_have_text`를 씁니다.

> **② 이름에 박힌 숫자**
>
> `name="완료 217"`처럼 건수가 이름에 포함된 요소는, 건수가 바뀌는 순간(218이 되는 순간) 테스트가 깨집니다. 숫자는 빼고 정규식으로 시작 부분만 고정하세요.

> **③ 기다림이 없다**
>
> 사람이 클릭할 땐 화면이 이미 떠 있어서 기다릴 필요가 없었지만, 코드는 화면보다 빠르게 실행됩니다. 데이터가 늦게 뜨는 화면은 `timeout=15000`처럼 직접 늘려줘야 합니다. 기본은 5초입니다.

> **④ auth.json은 절대 커밋 금지**
>
> 로그인 토큰이 평문으로 들어있어, 유출되면 그 계정으로 누구나 로그인 가능합니다. `.gitignore`에 넣어두고, 토큰은 며칠 지나면 만료되니 그때 `--save-storage`로 새로 받으면 됩니다.

> **한 문장으로**
>
> Codegen은 "화면에 뭐가 있나"를 알려주는 도구이지 테스트를 완성해주는 도구가 아닙니다. 셀렉터만 가져오고, 검증 로직과 안정성은 직접 손봐야 합니다.
