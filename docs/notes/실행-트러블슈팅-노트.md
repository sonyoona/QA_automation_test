# 실행이 깨졌을 때 보는 노트

테스트 **내용**이 아니라 **실행 자체**가 안 될 때 보는 곳입니다. 2026-09-10 에 하루 동안
세 가지에 연달아 물렸고, 셋 다 "코드가 잘못됐나?" 로 오해하기 쉬운 모양이었습니다.

기록을 남기는 이유는 **증상만 보면 원인이 엉뚱한 곳으로 보이기 때문**입니다. 실행 스크립트가
깨졌을 때는 스크립트 내용이 멀쩡했고, 모든 테스트가 빨간불일 때는 테스트 코드가 멀쩡했습니다.

## 빠른 찾기 — 증상에서 원인으로

| 증상 | 십중팔구 원인 | 어디로 |
|---|---|---|
| `'run_tests_and_report.bat' 용어가 ... 인식되지 않습니다` | PowerShell 은 현재 폴더 명령을 그냥 안 쓴다 | 01 |
| 배치 파일을 돌렸더니 `'ing'`·`'ure-results'` 같은 조각이 명령으로 실행됨 | `.bat` 이 LF 줄바꿈 | 02 |
| 배치 파일의 한글이 `'몄쟻?쇰줈'` 처럼 깨짐 | `.bat` 이 UTF-8 인코딩 | 02 |
| Mac/Linux 에서 `.sh` 가 `bad interpreter` 로 죽음 | `.sh` 가 CRLF 로 체크아웃됨 | 03 |
| **전 테스트가 ERROR** 인데 2FA 로그인 창이 안 뜸 | 세션은 죽었는데 쿠키가 안 만료됨 | 04 |
| 연속으로 `E` 가 쏟아짐 | 세션 충돌 (브라우저·다른 pytest) | 04 |
| 로그인 창은 떴는데 뭘 하라는 안내가 없음 | pytest 가 출력을 가둠 | 05 |

## 01. PowerShell 에서 `.\` 를 붙여야 하는 이유

```
run_tests_and_report.bat : 'run_tests_and_report.bat' 용어가 cmdlet, 함수, 스크립트 파일
또는 실행할 수 있는 프로그램 이름으로 인식되지 않습니다.
```

**고장이 아니라 PowerShell 의 정상 동작입니다.** 보안상 "현재 폴더에 있는 실행 파일"을
이름만으로는 실행해주지 않습니다. 현재 폴더에 악성 `ls.bat` 을 놔두고 사람이 `ls` 를 치도록
유도하는 공격을 막기 위한 것입니다.

```bash
.\run_tests_and_report.bat
```

`.\` 는 **"지금 이 폴더의"** 라는 뜻입니다. cmd.exe 나 Git Bash 에서는 필요 없습니다 —
PowerShell 에서만 그렇습니다.

## 02. `.bat` 이 깨진 두 가지 이유 (2026-09-10)

`.\run_tests_and_report.bat` 을 돌렸더니 이렇게 나왔습니다.

```
'몄쟻?쇰줈'은(는) 내부 또는 외부 명령, 실행할 수 있는 프로그램, 또는 배치 파일이 아닙니다.
'ing'은(는) ...
'ure-results'은(는) ...
'e-results'은(는) ...
```

원인이 **둘**이었고, 각각 다른 증상을 냈습니다.

### 원인 A — 줄바꿈이 LF 였다 (조각이 명령으로 실행된 이유)

`cmd` 는 배치 파일이 **CRLF** 줄바꿈인 것을 전제로 읽습니다. LF 로 저장돼 있으면 한 줄을
읽은 뒤 "다음 줄이 어디부터인지" 계산이 1바이트씩 어긋나고, 그 어긋남이 쌓여서 **줄 중간부터
명령으로 읽기 시작합니다.**

```
파일에 있던 줄:  allure generate allure-results --output allure-report
cmd 가 읽은 것:                  ing        ure-results       e-results
```

`'ing'`·`'ure-results'`·`'e-results'` 는 전부 원래 줄의 **꼬리 조각**입니다.

### 원인 B — 인코딩이 UTF-8 이었다 (한글이 깨진 이유)

한국어 Windows 의 `cmd` 는 배치 파일을 **cp949** 로 읽습니다. 파일이 UTF-8 이면 한글이
전부 깨집니다.

### 고친 것 — CRLF + cp949

```
줄바꿈  LF     ->  CRLF
인코딩  UTF-8  ->  cp949
```

### ★ `chcp 65001` 로는 못 고친다 (둘 다 실측)

UTF-8 을 유지한 채 배치 파일 안에서 코드페이지를 바꾸는 방법을 두 번 시도했고 둘 다 실패했습니다.

| 시도 | 결과 |
|---|---|
| `@echo off` 다음 줄에 `chcp 65001 >nul` | 한글은 나오는데 **`REM` 주석 줄까지 명령으로 실행**됨 (`'트가' is not recognized`) |
| `chcp 65001` 을 **맨 첫 줄**로 올림 | 같음 |

이유는 원인 A 와 같습니다 — **파일을 읽는 도중에 코드페이지를 바꾸면 바이트 위치 계산이
어긋납니다.** 그래서 인코딩 자체를 cp949 로 바꾸는 쪽이 유일한 해법이었습니다.

**대가**: 이 파일의 `git diff` 에서 한글이 깨져 보입니다. 거의 안 고치는 파일이라 감수했습니다.

### 곁다리로 같이 고친 둘

- **이모지·체크마크·em dash 를 아스키로** (`[*]`·`[OK]`·`[--]`·`-`) — cp949 에 없는 문자라
  콘솔에서 깨집니다. `CLAUDE.md` 의 "cp949에 없는 문자를 쓰지 않는다" 규칙과 같은 이유입니다.
- **`setlocal enabledelayedexpansion` -> `setlocal`** — 지연확장이 켜져 있으면 `echo` 의
  `!` 가 사라집니다. 실제로 `[!] --allow-mutating 켜짐` 이 `[] --allow-mutating 켜짐` 으로
  찍히고 있었습니다. 이 저장소는 `!변수!` 문법을 안 쓰므로 그냥 껐습니다.

## 03. 줄바꿈(LF / CRLF)과 git — 개념 정리

02 에서 나온 "줄바꿈" 이 뭔지, git 이 그걸 왜 건드리는지입니다.

### LF 와 CRLF

엔터를 눌렀을 때 파일에 저장되는 **눈에 안 보이는 문자**입니다. OS 마다 다릅니다.

| 이름 | 실제 바이트 | 쓰는 곳 |
|---|---|---|
| **LF** | `\n` (1바이트) | Mac · Linux |
| **CRLF** | `\r\n` (2바이트) | Windows |

편집기에서는 똑같이 "줄이 나뉜" 것으로 보이는데, 프로그램이 읽을 때는 다릅니다.

### `core.autocrlf` 가 하는 일

```bash
git config core.autocrlf     # 지금 값을 물어보는 명령 (아무것도 안 바꾼다)
```

이 저장소를 쓰는 환경에서는 값이 `true` 입니다. 뜻은 이렇습니다.

> **"저장소 안에는 LF 로 넣고, 내 컴퓨터로 꺼낼 때는 CRLF 로 바꿔서 줘라."**

```
저장소(GitHub)         <- 항상 LF 로 저장           ┐  autocrlf=true 가
내 Windows 작업 폴더   <- 꺼낼 때 CRLF 로 변환      ┘  자동으로 해주는 일
```

그래서 커밋할 때 이런 경고가 뜹니다. **오류가 아니라 예고**입니다.

```
warning: in the working copy of 'run_tests_and_report.sh', LF will be replaced by CRLF
```

### `.sh` 가 CRLF 면 왜 죽나

`.sh` 는 Mac/Linux 용 실행 스크립트입니다. 첫 줄이 이렇게 생겼습니다.

```bash
#!/bin/bash
```

"이 파일을 `/bin/bash` 로 실행해라" 라는 뜻입니다. CRLF 면 이게 **`/bin/bash` + 보이지 않는
`\r`** 가 되고, 그런 이름의 프로그램은 없으므로 이렇게 죽습니다.

```
bad interpreter: /bin/bash^M: no such file or directory
```

이 저장소에는 `run_tests_and_report.bat`(Windows용)과 `run_tests_and_report.sh`(Mac/Linux용)이
짝으로 있어서, **한쪽은 CRLF 여야 하고 다른 쪽은 LF 여야 합니다.** `core.autocrlf` 하나로는
둘을 다르게 맞출 수 없습니다.

### 그래서 `.gitattributes` 를 넣었다

```
*.sh   text eol=lf
*.bat  text eol=crlf
```

`.gitattributes` 는 **저장소에 들어가는 파일**이라 누가 어떤 환경에서 받아도 똑같이 적용되고,
사람마다 다를 수 있는 `core.autocrlf` **개인 설정을 이깁니다.**

**이걸 안 넣으면 02 에서 고친 `.bat` 이 다음 체크아웃에서 조용히 되돌아갑니다.**
`autocrlf=true` 가 변환해주는 건 맞지만 그건 **그 사람 설정에 달린 것**이라 근거로 삼을 수 없습니다.

## 04. 전 테스트 ERROR + 2FA 창이 안 뜬 사건 (2026-09-10)

**이 노트에서 제일 중요한 항목입니다.** 증상만 보면 코드 버그로 보이는데 원인은 세션입니다.

### 무슨 일이 있었나

| 시각 | 일어난 일 |
|---|---|
| 09-09 11:54 | 로그인 성공. 쿠키 만료가 **09-10 11:54** 로 저장됨 |
| 09-10 10:01 | 전체 실행. 만료까지 1시간 53분 남아 `_auth_state_is_fresh` 가 "신선함" 이라 답함 |
| | -> **재로그인이 일어나지 않음.** 사람은 2FA 창을 기다렸는데 안 뜸 |
| | 그런데 서버 쪽 세션은 이미 죽어 있었음 |
| 09-10 10:03 | 모든 TC 가 로그인 화면에서 GNB `차량관리` 를 30초씩 기다리다 타임아웃 -> **전부 ERROR** |

리포트에 남은 실제 오류가 증거입니다. **주소는 제대로 갔는데 메뉴가 없었다** =
로그인 화면에 서 있었다는 뜻입니다.

```
playwright._impl._errors.TimeoutError: Locator.click: Timeout 30000ms exceeded.
Call log:
  - waiting for locator("a").filter(has_text=re.compile(r"^차량관리$"))
    - navigated to "https://fms-dev-staff.carbom.co.kr/"
```

### 쿠키와 세션은 다른 곳에 있는 두 물건이다

이게 핵심 개념입니다.

| | 어디 있나 | 뭐라고 적혀 있나 |
|---|---|---|
| **쿠키** | **내 컴퓨터** (`auth.json`) | "나는 이 사람이다. 09-10 11:54 까지 유효" |
| **세션** | **서버** | "이 사람 로그인 중임" 이라는 **명단의 한 줄** |

화면에 들어갈 때마다 이렇게 대조합니다.

```
내 컴퓨터  --"이 쿠키 가진 사람인데요"-->  서버가 자기 명단을 확인
           <-- "명단에 있네, 들어와"
           <-- "명단에 없는데? 로그인부터 해"      <- 이번에 이쪽이었다
```

**쿠키에 적힌 만료 시각은 "내 쪽 종이에 적힌 글씨"일 뿐입니다.** 서버는 그걸 보고 판단하지
않고 **자기 명단**을 봅니다.

> **호텔 카드키로 바꿔 말하면** — 카드에 `09-10 11:54까지` 라고 인쇄돼 있어도, 프런트가
> 기록을 지우면 문이 안 열립니다. **카드만 봐서는 죽었는지 알 수가 없고, 문에 대봐야 압니다.**

### 서버가 왜 죽였나 — 확정 못 했다

**어느 것인지 확인하지 못했습니다.** 확인된 건 "10:01 시점에 이미 죽어 있었다" 뿐입니다.
후보가 셋이고, 이 프로젝트에서는 1번이 가장 흔합니다.

1. **같은 계정으로 다른 데서 로그인했다** — 이 계정은 동시에 한 곳에서만 로그인이 유지됩니다.
   새 로그인이 들어오면 서버가 앞의 것을 명단에서 지웁니다. **사람이 브라우저로 열어둔 창도
   똑같이 세션을 가져갑니다.**
2. **서버가 재시작됐다** — dev 는 배포가 잦고, 재시작으로 명단이 초기화될 수 있습니다.
3. **서버 쪽 유효기간이 쿠키보다 짧다** — 쿠키엔 24시간이라 적어놓고 서버는 더 짧게 잡은 경우.

### 고친 것 — 원인을 알아낼 필요가 없게 만들었다

세 경우 모두 증상이 같습니다(카드는 멀쩡한데 문이 안 열림). 그래서 원인을 추측하는 대신
**매번 문에 대봅니다.**

```python
# before — 카드에 인쇄된 날짜만 읽는다. 서버 사정은 알 수가 없다
if not _auth_state_is_fresh(AUTH_STATE_PATH):
    _login_and_save(browser_type)

# after — 날짜도 보고, 실제로 문이 열리는지도 본다
if _auth_state_is_fresh(...) and _session_alive(...):
    return AUTH_STATE_PATH
if os.path.exists(AUTH_STATE_PATH):
    os.remove(AUTH_STATE_PATH)     # 낡은 세션 파일을 남기지 않는다
_login_and_save(browser_type)      # -> 2FA 창이 뜬다
```

`_session_alive()` 는 headless 로 한 번 열어 **GNB 상위 메뉴가 보이는지**를 봅니다.
판정 기준을 GNB 로 잡은 것은 **테스트가 실제로 의존하는 신호와 같아서 새로 단정하는 게
없기 때문**입니다 — 위 타임아웃이 바로 "그 신호가 없었다" 는 증거입니다.

비용은 세션당 headless 브라우저 1회(약 3~5초), 막는 것은 20분짜리 전체 ERROR 실행입니다.

### ★ 같이 발견한 구멍

`_auth_state_is_fresh` 는 세션 쿠키(`expires == -1`)를 만료 판정에서 **제외**하도록 짜여
있어서, 그런 쿠키가 오면 **영원히 "신선함"** 이라고 답합니다. 지금 dev 쿠키는 만료 시각이
있어서 안 밟았지만, 서버가 세션 쿠키로 바뀌면 즉시 밟습니다. `_session_alive` 를 뒤에 둔
것이 그 대비입니다.

### 돌리기 전 습관

**`fms-dev-staff` 에 로그인해 둔 브라우저 창을 닫고 돌립니다.** 계정당 단일 세션이라
그 창이 테스트 세션을 계속 빼앗아 갑니다. `pytest` 를 두 개 동시에 돌려도 같습니다.

## 05. pytest 가 출력을 가둔다 (capturemanager)

로그인 창은 떴는데 **뭘 하라는 안내가 하나도 없던** 문제입니다.

### pytest 는 print 를 화면에 안 띄우고 통에 담아둔다

안 그러면 어느 테스트가 통과했는지가 print 에 파묻히기 때문입니다.

```
# 가두지 않으면
test_field_service.py::test_TC043_... [검증] 리셀러 컬럼 확인
[검증] 12행 전수 확인
PASSED    [ 1%]
```

그래서 pytest 는 print 를 통에 담아뒀다가 **그 테스트가 실패했을 때만** `Captured stdout`
으로 꺼내 보여주고, 통과하면 통을 버립니다. `pytest -s` 의 `-s` 가 **"통에 담지 말라"** 는 옵션입니다.

### 그래서 안내가 안 보였다

`_login_and_save` 안의 이 문구가 통에 담긴 뒤 버려지고 있었습니다.

```python
print("[로그인] 인증번호를 직접 입력해주세요. 최대 180초 기다립니다.")
```

### 고친 것 — 로그인 구간만 뚜껑을 연다

`-s` 로 전체를 열면 나머지 68개 테스트 출력이 다 쏟아져 "파묻힘" 이 그대로 돌아옵니다.
그래서 로그인하는 그 순간만 열고 다시 닫습니다.

```
테스트 시작 ------------------------------------------> 끝
              [뚜껑 열림]
              로그인 중
              ^         ^
         여기서 열고   여기서 반드시 닫음 (try/finally)
```

```python
capman = pytestconfig.pluginmanager.getplugin("capturemanager")
if capman is not None:
    capman.suspend_global_capture(in_=True)
try:
    _login_and_save(browser_type)
finally:
    if capman is not None:
        capman.resume_global_capture()
```

- **`getplugin` 은 캡처를 시작시키는 게 아니다.** 이미 일하고 있는 **그 객체**를 받아옵니다.
  `import` 로 새로 만들면 지금까지 가둔 출력을 모르는 딴 객체라 아무 일도 안 합니다.
  에어컨은 이미 돌고 있고, `getplugin` 은 **리모컨을 찾는 것**입니다.
- **`try/finally`** — 로그인이 실패해도 뚜껑은 반드시 닫아야 합니다. 안 닫으면 그 뒤
  68개 출력이 전부 쏟아져서 정작 무엇이 실패했는지를 못 찾습니다.
  (`company_guard` fixture 의 teardown 과 같은 발상 — **열었으면 반드시 닫는다.**)

### ★ 이 항목에서 두 번 틀렸다가 실측으로 고쳤다

처음에 이렇게 설명했는데 **둘 다 사실이 아니었습니다.** 실제로 돌려서 확인한 결과입니다.

| 처음 한 말 | 실측 결과 |
|---|---|
| "`-s` 로 돌리면 플러그인이 없어서 `None` 이다" | **틀림.** `-s` 여도 객체는 있다(내부 모드만 `no`). `None` 은 `-p no:capture` 일 때만 |
| "stdin 을 안 열면 터미널이 멈춘 것처럼 보인다" | **틀림.** 안 멈춘다. `input()` 이 즉시 `OSError` 로 죽고 메시지가 해결책까지 알려준다 |

```
# -s 로 돌렸을 때
PROBE capman = CaptureManager      <- None 이 아니다
PROBE method = no                  <- 있긴 한데 "안 가둠" 모드

# 캡처를 in_=False 로 두고 input() 을 부르면
PROBE input() -> OSError: pytest: reading from stdin while output is captured!
                 Consider using `-s`.
```

`in_=True` 는 **stdin 도 함께 여는** 스위치인데, 지금은 인증번호를 브라우저 창에 치므로
**아무 효과가 없습니다.** pytest 의 대화형 예제가 그렇게 쓰기 때문에 관례를 따른 것이고,
그 판단 기준을 `CLAUDE.md` 의 **"관례이고 비용이 0이면 관례를 따른다"** 장에 규칙으로
넣었습니다. 요점은 **"관례라서 넣었다"고 적고, 없는 위험을 지어내 정당화하지 않는 것**입니다 —
근거를 부풀리면 다음 사람이 '못 건드리는 코드'로 알고 피해 갑니다.

## 이 노트에서 반복되는 교훈 하나

세 사건 모두 **증상이 원인과 다른 곳을 가리켰습니다.**

| 증상이 가리킨 곳 | 실제 원인 |
|---|---|
| 실행 스크립트 내용이 잘못됐나 | 파일의 **줄바꿈·인코딩** (내용은 멀쩡) |
| 테스트 코드가 잘못됐나 (전부 ERROR) | **세션**이 죽어 있었다 (코드는 멀쩡) |
| 로그인 코드가 안내를 안 찍나 | 찍었는데 pytest 가 **가둬뒀다** |

`CLAUDE.md` 의 `실행 전제와 실패 구분` 장이 말하는 것과 같습니다 —
**기능 검증 실패와 환경 문제를 섞지 않는다.** 연속으로 `E` 가 쏟아지면 코드부터 뒤지지
말고 환경(세션·인코딩·실행 방식)을 먼저 봅니다.
