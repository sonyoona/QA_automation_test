# 현장 서비스 테스트 노트

`test_field_service.py` + `pages/field_service_page.py` — 차량관리 > 현장 서비스 화면(`/v2/field-service`)의
**TC-260907-001~005**를 다룹니다. 전부 읽기 전용(노출 확인) TC 입니다.

이 저장소에서 **처음으로 Page Object를 분리한 화면**이라, 왜 그렇게 했는지와 실측하며 밟은 함정을 같이 적어둡니다.

## 이 화면만 다른 점 — testid 가 붙어 있다

다른 화면들(모니터, 차량관리 수정 모달 등)은 `label` 텍스트나 `div.column` 같은 구조로 요소를 찾아야 했습니다.
현장 서비스는 프론트에서 시범적으로 `data-testid`를 붙여둔 페이지라, 셀렉터를 전부 testid 로 잡을 수 있습니다.

2026-09-07 실측 기준 **목록 40개 + 신규 서비스 신청 팝업 19개 = 59개**가 붙어 있고,
테이블 행·상세 버튼에는 PK 까지 들어 있습니다(`fs-table__row--10679`, `fs-table__action-btn--10679`).

| 접두어 | 범위 | 개수 |
|---|---|---|
| `fs-page__` | 화면 전체 컨테이너 | 1 |
| `fs-status-tabs__` | 상태 탭 · [신규 서비스 신청] 버튼 | 3 |
| `fs-filter__` | 조회 필터 13개 항목 | 13 |
| `fs-dashboard__` | 엑셀 다운로드 버튼 등 | 2 |
| `fs-table__` | 테이블 루트 + 행/상세버튼(PK 포함) | 21 (행 10건 기준) |
| `fs-new__` | 신규 서비스 신청 팝업 | 19 |

## 파일 구성 — testid 는 한 파일에만

```
pages/field_service_page.py     testid 가 적히는 유일한 곳
  ├─ FieldServicePage           목록 화면 (진입 · 필터 · 테이블)
  └─ NewServicePopup            신규 서비스 신청 팝업

test_field_service.py           TC 본문. testid 가 한 번도 나오지 않는다
```

**왜 나눴나** — 시범 단계라 testid 이름이 바뀔 수 있습니다. 테스트 본문에 흩뿌려두면 이름이 바뀔 때 고칠 곳이
여러 곳이 되고, 그중 하나를 놓치면 **테스트는 통과하는데 한 군데만 이상하게 구는** 상태가 됩니다.
Page Object 에 모아두면 바뀌어도 고칠 곳이 한 군데입니다.

다만 이름이 바뀌는 것보다 더 중요한 이유가 있습니다 — **"이 요소를 어떻게 읽어야 하는가"라는 지식을 한 곳에 두는 것**입니다.
결과 목록을 읽는 방법(아래 "겪은 문제 ②")이 TC 마다 갈리면, 그중 하나가 위양성이 되어도 셀렉터 이름은 멀쩡해서
아무도 눈치채지 못합니다. `row_ids()` 하나만 두면 TC 가 읽는 방법을 고를 여지 자체가 없습니다.

팝업을 `FieldServicePage` 안에 두지 않고 별도 클래스로 뺀 이유는, 팝업이 **페이지가 아니라 그 탭 안에서 열리는 것**이라
같은 층에 두면 계층이 어긋나기 때문입니다. `fs.open_new_service_popup()`이 `NewServicePopup`을 돌려주는 구조라
"목록 화면에서 팝업으로 들어간다"는 관계가 코드에 그대로 드러납니다.

## 겪은 문제 ① — 메뉴 이름이 "현장 서비스 관리"가 아니다

첫 실행에서 **5건 전부 진입 단계에서 30초 타임아웃**이 났습니다(pytest 는 ERROR, Allure 는 broken).

```
TimeoutError: Locator.click: Timeout 30000ms exceeded.
Call log:
  - waiting for get_by_role("link", name="현장 서비스 관리")
```

GNB 를 직접 열어 덤프해보니 하위 메뉴 이름이 달랐습니다.

```
/car_maintenance      정비 서비스
/v2/field-service     현장 서비스        ← 이것
```

**읽는 법** — 에러 로그가 `waiting for get_by_role(...)`에서 멈춰 있으면 "요소를 찾았는데 못 눌렀다"가 아니라
**"찾지도 못했다"**는 뜻입니다. 대기를 늘리거나 재시도를 넣어도 안 풀립니다. 셀렉터가 화면에 실제로 있는지부터 봅니다.

`exact=True`를 붙인 이유는 나중에 `현장 서비스 xxx` 같은 항목이 생겼을 때입니다 —
`get_by_role`의 `name`은 기본이 부분 일치라 둘 다 잡혀서 strict mode 위반이 납니다.

```python
self.page.locator("a").filter(has_text=re.compile(r"^차량관리$")).click()
self.page.get_by_role("link", name="현장 서비스", exact=True).click()
```

상위 메뉴 `차량관리`를 `^...$`로 고정하는 것도 같은 이유입니다 — 그 아래에 `차량 관리`라는 항목이 따로 있습니다.

## 겪은 문제 ② — 테이블이 보이는 것과 결과가 채워지는 것은 다른 시점

메뉴 이름을 고치자 이번엔 TC-003 만 실패했습니다.

```
AssertionError: [FAIL] 조회된 행이 0건입니다
assert []
```

`wait_loaded()`가 `fs-table__root` 가시성만 보고 빠져나오고 있었습니다. 실제로 재보니:

```
fs-page__root  보임: +0.19s
fs-table__root 보임: +0.24s   ← 여기서 통과했다
  이 시점 행 개수: 0
첫 행 등장:      +0.38s        ← 0.14초 뒤
3초 뒤 행 개수: 10
```

이 화면에는 **스피너가 없습니다**(`.spinner`, `[class*=loading]`, `[class*=skeleton]` 전부 0개).
기다릴 로딩 표시가 없어서 **결과 자체**를 기다려야 합니다.

### 왜 "행이 하나라도 생기면 통과"로 하지 않았나

두 가지가 걸립니다.

| | 문제 |
|---|---|
| 빈 결과가 정상인 검색 | 행이 영원히 안 생겨서 30초 타임아웃. 조건에 맞는 건이 없는 검색은 정상 동작이다 |
| 검색으로 목록을 다시 그릴 때 | 옛 행이 남아 있는 순간이 있어서, 행 개수만 보면 **갱신 전 목록**을 읽고 지나간다 |

그래서 **행 PK 목록(또는 빈 상태)이 연속 2회 같을 때**만 완료로 봅니다 — `wait_table_settled()`.
`cur != prev`로 판정하지 않는 것과 같은 이유입니다(다시 그리는 동안의 빈 목록도 `[] != prev`라 참이 됩니다).

```python
# 브라우저 안에서 평가한다 - 폴링 왕복이 없다
self.page.wait_for_function(..., polling=300, timeout=timeout_ms)
```

직전 호출이 남긴 스냅샷을 매번 지우고 시작합니다. 화면 이동은 페이지가 새로 떠서 상관없지만
**검색은 페이지가 그대로**라, 안 지우면 첫 샘플에서 곧바로 통과해버립니다.

### 이 대기의 한계 — 창을 좁힐 뿐 없애지 못한다

서버 응답이 폴링 간격 두 번(약 0.6초)보다 느리면 **옛 목록을 두 번 연속 읽고** "안정됐다"고 볼 수 있습니다.
갱신 전후를 구분해야 하는 TC 는 여기에 기대지 말고 본문에서 직접 대조해야 합니다.
docstring 에도 같은 내용을 적어두었습니다 — 주석을 코드보다 세게 쓰면 다음 사람이 그 위에 검증을 더 얹게 됩니다.

## 빈 결과일 때의 화면 구조

없는 차량번호로 조회해서 확인했습니다.

```
inbox

데이터가 없습니다

새 항목을 추가해 주세요
```

- 행이 0개일 뿐 아니라 **`tbody` 자체가 그려지지 않습니다**
- 이 안내 영역에는 **testid 가 없습니다** — 그래서 문구(`EMPTY_TEXT`)로 판정합니다

`is_empty_result()`를 따로 둔 이유가 여기 있습니다. **행 0개만으로는 "빈 결과"와 "아직 그리는 중"을 구분할 수 없습니다.**

| 상태 | 행 개수 | `데이터가 없습니다` |
|---|---|---|
| 아직 그리는 중 | 0 | 없음 |
| 빈 결과(정상) | 0 | 있음 |

## `_find_hidden` — 빠진 항목을 한 번에 다 보고한다

필터 13개·팝업 15개처럼 항목이 많은 TC 는 하나 발견하고 멈추면 원인 파악이 느립니다.
전부 훑어서 이름으로 모아 보고합니다.

```python
first_label, first_attr = fields[0]
expect(getattr(owner, first_attr)).to_be_visible()   # 렌더 완료를 여기서 보장
return [label for label, attr in fields if not getattr(owner, attr).is_visible()]
```

**첫 항목만 `expect`인 이유** — `is_visible()`은 재시도를 안 합니다. 아직 안 그려진 화면에 대고 쓰면
**전부 "없음"으로 나와서 13개가 다 빠진 것처럼 보고**됩니다. 하나를 `expect`로 기다려 렌더가 끝난 것을
확인한 뒤 나머지를 즉시 읽습니다. 13개를 전부 `expect`로 감싸면 없는 항목마다 타임아웃을 다 기다립니다.

이건 CLAUDE.md 의 "부정 검증 앞에 긍정 검증을 둔다"와 같은 구조입니다 —
앞의 `expect`가 하한 역할을 해서, 화면을 못 읽으면 "빠진 항목 없음"으로 통과하는 일이 없습니다.

## 안전장치 — `[신청 완료]`는 절대 누르지 않는다

팝업의 `fs-new__submit-button`은 **존재·활성 확인까지만** 합니다. 누르면 dev 에 실제 신청 건이 생성됩니다.

"어차피 유효성 검사에서 막히겠지" 하고 눌렀다가 **안 막혀서 데이터가 생긴 사례**가 있습니다.
막아주는 것 자체가 검증 대상이라, 회귀가 나면 그대로 데이터가 만들어집니다.
검증하려면 누르는 대신 **쓰기 요청을 서버에 닿기 전에 끊는** 방법을 써야 하는데, 지금 TC 범위에는 넣지 않았습니다.

`[목록에 추가]`(`add_to_list_button`)는 팝업 안에서만 일어나는 동작이라 눌러도 안전합니다.

## 이 화면 때문에 고친 공통 코드

`conftest.py`의 실패 증거 첨부가 `when == "call"`만 보고 있어서, **fixture 진입 실패(위 문제 ①)에는
스크린샷이 하나도 안 남았습니다.** 리포트를 열어도 왜 못 눌렀는지 알 수 없어서 브라우저를 따로 띄워야 했습니다.

```python
- if rep.when == "call" and rep.failed:
-     page = item.funcargs.get("logged_in_page")
+ if rep.when in ("setup", "call") and rep.failed:
+     page = getattr(item, "_page", None)
```

**조건만 넓혀서는 안 붙습니다.** `item.funcargs`에는 테스트 함수가 직접 요청한 fixture 만 올라오는데,
이 파일은 `fs`만 받고 `logged_in_page`는 `fs`가 대신 받는 구조라 `None`이 나옵니다.
콘솔 로그와 같은 방식으로 `logged_in_page` fixture 가 `request.node._page`에 달아두게 했습니다.

첨부 이름에는 단계를 넣었습니다(`사전조건(setup) 실패 시점 화면`) — 보는 사람이
"검증하다 틀린 것"과 "검증까지 가지도 못한 것"을 구분해야 하기 때문입니다.

## 아직 안 한 것

- **엑셀 TC 문서가 없습니다.** TC ID·번호를 코드에서 임시로 붙였습니다. 문서가 나오면 맞춰야 합니다.
- **`request_rows`의 testid 는 미실측입니다.** 팝업에서 [목록에 추가]로 1건 담은 뒤 실제 이름을 확인해야 합니다
  (`fs-new__request-list-row--` 는 추정). 지금 TC 는 이 속성을 쓰지 않습니다.
- **동작 검증 TC 가 없습니다.** 상태 탭 필터, 조회 필터 적용 결과, 정렬, 페이지네이션, 작업 상세 팝업은
  전부 노출 확인 범위 밖입니다. 필터 TC 를 쓸 때는 CLAUDE.md 의 "필터·검색 결과는 한 방향만 보면 반쪽이다"를

  탭 TC 를 쓸 때 시작 앵커 정규식(`^완료`)이 필요한지 확인해야 합니다.
