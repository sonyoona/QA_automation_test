## 이 화면만 다른 점 — testid 가 붙어 있다

다른 화면들(모니터, 차량관리 수정 모달 등)은 `label` 텍스트나 `div.column` 같은 구조로 요소를 찾아야 했습니다.
현장 서비스는 프론트에서 시범적으로 `data-testid`를 붙여둔 페이지라, 셀렉터를 전부 testid 로 잡을 수 있습니다.

2026-09-07 실측 기준 **목록 40개 + 신규 서비스 신청 팝업 19개 = 59개**가 붙어 있고,
테이블 행·액션 버튼에는 PK 까지 들어 있습니다(`fs-table__row--10679`, `fs-table__action-btn--10679`).
액션 버튼은 행 맨 오른쪽 **액션 컬럼**의 버튼이고, 라벨이 **행 상태에 따라 [수정]/[상세] 로 갈립니다**

## 파일 구성 — testid 는 한 파일에만

```
pages/field_service_page.py     testid 가 적히는 유일한 곳
  ├─ FieldServicePage           목록 화면 (진입 · 필터 · 테이블)
  └─ NewServicePopup            신규 서비스 신청 팝업

test_field_service.py           TC 본문. testid 가 한 번도 나오지 않는다
```

**왜 나눴나** — 시범 단계라 testid 이름이 바뀔 수 있습니다. 테스트 본문에 흩뿌려두면 이름이 바뀔 때 고칠 곳이
여러 곳이 되고, 그중 하나를 놓치면 **테스트는 통과하는데 한 군데만 이상하게 구는** 상태가 됩니다.
Page Object 에 모아두면 바뀌어도 고칠 곳이 한 군데입니다.

다만 이름이 바뀌는 것보다 더 중요한 이유가 있습니다 — **"이 요소를 어떻게 읽어야 하는가"라는 지식을 한 곳에 두는 것**입니다.
결과 목록을 읽는 방법(아래 "겪은 문제 ②")이 TC 마다 갈리면, 그중 하나가 위양성이 되어도 셀렉터 이름은 멀쩡해서
아무도 눈치채지 못합니다. `row_ids()` 하나만 두면 TC 가 읽는 방법을 고를 여지 자체가 없습니다.

팝업을 `FieldServicePage` 안에 두지 않고 별도 클래스로 뺀 이유는, 팝업이 **페이지가 아니라 그 탭 안에서 열리는 것**이라
같은 층에 두면 계층이 어긋나기 때문입니다. `fs.open_new_service_popup()`이 `NewServicePopup`을 돌려주는 구조라
"목록 화면에서 팝업으로 들어간다"는 관계가 코드에 그대로 드러납니다.

## 겪은 문제 ① — 메뉴 이름이 "현장 서비스 관리"가 아니다

첫 실행에서 **5건 전부 진입 단계에서 30초 타임아웃**이 났습니다(pytest 는 ERROR, Allure 는 broken).

```
TimeoutError: Locator.click: Timeout 30000ms exceeded.
Call log:
  - waiting for get_by_role("link", name="현장 서비스 관리")
```

GNB 를 직접 열어 덤프해보니 하위 메뉴 이름이 달랐습니다.

```
/car_maintenance      정비 서비스
/v2/field-service     현장 서비스        ← 이것
```

**읽는 법** — 에러 로그가 `waiting for get_by_role(...)`에서 멈춰 있으면 "요소를 찾았는데 못 눌렀다"가 아니라
**"찾지도 못했다"**는 뜻입니다. 대기를 늘리거나 재시도를 넣어도 안 풀립니다. 셀렉터가 화면에 실제로 있는지부터 봅니다.

`exact=True`를 붙인 이유는 나중에 `현장 서비스 xxx` 같은 항목이 생겼을 때입니다 —
`get_by_role`의 `name`은 기본이 부분 일치라 둘 다 잡혀서 strict mode 위반이 납니다.

```python
self.page.locator("a").filter(has_text=re.compile(r"^차량관리$")).click()
self.page.get_by_role("link", name="현장 서비스", exact=True).click()
```

상위 메뉴 `차량관리`를 `^...$`로 고정하는 것도 같은 이유입니다 — 그 아래에 `차량 관리`라는 항목이 따로 있습니다.

## 겪은 문제 ② — 테이블이 보이는 것과 결과가 채워지는 것은 다른 시점

메뉴 이름을 고치자 이번엔 TC-003 만 실패했습니다.

```
AssertionError: [FAIL] 조회된 행이 0건입니다
assert []
```

`wait_loaded()`가 `fs-table__root` 가시성만 보고 빠져나오고 있었습니다. 실제로 재보니:

```
fs-page__root  보임: +0.19s
fs-table__root 보임: +0.24s   ← 여기서 통과했다
  이 시점 행 개수: 0
첫 행 등장:      +0.38s        ← 0.14초 뒤
3초 뒤 행 개수: 10
```

이 화면에는 **스피너가 없습니다**(`.spinner`, `[class*=loading]`, `[class*=skeleton]` 전부 0개).
기다릴 로딩 표시가 없어서 **결과 자체**를 기다려야 합니다.

### 왜 "행이 하나라도 생기면 통과"로 하지 않았나

두 가지가 걸립니다.

| | 문제 |
|---|---|
| 빈 결과가 정상인 검색 | 행이 영원히 안 생겨서 30초 타임아웃. 조건에 맞는 건이 없는 검색은 정상 동작이다 |
| 검색으로 목록을 다시 그릴 때 | 옛 행이 남아 있는 순간이 있어서, 행 개수만 보면 **갱신 전 목록**을 읽고 지나간다 |

그래서 **행 PK 목록(또는 빈 상태)이 연속 2회 같을 때**만 완료로 봅니다 — `wait_table_settled()`.
`cur != prev`로 판정하지 않는 것과 같은 이유입니다(다시 그리는 동안의 빈 목록도 `[] != prev`라 참이 됩니다).

```python
# 브라우저 안에서 평가한다 - 폴링 왕복이 없다
self.page.wait_for_function(..., polling=300, timeout=timeout_ms)
```

직전 호출이 남긴 스냅샷을 매번 지우고 시작합니다. 화면 이동은 페이지가 새로 떠서 상관없지만
**검색은 페이지가 그대로**라, 안 지우면 첫 샘플에서 곧바로 통과해버립니다.

### 이 대기의 한계 — 창을 좁힐 뿐 없애지 못한다

서버 응답이 폴링 간격 두 번(약 0.6초)보다 느리면 **옛 목록을 두 번 연속 읽고** "안정됐다"고 볼 수 있습니다.
갱신 전후를 구분해야 하는 TC 는 여기에 기대지 말고 본문에서 직접 대조해야 합니다.
docstring 에도 같은 내용을 적어두었습니다 — 주석을 코드보다 세게 쓰면 다음 사람이 그 위에 검증을 더 얹게 됩니다.

### 2026-09-08 — 그 한계가 정확히 그대로 터졌다 (591건을 0건으로 읽었다)

TC-003 이 또 `조회된 행이 0건입니다` 로 실패했습니다. 이번엔 실패 메시지에 화면 상태가 함께 남아 있었습니다.

```
빈결과안내=True / 상태탭='전체\n대기\n배정완료\n완료\n취소\n작업불가'
표='inbox\n\n데이터가 없습니다\n\n새 항목을 추가해 주세요'
```

**사람이 같은 화면을 열어보니 총 591건이 정상 조회됐습니다.** 즉 "dev 데이터가 비었다" 가 아니라
**데이터가 도착하지 않은 화면을 다 그려진 것으로 읽은 것**이었습니다.

`wait_table_settled()`는 빈 상태 안내(`데이터가 없습니다`)가 연속 2회 보이면 완료로 인정합니다 —
빈 결과가 정상인 검색을 기다려주려고 그렇게 만든 것인데, **데이터가 안 온 화면도 똑같이 생겼습니다.**
이 대기 하나로는 둘을 절대 못 가릅니다.

**가르는 신호는 상태 탭 배지였습니다.** 정상 화면은 `전체 591 · 대기 70 · 배정완료 95 …` 처럼
숫자가 붙는데, 실패한 실행에서는 **탭 이름만 있고 숫자가 없었습니다.** 배지는 서버 응답이 와야
채워지므로, 그게 "데이터 도착" 의 유일한 신호입니다.

```python
expect(self.table_root).to_be_visible()
self.wait_table_settled()          # 빈 상태를 '다 그려짐' 으로 인정 -> 0건으로 통과
```
```python
expect(self.table_root).to_be_visible()
self.wait_status_counts()          # 배지에 숫자가 들어올 때까지 = 데이터 도착
self.wait_table_settled()
```

데이터가 끝내 안 오면 이제 여기서 **명시적으로 실패**합니다(세션 끊김·API 실패 의심 메시지).
조용히 0건으로 통과하는 것보다 낫습니다 — 특히 TC-003 은 `assert row_ids` 하한이 있어서 그나마
실패로 드러났지만, **"없어야 한다" 를 보는 TC 였다면 그대로 초록불**이 됐을 자리입니다.

**남은 의심 — 왜 데이터가 안 왔나.** 실행 당시 같은 계정으로 브라우저에 로그인해 있었다면
세션이 그쪽으로 넘어갑니다(CLAUDE.md — 계정당 단일 세션). 나머지 4건이 통과한 것도 이 가설과
맞습니다: 그 TC 들은 **요소 노출만** 보고 데이터를 읽지 않아서, 세션이 끊겨도 화면 껍데기만으로
통과합니다. 즉 **"4건 통과" 는 세션이 살아 있었다는 근거가 아닙니다.**

### 같은 구멍이 상태 탭 클릭에서 또 열렸다 (2026-09-09 실측)

위 대책(`wait_status_counts` 를 앞에 세우기)은 **화면 진입** 때만 듣습니다. 상태 탭 클릭에는
전혀 듣지 않는데, 이유가 이겁니다 — **배지는 탭을 눌러도 지워지지 않습니다.** 진입할 때 전 탭
분이 한꺼번에 채워지고 그대로 남아 있어서, 탭을 누른 직후에도 `전체 592 · 대기 70 · …` 이
멀쩡히 보입니다. 즉 그 자리에서 배지는 "데이터가 도착했다" 를 알려주는 신호가 아닙니다.

전체 실행(61건)에서 TC-260907-006 두 건이 이렇게 깨졌습니다.

```
[FAIL] [대기] 탭 배지는 70건인데 조회된 행이 0건이다 - 데이터가 없는 게 아니라 목록을 못 읽은 것이다
        행수=0 / 빈결과안내=True
        상태탭='전체 | 592 | 대기 | 70 | 배정완료 | 96 | 완료 | 226 | 취소 | 180 | 작업불가 | 20'
        표='inbox\n\n데이터가 없습니다\n\n새 항목을 추가해 주세요'
```

배지에는 숫자가 다 있는데 표만 빈 상태입니다. 탭을 누르면 서버 응답을 기다리는 동안 표가
**스피너가 아니라 "데이터가 없습니다" 안내**를 그리고, 그게 폴링 두 번(0.6초)보다 오래 남으면
`wait_table_settled()` 가 `__EMPTY__` 를 연속 2회 읽고 "다 그려졌다" 로 통과시킵니다.

**연속 2회 규칙이 무엇을 막고 무엇을 못 막는지가 여기서 갈립니다.**

| 속는 대상 | 연속 2회로 막히나 |
|---|---|
| 갱신 전 **옛 목록** | 막힌다 — 곧 다른 값으로 바뀌므로 2회 연속이 안 된다 |
| **빈 상태** | 못 막는다 — 가만히 있으면 2회 연속 같은 값이다 |

같은 실행에서 [완료]·[취소]·[작업불가] 는 통과했습니다. 코드가 아니라 **그날 그 순간의 응답
속도**가 가른 것이라, 통과한 쪽이 안전하다는 뜻이 아닙니다. `test_status_tab_filters_rows`
(TC-260907-007)도 같은 구멍 위에 있었고 그날은 운이 좋았을 뿐입니다.

**고친 방법 — 배지를 "도착 신호" 가 아니라 "행이 있어야 하는가" 의 근거로 쓴다.**

배지가 0 보다 크면 그 탭 1페이지에는 반드시 행이 있습니다. 그러면 표의 "데이터가 없습니다" 는
결과가 아니라 아직 안 온 것이므로, 빈 상태를 완료로 인정하면 안 됩니다. 그 판단을
`wait_table_settled(allow_empty=...)` 로 넘깁니다.

```python
# 전 - 빈 상태를 늘 완료로 인정한다
self.status_tab(name).click()
self.wait_table_settled()
```
```python
# 후 - 배지가 0 이 아니면 행이 붙을 때까지 기다린다
self.status_tab(name).click()
expected = self.status_tab_count(name)
self.wait_table_settled(allow_empty=(expected == 0))
```

- 배지가 0 인 탭은 그대로 빈 상태를 인정합니다 - 진짜 0건인 탭까지 타임아웃시키면 안 됩니다.
- 끝내 행이 안 붙으면 30초 뒤 `[FAIL] 행이 있어야 하는 자리인데 끝내 안 붙었다` 로 끊습니다.
  화면 상태 요약이 함께 붙어서, 세션 끊김인지 진짜 회귀인지 리포트만 보고 가릅니다.

  생기면 이 전제가 깨질 수 있는데, 그때는 조용히 통과하지 않고 타임아웃으로 드러납니다.

**배운 것 - "이 대기가 A 를 막아준다" 를 상황을 빼고 적으면 안 된다.** 위 2026-09-08 대책은
사실 "화면 진입에서는" 이라는 단서가 붙은 것이었는데 그걸 안 적어서, 같은 구멍이 다른 자리에
그대로 남아 있는 것을 못 봤습니다.

## `_find_hidden` — 빠진 항목을 한 번에 다 보고한다

필터 13개·팝업 15개처럼 항목이 많은 TC 는 하나 발견하고 멈추면 원인 파악이 느립니다.
전부 훑어서 이름으로 모아 보고합니다.

```python
first_label, first_attr = fields[0]
_expect_rendered(getattr(owner, first_attr), f"첫 항목 '{first_label}'")   # 렌더 완료를 여기서 보장
return [label for label, attr in fields if not getattr(owner, attr).is_visible()]
```

**첫 항목만 `expect`인 이유** — `is_visible()`은 재시도를 안 합니다. 아직 안 그려진 화면에 대고 쓰면
**전부 "없음"으로 나와서 13개가 다 빠진 것처럼 보고**됩니다. 하나를 `expect`로 기다려 렌더가 끝난 것을
확인한 뒤 나머지를 즉시 읽습니다. 13개를 전부 `expect`로 감싸면 없는 항목마다 타임아웃을 다 기다립니다.

이건 CLAUDE.md 의 "부정 검증 앞에 긍정 검증을 둔다"와 같은 구조입니다 —
앞의 `expect`가 하한 역할을 해서, 화면을 못 읽으면 "빠진 항목 없음"으로 통과하는 일이 없습니다.

### 2026-09-08 — 그 첫 항목만 이름 없이 실패하고 있었다

원래는 `expect(...).to_be_visible()`을 그냥 부르고 있었습니다. **나머지 12개는 `hidden` 목록에
한글 이름으로 보고되는데, 하필 대표로 기다리는 첫 항목만** Playwright 기본 메시지
(`Locator expected to be visible` + testid)로 끝나서 **리포트만 봐서는 그게 어느 필터인지
알 수 없었습니다.** 검증 자체는 옳게 돌고 있었고 깨진 건 실패 메시지 쪽입니다.

`_expect_rendered(locator, what)`으로 빼서 한글 이름을 담아 다시 던지게 했습니다. 헬퍼로 뺀 이유는
같은 요령("대표 하나를 기다린 뒤 나머지를 훑는다")을 TC-260907-003 도 쓰기 때문입니다 — 한 줄짜리를
감싼 게 아니라 **대기 + 실패 메시지 변환이라는 요령**이 붙어 있어서, CLAUDE.md 의 헬퍼 추출 기준
두 번째 줄에 해당합니다.

## TC-260907-003 — testid 존재만 보면 세 가지가 안 보인다

처음엔 이렇게 썼습니다. `count() == 0` 인 행이 없으면 통과입니다.

|---|---|
| 이 버튼이 무엇인지 아무도 몰랐다 | 코드·노트가 "상세 버튼" 이라 부르고 있었다. 라벨을 한 번도 안 봤으니 틀린 이름이 유지됐다 |

지금은 **노출 + 라벨**까지 봅니다. `expect`를 행마다 걸지 않고 `_expect_rendered`로 첫 행만 기다린 뒤
나머지를 훑는 것은 `_find_hidden`과 같은 이유입니다 — 이상한 행을 **한 번에 다 모아서** 보고하기 위해서입니다.

```python
_expect_rendered(fs.row_action_button(row_ids[0]), f"첫 행({row_ids[0]})의 액션 버튼")
for row_id in row_ids:
    ...
    label = button.inner_text().strip()

```

### 라벨은 한 가지가 아니었다 — 상태에 따라 [수정]/[상세]

라벨을 확인하러 화면을 열었더니 **한 컬럼 안에 두 종류가 섞여** 있었습니다(2026-09-08 실측).

처음엔 `{"수정", "상세"}` 로 **둘 중 하나인지까지만** 봤습니다 — 라벨이 두 종류라는 것만 눈으로
봤을 뿐, 상태와의 대응은 근거가 없었기 때문입니다. 그 상태로는 **"완료 건에 [수정]이 떠 있다"**
같은 회귀(종료된 건을 고칠 수 있게 되는 것)를 못 잡습니다.

[전체] 탭 1페이지에는 대기·배정완료·완료만 올라와서 취소·작업불가가 미실측으로 남았고,
그래서 **상태 탭을 하나씩 눌러 각 10행씩 총 50행**을 다시 떴습니다(2026-09-08).

| 행 상태 | 액션 버튼 | 표본 |
|---|---|---|
| 대기 · 배정완료 | **[수정]** | 각 10행 |
| 완료 · 취소 · 작업불가 | **[상세]** | 각 10행 |

**상태마다 라벨이 하나로 일정했습니다** — 한 상태에서 두 라벨이 섞이는 경우는 없었습니다.
"진행 중이면 고칠 수 있고([수정]), 끝난 건은 보기만 한다([상세])" 로 읽힙니다.

```python
expected = ACTION_LABEL_BY_STATUS.get(status)          # 지금은 5개 상태가 모두 들어 있다
if expected and label != expected:
    broken.append(f"{row_id}: 상태 {status!r} 인데 라벨이 {label!r} (기대 {expected!r})")
elif not expected and label not in ACTION_BUTTON_LABELS:
    broken.append(f"{row_id}: 미실측 상태 {status!r} 의 라벨이 {label!r}")
```

`elif` 쪽은 지금은 안 걸립니다 — 상태를 다 채웠기 때문입니다. **나중에 상태가 새로 생겼을 때를
위한 그물**로 남겨둡니다. 모르는 상태가 와도 라벨이 둘 중 하나이긴 한지는 봅니다.

**"끝난 건은 [상세]" 라는 규칙 자체는 여전히 기획서로 확인한 게 아닙니다.** 우리가 가진 건
일관된 관찰뿐입니다. 다만 그건 **관찰된 사실**이라, 어긋나면 화면이 바뀐 것이니
빨간불이 뜨는 게 맞습니다. 규칙이 원래 다른 것으로 확인되면 그때 대응표를 고칩니다.

**상태 컬럼은 헤더 텍스트로 찾습니다**(`column_index("상태")`). 실측 기준 헤더가 17개고 상태가 0번,
액션이 16번인데, 인덱스를 박으면 프론트가 컬럼을 하나 끼울 때 **예외가 아니라 빈 문자열**이 읽혀
조용히 지나갑니다. `print` 에는 관찰된 (상태, 라벨) 조합을 남겨서 실행 로그가 표본이 되게 했습니다.

★ 이 버튼은 **누르지 않습니다.** 수정 화면으로 들어가는 입구라, 노출·라벨 확인까지만 합니다.

맞는 라벨인지만 봅니다. 필터가 깨져 [대기] 탭에 완료 건이 섞여도 이 TC 는 통과하는데,

## TC-260907-007 — 필터는 두 방향을 같이 걸어야 한다

상태 탭이 "그 상태만" 조회하는지 보려면 한 방향으로는 부족합니다.

| 방향 | 무엇을 막나 | 이것만 걸면 |
|---|---|---|
| 결과 ⊆ 조건 | **섞임** — 다른 상태가 결과에 들어옴 | 필터가 **아무것도 안 돌려줘도**(0건) 통과 |
| 조건 ⊆ 결과 | **누락** — 그 상태인데 결과에 없음 | 필터가 **전부 돌려줘도** 통과 |

### 누락(②)을 볼 정답을 어디서 가져오는가

`assert` 를 쓰기 전에 **정답 출처부터** 정해야 합니다. 여기서는 화면 안에 있습니다 —
[전체] 탭 1페이지를 먼저 읽어 상태가 X 인 행 PK 를 모아두고, [X] 탭 결과에 그것들이
다 들어 있는지 봅니다.

```python
fs.click_status_tab(ALL_TAB)
all_statuses = fs.row_statuses()
expected_ids = [i for i in all_ids if all_statuses[i] == tab]   # 정답 출처
...
missing = [i for i in expected_ids if i not in row_ids]
```

**전제 — 두 목록의 정렬 기준이 같다는 것.** 목록 조회 API 가
`sort=requestedDateTime,desc`(작업신청일 내림차순)로 나가는 것을 2026-09-08 에 확인했습니다.
그러면 [전체] 1페이지에 있는 X 행은 반드시 [X] 탭 1페이지 안에 있습니다 — 전체에서 그 행보다
위에 있는 행이 9개 이하이므로, X 중에서도 9번째 안이기 때문입니다.

정렬 기본값이 바뀌면 이 전제가 깨져 **거짓 실패**가 납니다. 그래서 실패 메시지에
`정렬 전제(작업신청일 내림차순)가 깨졌을 수도 있다` 를 넣어뒀습니다 — 이 문구가 보이면
필터가 아니라 정렬부터 확인합니다.

### 배지가 0이라는 말도 그냥 믿지 않는다

```python
if total == 0:
    assert not expected_ids, f"[FAIL] [{tab}] 탭 배지는 0건인데 [전체] 탭에는 그 상태 행이 있다: ..."
    pytest.skip(...)
```

배지가 0 이면 검증할 행이 없어 skip 이지만, **[전체] 탭에서 그 상태를 봤다면 모순**입니다.
skip 하기 전에 그것부터 겁니다 — 안 그러면 필터가 그 상태를 통째로 잃어버려도
"건이 없나 보다" 하고 노란불에 묻힙니다.

### 이 TC 도 한 번 깨봤다

두 방향이 각각 실제로 실패하는지 따로 확인했습니다.

| 깬 것 | 결과 |
|---|---|
| ① 비교 대상을 `tab` → `"대기"` 로 | 대기 외 4개 탭이 빨간불 |
| ② 정답 출처를 `== tab` → `!= tab` 으로 | `[전체] 탭에서 상태가 '대기' 이던 행이 [대기] 탭 결과에 없다: [...]` |

**방향이 둘이면 두 번 깨봐야 합니다.** 한쪽만 확인하면 나머지 한쪽이 위양성인 채로
남을 수 있습니다.

## 팝업 TC 는 `assert` 를 `close()` 보다 먼저 둔다

처음엔 반대로 썼습니다 — 확인이 끝났으니 팝업을 닫고 나서 판정하는 게 정리 순서로 자연스러워 보였습니다.

```python
hidden = _find_hidden(popup, NEW_POPUP_FIELDS)
popup.close()
assert not hidden, ...
```

**그러면 실패했을 때 증거가 사라집니다.** 실패 스크린샷을 붙이는 훅은 fixture teardown **전에**,
그 시점의 화면을 찍습니다(`conftest.py` 의 `pytest_runtest_makereport`). 팝업을 먼저 닫으면
*"메모 필드가 안 보인다"* 로 실패했는데 리포트에는 **목록 화면만** 남습니다.

```python
hidden = _find_hidden(popup, NEW_POPUP_FIELDS)
assert not hidden, ...      # 실패하면 여기서 끝 -> 팝업이 열린 화면이 찍힌다
popup.close()
```

### "팝업을 안 닫으면 다음 TC 가 영향받는다" 는 걱정은 여기선 성립하지 않는다

`logged_in_page` 가 **function scope** 라 테스트마다 컨텍스트를 새로 만들고 끝나면 닫습니다.
팝업이 열린 채 끝나도 그 탭째 사라지므로 다음 TC 에 남지 않습니다.

**이걸 확인하지 않고 "테스트는 뒷정리를 해야 한다" 는 통념으로 순서를 정했던 것**이 원인이었습니다.
뒷정리가 필요한 구조인지 먼저 봤어야 합니다 — CLAUDE.md 의 "화면에 대한 사실은 실측으로만
단언한다" 는 코드를 읽을 때도 똑같이 적용됩니다.

★ TC-260907-005 의 `close()` 는 그대로 둡니다. 거긴 정리가 아니라 **"닫으면 목록으로 복귀하는가"
라는 검증 자체**라 위치가 의미를 갖습니다.

## 안전장치 — `[신청 완료]`는 절대 누르지 않는다

팝업의 `fs-new__submit-button`은 **존재·활성 확인까지만** 합니다. 누르면 dev 에 실제 신청 건이 생성됩니다.

"어차피 유효성 검사에서 막히겠지" 하고 눌렀다가 **안 막혀서 데이터가 생긴 사례**가 있습니다.
막아주는 것 자체가 검증 대상이라, 회귀가 나면 그대로 데이터가 만들어집니다.
검증하려면 누르는 대신 **쓰기 요청을 서버에 닿기 전에 끊는** 방법을 써야 하는데, 지금 TC 범위에는 넣지 않았습니다.

`[목록에 추가]`(`add_to_list_button`)는 팝업 안에서만 일어나는 동작이라 눌러도 안전합니다.

## 이 화면 때문에 고친 공통 코드

`conftest.py`의 실패 증거 첨부가 `when == "call"`만 보고 있어서, **fixture 진입 실패(위 문제 ①)에는
스크린샷이 하나도 안 남았습니다.** 리포트를 열어도 왜 못 눌렀는지 알 수 없어서 브라우저를 따로 띄워야 했습니다.

```python
- if rep.when == "call" and rep.failed:
-     page = item.funcargs.get("logged_in_page")
+ if rep.when in ("setup", "call") and rep.failed:
+     page = getattr(item, "_page", None)
```

**조건만 넓혀서는 안 붙습니다.** `item.funcargs`에는 테스트 함수가 직접 요청한 fixture 만 올라오는데,
이 파일은 `fs`만 받고 `logged_in_page`는 `fs`가 대신 받는 구조라 `None`이 나옵니다.
콘솔 로그와 같은 방식으로 `logged_in_page` fixture 가 `request.node._page`에 달아두게 했습니다.

첨부 이름에는 단계를 넣었습니다(`사전조건(setup) 실패 시점 화면`) — 보는 사람이
"검증하다 틀린 것"과 "검증까지 가지도 못한 것"을 구분해야 하기 때문입니다.

### 왜 `request_rows` 는 [목록에 추가]를 눌러야 잴 수 있나

신규 서비스 신청 팝업은 **한 번에 여러 건을 담아 한꺼번에 신청**하는 구조입니다.

```
서비스 정보 입력 → 업체·지점·차량 선택 → [목록에 추가] → 팝업 안 목록에 1행이 쌓인다
                                                    ↑ 반복해서 여러 건을 담을 수 있다
                                          → [신청 완료] 로 담긴 것을 한꺼번에 제출  ★ 누르지 않는다
```

`request_rows` 는 그 **팝업 안 목록의 행들**입니다. 팝업을 막 열었을 때는 목록이 비어 있어서
**그 행 요소가 DOM 에 아예 없습니다.** testid 는 존재하는 요소에서만 읽을 수 있으니, 1건을 담아
행을 만들어야 이름을 볼 수 있습니다.

### 재보니 — 접두어는 맞았고, 뒤에 붙는 값이 표와 달랐다

2026-09-08 실측(사람이 화면에서 직접 담아 확인).

```
fs-table__row--10679            ← 표: 서버가 준 그 건의 id
fs-new__request-list-row--0     ← 팝업 목록: 0 부터 세는 순번
fs-new__request-list-row--1
```

**아직 서버에 보내기 전이라 id 가 있을 수 없습니다.** 신청 건은 [신청 완료]를 눌러야 만들어지고,
그 전까지 이 목록은 화면 안에만 있는 임시 상태입니다. 그러니 뒤에 붙을 수 있는 값은 순번뿐입니다.

**그래서 이 번호는 신원이 아니라 위치입니다.** 중간 행을 지우면 뒤 행의 번호가 당겨집니다.

| 쓸 수 있는 것 | 쓰면 안 되는 것 |
|---|---|
| 개수 세기 (`to_have_count(2)`) | 조작 전후로 **같은 행** 다시 찾기 |
| "N 번째 담긴 행" 가리키기 (같은 렌더 안에서) | 지우기·순서 바꾸기를 사이에 두고 추적하기 |

CLAUDE.md "행 식별" 장의 순위표에서 **4순위(인덱스 — 같은 렌더 안에서만)** 에 해당합니다.
표 행은 1순위(PK 가 담긴 속성)인데, **같은 화면 안에서도 자리마다 등급이 다릅니다.**
testid 뒤에 숫자가 붙어 있다고 다 식별자가 아닙니다 — 무엇이 붙어 있는지 봐야 합니다.

**[목록에 추가]가 서버에 요청을 보내는지는 아직 확인 안 했습니다.** 팝업 안에서만 끝나는
동작으로 보고 있지만 그것도 관찰이지 증명은 아닙니다 — 자동화로 이 버튼을 쓰게 될 때
네트워크를 함께 보면 됩니다(그때 쓰기 요청을 서버에 닿기 전에 끊어두면 확인 자체도 안전합니다).

첫 행의 **글자가 완전히 같을 수 있습니다.** 그래서 `row_ids()` 로 식별자를 비교합니다.
