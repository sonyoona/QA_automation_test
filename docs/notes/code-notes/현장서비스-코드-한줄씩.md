## 2. import

```python
import allure
```

`@allure.title` · `@allure.label` 데코레이터를 쓰기 위한 것입니다. pytest 처럼 자동으로 발견되는
게 아니라 **이름을 직접 불러 쓰는** 도구라 import 가 필요합니다.

```python
import pytest
```

여기서는 **`@pytest.fixture` 하나** 때문에 필요합니다. 테스트 함수 자체는 `test_` 로 시작하기만
하면 pytest 가 알아서 찾으므로 import 가 필요 없습니다.

```python
from playwright.sync_api import Locator, Page, expect
```

셋의 역할이 다릅니다.

| 이름 | 쓰임 | 없으면 |
|---|---|---|
| `expect` | 재시도되는 검증 | 코드가 안 돎 |
| `Page` | 타입 어노테이션 (`logged_in_page: Page`) | 돌긴 함 |
| `Locator` | 타입 어노테이션 (`locator: Locator`) | 돌긴 함 |

뒤의 둘은 **동작에 영향이 없습니다.** "이 자리엔 이런 게 온다" 고 적어두는 것이고,
IDE 자동완성과 읽는 사람을 위한 것입니다.

```python
from pages.field_service_page import FieldServicePage
```

`pages` 폴더의 `field_service_page.py` 안에 있는 `FieldServicePage` 클래스를 가져옵니다.
**이 파일에 셀렉터가 한 글자도 안 나오는 이유**가 이것입니다 — 화면을 아는 일은 전부 저쪽이 합니다.

## 4. 상수

```python
ACTION_LABEL_BY_STATUS = {
    "대기": "수정",
    "배정완료": "수정",
    "완료": "상세",
    "취소": "상세",
    "작업불가": "상세",
}
```

**상태 → 버튼 라벨** 대응표(dict)입니다. 2026-09-08 실측값으로, 상태 탭 5개를 하나씩 눌러
각 10행씩 확인했습니다 — 진행 중이면 [수정], 끝난 건이면 [상세] 입니다.

```python
ACTION_BUTTON_LABELS = set(ACTION_LABEL_BY_STATUS.values())
```

위 dict 의 **값들만** 모아 중복을 없앤 집합 → `{"수정", "상세"}`. 직접 `{"수정","상세"}` 라고
또 적지 않고 **파생시킨 이유**는, 대응표에 상태를 추가할 때 이 줄을 같이 고치는 걸 잊을 수 없게
하려는 것입니다. **한쪽만 고쳐지는 상황을 애초에 못 만드는** 방식입니다.

```python
FILTER_FIELDS = [
    ("리셀러", "reseller_select"),
    ...
]
```

**(화면에 보이는 이름, 화면 객체의 속성명)** 짝의 목록입니다. 오른쪽이 문자열인 게 핵심인데,
이러면 `getattr` 로 꺼낼 수 있어서 13줄짜리 반복을 한 줄로 줄일 수 있습니다.

왼쪽의 한글 이름은 **실패 메시지에 찍히는 용도**입니다 —
`노출되지 않은 조회 필터 항목: ['리셀러', 'GPS 음영']` 처럼 나와야 리포트만 보고 알 수 있습니다.

## 5. `fs` fixture

```python
@pytest.fixture
def fs(logged_in_page: Page) -> FieldServicePage:
```

`@pytest.fixture` 를 붙이면 **테스트가 이름으로 요청할 수 있는 준비물**이 됩니다.
아래 테스트들이 `def test_xxx(fs)` 라고 쓰면 pytest 가 이 함수를 먼저 실행해 결과를 넣어줍니다.

`logged_in_page` 는 `conftest.py` 에 있는 다른 fixture 입니다. **fixture 가 fixture 를 받는**
구조라, 로그인 → 새 탭 → 화면 진입이 사슬로 이어집니다.

```python
    page_object = FieldServicePage(logged_in_page)
    page_object.goto()
    return page_object
```

화면 객체를 만들고 → 메뉴를 눌러 진입하고 → 돌려줍니다. 테스트 5개가 각각 이 fixture 를 받으므로
**테스트마다 새 탭에서 새로 진입**합니다(테스트 독립성).

진입을 fixture 에 둔 이유는 진입이 검증 대상이 아니라 **사전 조건**이기 때문입니다. 여기서 깨지면
pytest 가 `ERROR` 로 표시해서, 기능 검증 실패(`FAIL`)와 눈으로 구분됩니다.

## 6. `_expect_rendered`

```python
def _expect_rendered(locator: Locator, what: str) -> None:
```

이름 앞의 `_` 는 파이썬 관례로 **"이 파일 안에서만 쓰는 것"** 이라는 표시입니다(강제되진 않습니다).

```python
    try:
        expect(locator).to_be_visible()
    except AssertionError as e:
```

`expect(...).to_be_visible()` 은 **보일 때까지 재시도**하다가(기본 5초) 안 되면 `AssertionError`
를 냅니다. 그걸 붙잡습니다.

```python
        raise AssertionError(
            f"[FAIL] {what} 이(가) 끝내 노출되지 않아 나머지를 확인할 수 없다"
        ) from e
```

한글 이름을 담아 **다시 던집니다.** Playwright 기본 메시지는 셀렉터만 보여줘서, 리포트만 보면
그게 어느 항목인지 알 수 없기 때문입니다.

`from e` 가 중요합니다 — 원래 예외를 **원인으로 매달아** 둡니다. 리포트에 `위 예외가 원인이 되어…`
로 원본까지 같이 남아서, 한글 설명과 Playwright 의 상세 정보를 **둘 다** 볼 수 있습니다.
`from e` 를 빼면 원본이 사라집니다.

## 7. `_find_hidden`

```python
    first_label, first_attr = fields[0]
```

목록의 첫 짝을 두 변수로 **풀어 담습니다**(튜플 언패킹).
`("리셀러", "reseller_select")` → `first_label="리셀러"`, `first_attr="reseller_select"`.

```python
    _expect_rendered(getattr(owner, first_attr), f"첫 항목 '{first_label}'")
```

`getattr(owner, "reseller_select")` 는 `owner.reseller_select` 와 같습니다.
**속성명이 문자열로 들어 있을 때** 쓰는 방법입니다.

여기서 **대표 하나를 기다리는 게 이 함수의 핵심**입니다. 아래 `is_visible()` 은 재시도가 없어서,
아직 안 그려진 화면에 쓰면 **13개가 전부 "안 보임" 으로** 나옵니다.

```python
    return [label for label, attr in fields if not getattr(owner, attr).is_visible()]
```

리스트 컴프리헨션입니다. 풀어 쓰면 이렇습니다.

```python
    result = []
    for label, attr in fields:
        if not getattr(owner, attr).is_visible():
            result.append(label)
    return result
```

**전부 훑어서 모읍니다.** 하나 발견하고 멈추면 "리셀러가 없다" 만 알고 끝나는데, 모으면
"13개 중 5개가 없다 = 영역 자체가 안 떴다" 를 한 번에 압니다.

`expect` 를 13개에 다 걸지 않은 이유도 있습니다 — 없는 항목마다 5초씩 기다려서 느려집니다.

```python
    expect(fs.root).to_be_visible()
```

다섯 줄이 각각 영역 하나씩입니다. `fs.root` 는 `@property` 라 **부를 때마다 Locator 를 새로**

여긴 `_find_hidden` 을 안 쓰는데, **5개뿐이고 이름이 다 다른 것**이라 나열하는 편이 읽기 낫기
때문입니다.

## 9. TC-260907-002 — 조회 필터 항목

```python
    hidden = _find_hidden(fs, FILTER_FIELDS)
    assert not hidden, f"[FAIL] 노출되지 않은 조회 필터 항목: {hidden}"
```

`assert 조건, 메시지` — 조건이 **참이면 통과**하고, 거짓이면 그 메시지와 함께 실패합니다.
메시지는 **실패했을 때만** 나옵니다.

`not hidden` 은 **빈 리스트면 참**입니다(파이썬에서 빈 리스트는 거짓). 즉 "안 보이는 항목이
하나도 없어야 한다" 는 뜻입니다.

> **`assert not X` 를 읽는 법** — 그 리스트가 "없어야 정상" 인지 "있어야 정상" 인지로 갈립니다.
> `hidden`(안 보이는 항목)·`broken`(문제 행)은 **비어야** 정상이라 `not` 을 붙이고,
> `row_ids`(조회된 행)는 **있어야** 정상이라 그냥 씁니다.

## 10. TC-260907-003 — 행별 액션 버튼 (이 파일에서 가장 복잡한 것)

```python
    row_ids = fs.row_ids()
    assert row_ids, ( ... )
```

**하한**입니다. 이게 없으면 아래 `for` 문이 0번 돌아서 **검증이 통째로 사라진 채 통과**합니다.
2026-09-08 에 591건짜리 화면을 0건으로 읽었을 때 이 줄이 잡아냈습니다.

메시지에 `fs.state_summary()` 를 넣은 건, "0건" 이 세 가지 원인(실제로 없음 / 필터가 걸러냄 /
로딩·세션 실패)에서 똑같이 나오기 때문입니다. 값을 같이 안 남기면 리포트만 보고는 못 가릅니다.

```python
    _expect_rendered(fs.row_action_button(row_ids[0]), f"첫 행({row_ids[0]})의 액션 버튼")
    statuses = fs.row_statuses()
```

`_find_hidden` 과 **같은 요령**입니다 — 대표 하나를 기다린 뒤 나머지를 훑습니다.
`statuses` 는 `{"10682": "대기", "10680": "배정완료", ...}` 형태의 dict 입니다.

```python
    broken = []
    seen = []
```

`broken` 은 문제 있는 행, `seen` 은 관찰된 (상태, 라벨) 조합입니다. **바로 실패시키지 않고 모으는**
이유는 위와 같습니다 — 한 번에 다 보고합니다.

```python
        if not button.is_visible():
            broken.append(f"{row_id}: 버튼이 없거나 숨겨져 있음")
            continue
```

`continue` 는 이 행을 여기서 끝내고 다음 행으로 넘어가라는 뜻입니다. 버튼이 안 보이면 라벨을
읽어봐야 의미가 없습니다.

```python
        label = button.inner_text().strip()
```

`.strip()` 은 앞뒤 공백·줄바꿈 제거입니다. HTML 은 들여쓰기 때문에 `"\n  수정\n"` 처럼 오기 쉽습니다.

```python
        expected = ACTION_LABEL_BY_STATUS.get(status)
```

**`.get()` 과 `[...]` 의 차이가 여기서 핵심입니다.** `dict[key]` 는 없는 키면 에러가 나지만,
`.get()` 은 **`None` 을 돌려줍니다.** 나중에 상태가 새로 생겨 대응표에 없는 값이 와도 죽지 않습니다.

```python
        if expected and label != expected:
            broken.append(f"{row_id}: 상태 {status!r} 인데 라벨이 {label!r} (기대 {expected!r})")
        elif not expected and label not in ACTION_BUTTON_LABELS:
            broken.append(f"{row_id}: 미실측 상태 {status!r} 의 라벨이 {label!r}")
```

두 갈래입니다.

| 상황 | 검증 |
|---|---|
| 실측된 상태 (`expected` 가 있음) | 라벨이 **정확히 그것**인가 |
| 대응표에 없는 상태 (`expected` 가 `None`) | 라벨이 **둘 중 하나**이긴 한가 |

지금은 상태 5개를 다 채워서 아래쪽 갈래에 걸리는 행이 없습니다. **나중에 상태가 새로 생겼을
때를 위한 그물**로 남겨둔 것입니다.

`{label!r}` 의 `!r` 은 `repr()` 로 찍으라는 뜻입니다 — `수정` 이 아니라 `'수정'` 으로 따옴표까지
나옵니다. **빈 문자열이나 공백을 구분하려면 필수**입니다(`''` 와 `' '` 은 따옴표가 없으면
똑같아 보입니다).

```python
    print(f"[검증] ... {sorted(set(seen))}")
```

`set` 으로 중복 제거 → `sorted` 로 정렬합니다. 실행 로그가 **다음 실측의 표본**이 되게 남깁니다.

## 11. TC-260907-004 · 005 — 팝업

```python
    popup = fs.open_new_service_popup()
```

화면 객체가 **팝업 객체를 돌려줍니다.** "목록 화면에서 팝업으로 들어간다" 는 관계가 코드에
그대로 드러납니다.

```python
    hidden = _find_hidden(popup, NEW_POPUP_FIELDS)

    assert not hidden, f"[FAIL] 노출되지 않은 팝업 입력 항목: {hidden}"
    popup.close()
```

**`assert` 가 `close()` 보다 먼저인 것이 중요합니다.** 실패하면 `close()` 에 도달하지 않아
팝업이 열린 화면이 리포트에 첨부됩니다. 반대로 두면 "어느 필드가 안 보이는가" 로 실패했는데
스크린샷에는 목록 화면만 남습니다 — 자세한 경위는 `현장서비스-테스트-노트.md` 참고.

```python
    expect(popup.submit_button).to_be_visible()
```

★ [신청 완료] 버튼은 **있는지만** 봅니다. 화면 객체에 `submit_button`(요소)은 있지만
`submit()`(누르는 메서드)은 **일부러 안 만들었습니다** — 있으면 다음 사람이 씁니다.

```python
    popup.close()
    expect(fs.table_root).to_be_visible()
```

TC-005 의 `close()` 는 정리가 아니라 **검증 자체**입니다 — 닫은 뒤 목록이 돌아오는지까지 봐야
"닫기가 동작했다" 가 됩니다. 그래서 이 자리의 `close()` 는 위치를 바꾸면 안 됩니다.
