**옆 문서와 역할이 다릅니다.**

## 2. import

```python
import allure
```

`@allure.title` · `@allure.label` 데코레이터를 쓰기 위한 것입니다. pytest 처럼 자동으로 발견되는
게 아니라 **이름을 직접 불러 쓰는** 도구라 import 가 필요합니다.

```python
import pytest
```

여기서는 **`@pytest.fixture` 하나** 때문에 필요합니다. 테스트 함수 자체는 `test_` 로 시작하기만
하면 pytest 가 알아서 찾으므로 import 가 필요 없습니다.

```python
from playwright.sync_api import Locator, Page, expect
```

셋의 역할이 다릅니다.

| 이름 | 쓰임 | 없으면 |
|---|---|---|
| `expect` | 재시도되는 검증 | 코드가 안 돎 |
| `Page` | 타입 어노테이션 (`logged_in_page: Page`) | 돌긴 함 |
| `Locator` | 타입 어노테이션 (`locator: Locator`) | 돌긴 함 |

뒤의 둘은 **동작에 영향이 없습니다.** "이 자리엔 이런 게 온다" 고 적어두는 것이고,
IDE 자동완성과 읽는 사람을 위한 것입니다.

```python
from pages.field_service_page import FieldServicePage
```

`pages` 폴더의 `field_service_page.py` 안에 있는 `FieldServicePage` 클래스를 가져옵니다.
**이 파일에 셀렉터가 한 글자도 안 나오는 이유**가 이것입니다 — 화면을 아는 일은 전부 저쪽이 합니다.

## 4. 상수

```python
ACTION_LABEL_BY_STATUS = {
    "대기": "수정",
    "배정완료": "수정",
    "완료": "상세",
    "취소": "상세",
    "작업불가": "상세",
}
```

**상태 → 버튼 라벨** 대응표(dict)입니다. 2026-09-08 실측값으로, 상태 탭 5개를 하나씩 눌러
각 10행씩 확인했습니다 — 진행 중이면 [수정], 끝난 건이면 [상세] 입니다.

```python
ACTION_BUTTON_LABELS = set(ACTION_LABEL_BY_STATUS.values())
```

위 dict 의 **값들만** 모아 중복을 없앤 집합 → `{"수정", "상세"}`. 직접 `{"수정","상세"}` 라고
또 적지 않고 **파생시킨 이유**는, 대응표에 상태를 추가할 때 이 줄을 같이 고치는 걸 잊을 수 없게
하려는 것입니다. **한쪽만 고쳐지는 상황을 애초에 못 만드는** 방식입니다.

```python
FILTER_FIELDS = [
    ("리셀러", "reseller_select"),
    ...
]
```

**(화면에 보이는 이름, 화면 객체의 속성명)** 짝의 목록입니다. 오른쪽이 문자열인 게 핵심인데,
이러면 `getattr` 로 꺼낼 수 있어서 13줄짜리 반복을 한 줄로 줄일 수 있습니다.

왼쪽의 한글 이름은 **실패 메시지에 찍히는 용도**입니다 —
`노출되지 않은 조회 필터 항목: ['리셀러', 'GPS 음영']` 처럼 나와야 리포트만 보고 알 수 있습니다.

## 5. `fs` fixture

```python
@pytest.fixture
def fs(logged_in_page: Page) -> FieldServicePage:
```

`@pytest.fixture` 를 붙이면 **테스트가 이름으로 요청할 수 있는 준비물**이 됩니다.
아래 테스트들이 `def test_xxx(fs)` 라고 쓰면 pytest 가 이 함수를 먼저 실행해 결과를 넣어줍니다.

`logged_in_page` 는 `conftest.py` 에 있는 다른 fixture 입니다. **fixture 가 fixture 를 받는**
구조라, 로그인 → 새 탭 → 화면 진입이 사슬로 이어집니다.

```python
    page_object = FieldServicePage(logged_in_page)
    page_object.goto()
    return page_object
```

화면 객체를 만들고 → 메뉴를 눌러 진입하고 → 돌려줍니다. 테스트 5개가 각각 이 fixture 를 받으므로
**테스트마다 새 탭에서 새로 진입**합니다(테스트 독립성).

진입을 fixture 에 둔 이유는 진입이 검증 대상이 아니라 **사전 조건**이기 때문입니다. 여기서 깨지면
pytest 가 `ERROR` 로 표시해서, 기능 검증 실패(`FAIL`)와 눈으로 구분됩니다.

## 6. `_expect_rendered`

```python
def _expect_rendered(locator: Locator, what: str) -> None:
```

이름 앞의 `_` 는 파이썬 관례로 **"이 파일 안에서만 쓰는 것"** 이라는 표시입니다(강제되진 않습니다).

```python
    try:
        expect(locator).to_be_visible()
    except AssertionError as e:
```

`expect(...).to_be_visible()` 은 **보일 때까지 재시도**하다가(기본 5초) 안 되면 `AssertionError`
를 냅니다. 그걸 붙잡습니다.

```python
        raise AssertionError(
            f"[FAIL] {what} 이(가) 끝내 노출되지 않아 나머지를 확인할 수 없다"
        ) from e
```

한글 이름을 담아 **다시 던집니다.** Playwright 기본 메시지는 셀렉터만 보여줘서, 리포트만 보면
그게 어느 항목인지 알 수 없기 때문입니다.

`from e` 가 중요합니다 — 원래 예외를 **원인으로 매달아** 둡니다. 리포트에 `위 예외가 원인이 되어…`
로 원본까지 같이 남아서, 한글 설명과 Playwright 의 상세 정보를 **둘 다** 볼 수 있습니다.
`from e` 를 빼면 원본이 사라집니다.

## 7. `_find_hidden`

```python
    first_label, first_attr = fields[0]
```

목록의 첫 짝을 두 변수로 **풀어 담습니다**(튜플 언패킹).
`("리셀러", "reseller_select")` → `first_label="리셀러"`, `first_attr="reseller_select"`.

```python
    _expect_rendered(getattr(owner, first_attr), f"첫 항목 '{first_label}'")
```

`getattr(owner, "reseller_select")` 는 `owner.reseller_select` 와 같습니다.
**속성명이 문자열로 들어 있을 때** 쓰는 방법입니다.

여기서 **대표 하나를 기다리는 게 이 함수의 핵심**입니다. 아래 `is_visible()` 은 재시도가 없어서,
아직 안 그려진 화면에 쓰면 **13개가 전부 "안 보임" 으로** 나옵니다.

```python
    return [label for label, attr in fields if not getattr(owner, attr).is_visible()]
```

리스트 컴프리헨션입니다. 풀어 쓰면 이렇습니다.

```python
    result = []
    for label, attr in fields:
        if not getattr(owner, attr).is_visible():
            result.append(label)
    return result
```

**전부 훑어서 모읍니다.** 하나 발견하고 멈추면 "리셀러가 없다" 만 알고 끝나는데, 모으면
"13개 중 5개가 없다 = 영역 자체가 안 떴다" 를 한 번에 압니다.

`expect` 를 13개에 다 걸지 않은 이유도 있습니다 — 없는 항목마다 5초씩 기다려서 느려집니다.

때문입니다.

## 9. TC-260907-002 — 조회 필터 항목

```python
    hidden = _find_hidden(fs, FILTER_FIELDS)
    assert not hidden, f"[FAIL] 노출되지 않은 조회 필터 항목: {hidden}"
```

`assert 조건, 메시지` — 조건이 **참이면 통과**하고, 거짓이면 그 메시지와 함께 실패합니다.
메시지는 **실패했을 때만** 나옵니다.

`not hidden` 은 **빈 리스트면 참**입니다(파이썬에서 빈 리스트는 거짓). 즉 "안 보이는 항목이
하나도 없어야 한다" 는 뜻입니다.

> **`assert not X` 를 읽는 법** — 그 리스트가 "없어야 정상" 인지 "있어야 정상" 인지로 갈립니다.
> `hidden`(안 보이는 항목)·`broken`(문제 행)은 **비어야** 정상이라 `not` 을 붙이고,
> `row_ids`(조회된 행)는 **있어야** 정상이라 그냥 씁니다.

## 10. TC-260907-003 — 행별 액션 버튼 (이 파일에서 가장 복잡한 것)

```python
    row_ids = fs.row_ids()
    assert row_ids, ( ... )
```

**하한**입니다. 이게 없으면 아래 `for` 문이 0번 돌아서 **검증이 통째로 사라진 채 통과**합니다.
2026-09-08 에 591건짜리 화면을 0건으로 읽었을 때 이 줄이 잡아냈습니다.

메시지에 `fs.state_summary()` 를 넣은 건, "0건" 이 세 가지 원인(실제로 없음 / 필터가 걸러냄 /
로딩·세션 실패)에서 똑같이 나오기 때문입니다. 값을 같이 안 남기면 리포트만 보고는 못 가릅니다.

```python
    _expect_rendered(fs.row_action_button(row_ids[0]), f"첫 행({row_ids[0]})의 액션 버튼")
    statuses = fs.row_statuses()
```

`_find_hidden` 과 **같은 요령**입니다 — 대표 하나를 기다린 뒤 나머지를 훑습니다.
`statuses` 는 `{"10682": "대기", "10680": "배정완료", ...}` 형태의 dict 입니다.

```python
    broken = []
    seen = []
```

`broken` 은 문제 있는 행, `seen` 은 관찰된 (상태, 라벨) 조합입니다. **바로 실패시키지 않고 모으는**
이유는 위와 같습니다 — 한 번에 다 보고합니다.

```python
        if not button.is_visible():
            broken.append(f"{row_id}: 버튼이 없거나 숨겨져 있음")
            continue
```

`continue` 는 이 행을 여기서 끝내고 다음 행으로 넘어가라는 뜻입니다. 버튼이 안 보이면 라벨을
읽어봐야 의미가 없습니다.

```python
        label = button.inner_text().strip()
```

`.strip()` 은 앞뒤 공백·줄바꿈 제거입니다. HTML 은 들여쓰기 때문에 `"\n  수정\n"` 처럼 오기 쉽습니다.

```python
        expected = ACTION_LABEL_BY_STATUS.get(status)
```

**`.get()` 과 `[...]` 의 차이가 여기서 핵심입니다.** `dict[key]` 는 없는 키면 에러가 나지만,
`.get()` 은 **`None` 을 돌려줍니다.** 나중에 상태가 새로 생겨 대응표에 없는 값이 와도 죽지 않습니다.

```python
        if expected and label != expected:
            broken.append(f"{row_id}: 상태 {status!r} 인데 라벨이 {label!r} (기대 {expected!r})")
        elif not expected and label not in ACTION_BUTTON_LABELS:
            broken.append(f"{row_id}: 미실측 상태 {status!r} 의 라벨이 {label!r}")
```

두 갈래입니다.

| 상황 | 검증 |
|---|---|
| 실측된 상태 (`expected` 가 있음) | 라벨이 **정확히 그것**인가 |
| 대응표에 없는 상태 (`expected` 가 `None`) | 라벨이 **둘 중 하나**이긴 한가 |

지금은 상태 5개를 다 채워서 아래쪽 갈래에 걸리는 행이 없습니다. **나중에 상태가 새로 생겼을
때를 위한 그물**로 남겨둔 것입니다.

`{label!r}` 의 `!r` 은 `repr()` 로 찍으라는 뜻입니다 — `수정` 이 아니라 `'수정'` 으로 따옴표까지
나옵니다. **빈 문자열이나 공백을 구분하려면 필수**입니다(`''` 와 `' '` 은 따옴표가 없으면
똑같아 보입니다).

```python
    print(f"[검증] ... {sorted(set(seen))}")
```

`set` 으로 중복 제거 → `sorted` 로 정렬합니다. 실행 로그가 **다음 실측의 표본**이 되게 남깁니다.

## 11. TC-260907-004 · 005 — 팝업

```python
    popup = fs.open_new_service_popup()
```

화면 객체가 **팝업 객체를 돌려줍니다.** "목록 화면에서 팝업으로 들어간다" 는 관계가 코드에
그대로 드러납니다.

```python
    hidden = _find_hidden(popup, NEW_POPUP_FIELDS)

    assert not hidden, f"[FAIL] 노출되지 않은 팝업 입력 항목: {hidden}"
    popup.close()
```

**`assert` 가 `close()` 보다 먼저인 것이 중요합니다.** 실패하면 `close()` 에 도달하지 않아
팝업이 열린 화면이 리포트에 첨부됩니다. 반대로 두면 "어느 필드가 안 보이는가" 로 실패했는데
스크린샷에는 목록 화면만 남습니다 — 자세한 경위는 `현장서비스-테스트-노트.md` 참고.

```python
    expect(popup.submit_button).to_be_visible()
```

★ [신청 완료] 버튼은 **있는지만** 봅니다. 화면 객체에 `submit_button`(요소)은 있지만
`submit()`(누르는 메서드)은 **일부러 안 만들었습니다** — 있으면 다음 사람이 씁니다.

```python
    popup.close()
    expect(fs.table_root).to_be_visible()
```

TC-005 의 `close()` 는 정리가 아니라 **검증 자체**입니다 — 닫은 뒤 목록이 돌아오는지까지 봐야
"닫기가 동작했다" 가 됩니다. 그래서 이 자리의 `close()` 는 위치를 바꾸면 안 됩니다.

# 2부 — 테스트 본문 바깥

여기부터는 `test_field_service.py` 가 아니라 **그 파일이 기대고 있는 것들**입니다.
`fs` 를 받는 순간 이미 로그인·화면 진입·데이터 도착 대기가 다 끝나 있는데,
그 일이 어디서 어떻게 벌어지는지가 본문에는 안 보입니다.

## 12. 실행 구조 — 테스트 한 건이 도는 3단계

### 12-1. pytest 는 테스트 하나를 세 단계로 쪼갠다

지어낸 말이 아니라 pytest 의 정식 용어이고, 코드에도 글자 그대로 나옵니다
(`conftest.py` 의 실패 첨부 훅).

```python
if rep.when in ("setup", "call") and rep.failed:
```

`rep.when` 에는 `"setup"` · `"call"` · `"teardown"` 셋 중 하나가 문자열로 들어옵니다.

| 단계 | 무슨 일 | 이 프로젝트에서는 | 실패하면 |
|---|---|---|---|
| **setup** | 준비 — fixture 들을 만든다 | `auth_state` → `browser` → `logged_in_page` → `fs` | `E` (ERROR) |
| **call** | 테스트 함수 본문이 실행된다 | `test_...` 안의 `expect`/`assert` | `F` (FAILED) |
| **teardown** | 뒷정리 | `context.close()` | `E` |

`E` 와 `F` 가 갈리는 것이 중요합니다 — `E` 는 **검증까지 가지도 못한 것**(환경·진입 문제),
`F` 는 **검증하다 틀린 것**(기능 문제)입니다. 이 구분을 테스트 본문에서 `try/except` 로
뭉개면 안 되는 이유가 여기 있습니다.

### 12-2. fixture 는 "요청은 위에서 아래로, 생성은 아래에서 위로"

pytest 는 **함수의 매개변수 이름**을 보고 "이 이름의 fixture 를 달라는 뜻" 으로 해석합니다.
그게 전부입니다 — 등록도 import 도 필요 없습니다.

```python
def test_page_areas_visible(fs):               # 나는 fs 가 필요하다
def fs(logged_in_page):                        #   fs 를 만들려면 logged_in_page 가 필요하다
def logged_in_page(browser, auth_state, ...):  #     그걸 만들려면 browser 와 auth_state 가 필요하다
def auth_state(browser_type):                  #       그걸 만들려면 browser_type 이 필요하다
```

pytest 는 이 사슬을 끝까지 따라 내려간 뒤 **맨 아래부터 거꾸로 만들어 올라옵니다.**
탭을 열려면 브라우저가 먼저 있어야 하므로 순서가 그럴 수밖에 없습니다.

```
요청 아래로                          생성 위로
  test                                (5) 이제 테스트 본문 실행
   └ fs                               (4) FieldServicePage 만들고 goto()
      └ logged_in_page                (3) 새 탭 열기 + 로그 수집기 부착
         ├ browser                    (2) headless 크롬 실행
         └ auth_state                 (1) auth.json 확인 / 없으면 로그인
```

### 12-3. `yield` 가 setup 과 teardown 의 경계다

```python
    yield page          # 여기서 테스트에게 넘겨주고 멈춰 있는다 (call 단계 진행)
                        # 테스트가 끝나면 이 아래가 이어서 실행된다
    context.close()     # 이것이 teardown
```

`yield` **위**가 setup, **아래**가 teardown 입니다. `_login_and_save` 의
`finally: context.close()` 도 같은 역할입니다.

### 12-4. `page` 와 `context` 는 다르다

Playwright 는 3층입니다.

```
Browser              크롬 프로그램 하나          <- session fixture. 한 번 띄우고 끝까지 재사용
 └ BrowserContext    독립된 프로필 (시크릿 창)    <- 테스트 실행 1건당 하나
     └ Page          그 창 안의 탭               <- 실제로 조작하는 대상
```

| | 담는 것 | 이 프로젝트에서 |
|---|---|---|
| **Context** | 쿠키 · localStorage · 로그인 세션 | `auth.json` 을 여기에 주입한다 |
| **Page** | 화면 그 자체 (`click` · `fill` · `screenshot`) | 창마다 하나만 연다 |

```python
context = browser.new_context(storage_state=auth_state)   # auth.json 을 이 창에 주입
page = context.new_page()                                 # 그 창에 탭 하나
```

**로그인 토큰은 탭이 아니라 창에 붙는 것**이라 context 를 거쳐야 합니다 — page 만으로는
로그인 상태를 심을 방법이 없습니다.

**`context.close()` 가 닫는 범위** — 그 context 하나와 그 안의 탭 전부입니다.
브라우저 자체는 살아 있고 다른 context 도 영향받지 않습니다. 테스트 중에 새 탭이
열렸다면(`target="_blank"` 등) 그것도 같은 context 안이라 함께 닫힙니다 — 그것이 의도한
동작입니다. "테스트가 벌여놓은 것을 통째로 치운다" 는 뜻입니다.

**동시에 여러 개가 떠 있는 것이 아닙니다.** 이 파일은 함수 7개지만 parametrize 로 실행이
15건이라 context 도 15개인데, 하나 열고 → 쓰고 → 닫고 → 다음 것을 엽니다.

```
시간 ->
 [ctx 1]      [ctx 2]      [ctx 3]  ...        크롬(Browser)은 계속 살아 있다
 열고 닫고    열고 닫고    열고 닫고
```

`browser` 를 session scope 로 둔 이유가 이것입니다 — 창 하나 여는 것은 수십 ms 로 싸지만
크롬 프로그램 자체를 띄우는 것은 1~2 초로 비쌉니다.

### 12-5. 콘솔 로그 수집기 — `page.on(...)`

```python
console_logs: list[str] = []                                                    # 빈 바구니
page.on("console",   lambda msg: console_logs.append(f"[{msg.type}] {msg.text}"))
page.on("pageerror", lambda exc: console_logs.append(f"[pageerror] {exc}"))
request.node._console_logs = console_logs
request.node._page = page
```

- **언제 부착되나** — 탭을 열자마자 한 번. 즉 테스트 하나당 한 번입니다.
- **`page.on(이벤트, 함수)`** 는 지금 무엇을 실행하는 것이 아니라 **"앞으로 이 일이 생기면
  이 함수를 불러줘"** 라고 등록해 두는 구독 명령입니다.
  - `"console"` — 웹페이지가 `console.log/warn/error` 를 찍을 때
  - `"pageerror"` — 웹페이지 자바스크립트가 에러로 죽을 때
- 그 뒤로 테스트가 도는 내내, 브라우저가 무언가 찍을 때마다 저 `lambda` 가 자동으로 불려
  바구니에 한 줄씩 담깁니다.
- **마지막 두 줄이 핵심입니다** — 바구니와 탭을 테스트 객체(`request.node`)에 걸어 둡니다.
  실패 첨부 훅이 `item._page` · `item._console_logs` 로 이것을 꺼내 씁니다. 그냥 지역
  변수로 두면 훅이 접근할 방법이 없습니다.

**증거 첨부는 teardown 보다 먼저 돕니다** — 그래서 탭이 아직 살아 있어 그 시점 화면을
찍을 수 있습니다. 훅이 `"setup"` 도 함께 보는 이유는 `현장서비스-테스트-노트.md` 참고
(진입 실패가 ERROR 로 끝나 증거가 하나도 안 남던 문제).

## 13. `wait_status_counts` — "데이터가 도착했다" 는 유일한 신호

### 13-1. 무엇을 막는 함수인가

정상적으로 다 뜬 화면:

```
[전체 591] [대기 70] [배정완료 4] [완료 217] ...   <- 배지에 숫자가 있다
+-------------------------------------+
| 12가3456 · LG업체 · 대기 ...          |
| ... (10행)                           |
+-------------------------------------+
```

서버 응답이 **아직 안 온** 동안의 화면:

```
[전체] [대기] [배정완료] [완료] ...              <- 숫자가 없다
+-------------------------------------+
|          데이터가 없습니다             |   <- 화면이 스스로 이렇게 그려 놓는다
+-------------------------------------+
```

그런데 **진짜로 조건에 맞는 건이 0건인 화면**도 표는 똑같이 생겼습니다. 즉
**"아직 안 왔다" 와 "진짜 없다" 가 표만 봐서는 글자까지 같습니다.**

둘을 구분하는 유일한 단서가 배지 숫자입니다 — 배지는 서버 응답이 와야 채워지므로,
숫자가 박혀 있으면 "데이터 도착" 이 확정됩니다. 그래서 표를 읽기 **전에** 배지를 기다립니다.
2026-09-08 에 591 건짜리 화면을 "0건" 으로 읽은 사고가 정확히 이것이었습니다.

### 13-2. 코드 한 줄씩

```python
self.page.wait_for_function(
    """(selector) => {
        const el = document.querySelector(selector);
        return !!el && /\d/.test(el.innerText);
    }""",
    arg='[data-testid="fs-status-tabs__tabs"]',
    polling=300,
    timeout=timeout_ms,
)
```

| 줄 | 뜻 |
|---|---|
| `wait_for_function(...)` | "이 자바스크립트 함수가 `true` 를 돌려줄 때까지 기다려라". 함수는 **브라우저 안에서** 돈다 (파이썬-브라우저 왕복이 없다) |
| `(selector) => {...}` | JS 화살표 함수. `selector` 를 인자로 받는다 |
| `document.querySelector(selector)` | 상태 탭 묶음 요소를 찾는다. 없으면 `null` |
| `!!el` | "그 요소가 있나" |
| `/\d/.test(el.innerText)` | 그 요소의 글자 안에 **숫자가 하나라도** 있나. `전체 591` 이면 참, `전체` 뿐이면 거짓 |
| `arg=` | 위 함수의 `selector` 자리에 넣어 줄 값 |
| `polling=300` | 0.3 초마다 다시 재본다 |
| `timeout=15000` | 15 초 안에 참이 안 되면 예외 |

**`!!` 는 느낌표 두 개**입니다 — 불리언으로 변환하는 관용구입니다.

```javascript
el      // 요소 객체 또는 null   <- 불리언이 아니다
!el     // "없다"  ->  true / false
!!el    // 다시 뒤집어 "있다"  ->  true / false
```

기능상 차이는 없습니다(`el && ...` 로 써도 동작합니다). 다만 그렇게 쓰면 `el` 이 없을 때
`false` 가 아니라 **`null` 을 반환**합니다. 반환값을 항상 `true`/`false` 로 맞추고,
읽는 사람에게 "여기는 불리언 자리" 라고 알리려는 표시입니다.

`except` 절은 예외를 **한글 메시지로 바꿔 다시 던지는** 부분입니다. Playwright 기본
메시지는 "함수가 true 가 안 됐다" 뿐이라 리포트만 보고는 원인을 모릅니다.

## 14. `wait_table_settled` — "그만 바뀌었다" 를 판정한다

### 14-1. `cur != prev` 로 하면 안 되는 이유

두 방식은 **묻는 질문이 다릅니다.**

| 방식 | 묻는 것 | |
|---|---|---|
| `cur != prev` | "**바뀌었나?**" | 바뀌는 순간 즉시 통과 |
| 연속 2회 동일 | "**그만 바뀌었나?**" | 더 안 바뀌게 된 뒤 통과 |

표를 다시 그릴 때 화면은 이렇게 지나갑니다.

```
시각     표 상태               cur != prev?            연속 2회 동일?
0.0s   [옛 행 10개]  <- prev
0.3s   [   빈 표   ]  지우는 중  다르다 -> 통과!! (X)   다르다 -> 계속 기다림
0.6s   [새 행 10개]                                    다르다 -> 계속 기다림
0.9s   [새 행 10개]                                    같다  -> 통과 (O)
```

`cur != prev` 는 **표가 텅 빈 0.3 초 지점에서** "바뀌었다" 며 빠져나옵니다
(`[] != [옛 행 10개]` 는 참이므로). 그러면 테스트가 빈 표를 읽고 0건으로 판정합니다.

### 14-2. 코드 한 줄씩

```python
self.page.evaluate("() => { window.__fsTableSnapshot = undefined; }")   # (1)
```

(1) **직전 호출이 브라우저에 남겨 둔 기록을 지웁니다.**
여기서 "직전 호출" 은 **다른 테스트가 아니라 같은 탭에서 앞서 부른 이 함수**입니다.
`window.__fsTableSnapshot` 은 그 탭의 자바스크립트 메모리에 살고, 테스트가 끝나면 탭째
닫히므로 다음 테스트로 넘어가지 않습니다. 그런데 **한 테스트 안에서 여러 번 불립니다.**

```
TC-260907-007 의 경우
  fs fixture     goto() -> wait_loaded() -> wait_table_settled()   <- 1번째
  테스트 본문    click_status_tab("전체") -> wait_table_settled()   <- 2번째
                 click_status_tab("대기") -> wait_table_settled()   <- 3번째
```

셋 다 같은 탭입니다. 2번째를 시작할 때 1번째가 남긴 지문이 그대로 있고, 하필 그것이 지금
화면과 같으면(탭을 눌렀는데 아직 옛 목록이 떠 있는 순간) **첫 판에 바로 "같다" 가 나와
갱신 전 목록을 읽고 통과**합니다. (1)이 그것을 막습니다.

```javascript
(emptyText) => {
    const ids = [...document.querySelectorAll('[data-testid^="fs-table__row--"]')]   // (2)
        .map(e => e.getAttribute('data-testid')).join(',');                          // (3)
    const root = document.querySelector('[data-testid="fs-table__root"]');
    const isEmpty = !!(root && root.innerText.includes(emptyText));                  // (4)
    if (!ids && !isEmpty) { window.__fsTableSnapshot = undefined; return false; }    // (5)
    const snapshot = isEmpty ? '__EMPTY__' : ids;                                    // (6)
    const settled = window.__fsTableSnapshot === snapshot;                           // (7)
    window.__fsTableSnapshot = snapshot;                                             // (8)
    return settled;
}
```

| | |
|---|---|
| (2) | testid 가 `fs-table__row--` **로 시작하는** 요소를 전부 찾는다 (`^=` 가 "이것으로 시작") = 지금 화면의 결과 행들 |
| (3) | 각 행의 testid 를 뽑아 쉼표로 잇는다 -> `"fs-table__row--10679,fs-table__row--10677,..."` **= 지금 목록의 지문** |
| (4) | 표 안에 `데이터가 없습니다` 가 떠 있나 |
| (5) | 행도 없고 빈 안내도 없다 = **아직 그리는 중**. 기록까지 지우고 `false` |
| (6) | 이번 지문. 빈 상태면 `'__EMPTY__'` 라는 지문을 쓴다 |
| (7) | **직전 지문과 같나** = 0.3 초 간격으로 두 번 봤는데 같다 = 다 그려졌다 |
| (8) | 이번 지문을 저장 (다음 회차의 "직전 지문" 이 된다) |

**"지문을 찍는다" 는 사진이 아니라 DOM 을 읽어 문자열 하나로 만드는 것**입니다 —
찍는 코드는 (2)(3)(6) 세 줄입니다.

### 14-3. (8) 이 필요한 이유 — 파이썬이 아니라 폴링이 반복 호출한다

`wait_for_function` 은 **그 JS 함수를 0.3 초마다 알아서 반복 실행합니다.**
파이썬은 한 번만 부르지만 브라우저 안에서는 참이 될 때까지 몇 번이고 돕니다.

```
파이썬:  self.page.wait_for_function(...)      <- 딱 한 줄, 한 번 호출
   |
   +- 브라우저: 그 JS 함수를 0.3초 간격으로 반복 실행
        1회차 (0.0초)  지문 A 읽음 -> 저장된 것이 없다 -> 다르다 -> false
        2회차 (0.3초)  지문 B 읽음 -> 저장된 A 와 비교 -> 다르다 -> false
        3회차 (0.6초)  지문 B 읽음 -> 저장된 B 와 비교 -> 같다   -> true
   |
   +- 파이썬: 다음 줄로 넘어간다
```

그래서 (8) 이 필요합니다 — **이번 회차가 다음 회차에게 값을 넘겨주는 유일한 통로**입니다.
이것이 없으면 매 회차가 "저장된 것이 없네" 만 반복하며 영원히 `false` 를 돌려주고
타임아웃이 납니다.

`window` 에 두는 이유도 여기 있습니다. JS 함수 안의 지역 변수는 회차가 끝나면 사라지지만
`window` 는 그 탭이 살아 있는 한 남습니다 — **회차 사이에 기억을 남기는 장소**가 필요합니다.
파이썬 변수에는 브라우저 쪽에서 손이 닿지 않습니다.

**폴링이 비효율적이지 않은가** — 조건이 참이 되는 순간 즉시 멈추므로 보통 2~3 회 돌고
끝납니다(약 0.6 초). 그리고 저 함수는 브라우저 안에서 도므로 폴링마다 파이썬을 오가지
않습니다.

| 방법 | 비용 | 문제 |
|---|---|---|
| `wait_for_timeout(2000)` | 항상 2초 | 0.1초면 될 때도 2초를 버리고, 3초 걸리는 날에는 깨진다 |
| 파이썬에서 0.3초마다 확인 | 폴링마다 파이썬-브라우저 왕복 | 왕복이 비용의 대부분 |
| `wait_for_function` | 폴링마다 브라우저 안에서 DOM 몇 줄 읽기 | 왕복 0. 되는 즉시 탈출 |

`polling=300` 은 비용만 보고 정한 값이 아닙니다. **두 샘플 사이 간격이 곧 "안정 판정 창"**
이라, 10ms 로 줄이면 아직 갱신 중인데 "안 바뀌었다" 로 오판할 확률이 커집니다.
대신 최소 대기가 0.3 초 x 2 = 0.6 초로 고정되는 대가를 치릅니다.

### 14-4. 이 함수가 못 막는 것 — 빈 표에는 두 종류가 있다

| 종류 | 화면 | 결과 |
|---|---|---|
| **(A) 행도 없고 안내 문구도 없다** | 표가 그냥 텅 빔 = 그리는 중 | (5) 가 걸러낸다. **몇 번 연속이어도 통과 못 함** |
| **(B) 행은 없는데 "데이터가 없습니다" 가 떠 있다** | 화면이 적극적으로 "없음" 을 그린 상태 | `'__EMPTY__'` 지문 -> **2회 연속이면 통과함** |

(B) 가 2026-09-08 에 터진 그 사고입니다. 그리고 **이 함수 혼자서는 (B) 를 막을 수 없습니다** —
진짜로 0건인 검색도 있어야 하므로 빈 상태를 무조건 실패로 볼 수 없기 때문입니다.
그래서 앞에 `wait_status_counts()` 를 세웠습니다.

```
wait_status_counts()   배지에 숫자가 있나 -> "서버 응답이 왔다" 가 확정된다   <- (B) 를 자른다
       |
wait_table_settled()   그 뒤에야 표를 본다. 이제 빈 표는 진짜 0건이다        <- (A)·갱신 중을 담당
```

**한 함수가 다 막는 것이 아니라 둘이 나눠 막는 구조**입니다.

남은 구멍도 있습니다 — 검색 버튼을 눌렀을 때 서버가 폴링 간격 두 번(0.6 초)보다 느리면
**옛 목록**을 두 번 연속 읽고 "안정됐다" 로 볼 수 있습니다. 갱신 전후를 구분해야 하는 TC 는
이 대기에 기대지 말고 본문에서 직접 대조해야 합니다.

## 15. `with allure.step(...)` — 리포트에 단계를 남긴다

`with` 은 allure 문법이 아니라 **파이썬 문법**입니다. "블록에 들어갈 때 무언가 하고,
나갈 때 무언가 한다" 를 자동화합니다 — 익숙한 예로는 이것과 같은 종류입니다.

```python
with open("a.txt") as f:     # 들어갈 때: 파일을 연다
    data = f.read()
                             # 나갈 때: 자동으로 닫는다 (에러가 나도 닫힌다)
```

```python
with allure.step("① 결과에 다른 상태가 섞이지 않았는가 (오검출)"):
    wrong = {...}                # 들어갈 때: "이 단계 시작" 기록
    assert not wrong, "..."
                                 # 나갈 때: "통과" 또는 "이 단계에서 실패" 기록
```

**동작은 하나도 바뀌지 않습니다.** `with` 줄을 지우고 들여쓰기를 풀어도 `assert` 는 똑같이
돕니다. 오직 리포트 모양만 달라집니다.

```
TC-260907-007 | [대기] 탭 — 그 상태의 건만, 빠짐없이 조회된다      실패
  ├ [전체] 탭에서 기준 목록 읽기                                 통과
  ├ [대기] 상태 탭 클릭                                         통과
  ├ ① 결과에 다른 상태가 섞이지 않았는가 (오검출)                  통과
  └ ② 그 상태인데 결과에서 빠진 건이 없는가 (누락)                 실패  <- 여기서 깨졌다
```

이것이 없으면 "TC-007 실패" 한 줄이라, 오검출에서 깨졌는지 누락에서 깨졌는지 메시지를
읽어봐야 압니다. 두 방향을 다 보는 TC 라 특히 갈라 둘 값어치가 있었습니다.

같은 `allure.step` 을 **데코레이터**로도 씁니다 — 화면 객체 메서드에 붙은 것이 그 형태입니다.

```python
@allure.step("[{name}] 상태 탭 클릭")     # 함수 전체가 한 단계
def click_status_tab(self, name): ...

with allure.step("① ..."):              # 함수 안의 일부 구간만 한 단계
```

함수 하나가 통째로 한 단계면 데코레이터, 함수 안을 여러 구간으로 쪼개고 싶으면 `with`.
하는 일은 같습니다.
