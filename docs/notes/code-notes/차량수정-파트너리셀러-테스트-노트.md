### 문제 1 — 업체/차량 데이터가 비동기로 늦게 채워짐 (레이스 컨디션)

처음 모달을 조사할 때 `page.wait_for_timeout(1500)`(고정 대기)으로 열고 바로 DOM을 읽었더니, **업체 필드가 "선택"(빈 값)으로 찍혔습니다.** 다른 차량으로 다시 확인하니 이번엔 업체명이 정상적으로 채워져 있었어요 — 즉 매번 다른 게 아니라, **모달이 열린 직후 서버에서 상세 데이터를 비동기로 받아오는 동안 잠깐 비어있는 순간**이 있고, 고정 대기시간이 그 타이밍을 우연히 걸치기도 안 걸치기도 했던 것입니다.

`자동화 테스트 노트`에 이미 있는 "assert는 그 순간 한 번만 본다" 문제와 같은 종류입니다. 그래서 고정 대기 대신, **"차량 번호 입력값이 실제로 그 차량 걸로 찼는지"를 `expect().to_have_value()`로 재확인**한 뒤에야 다른 필드를 읽도록 했습니다 — 차량 번호가 맞게 채워졌다는 건 그 차량의 상세 데이터 로딩이 끝났다는 신호로 쓸 수 있기 때문입니다.

```python
car_number_input = page.locator('input[name="carNumber"]')
expect(car_number_input).to_have_value(car_number, timeout=15_000)
```

### 문제 2 — 비활성 상태에서도 `role="combobox"` (등록 모달과 다름)

등록 모달에서는 파트너/리셀러가 비활성일 때 `role="listbox"`였는데, 이 수정 모달에서는 **비활성이어도 계속 `role="combobox"`**입니다.

```html
<!-- 수정 모달: 파트너 비활성 상태 -->
<div name="파트너 선택" role="combobox" aria-disabled="true" class="ui disabled search selection dropdown form-select">
  <div class="divider text">커넥트</div>
  ...
</div>
```

`aria-disabled` 속성으로 활성/비활성을 판단하는 로직(`_get_edit_field` + `to_have_attribute`)은 그대로 재사용했지만, **활성 상태일 땐 `aria-disabled` 속성 자체가 아예 없다**는 것도 새로 확인했습니다(등록 모달은 `aria-disabled="false"`로 명시했던 것과 다름). 그래서 TC-055에서는 `to_have_attribute("aria-disabled", "true")`가 아니라 `not_to_have_attribute("aria-disabled", "true")`로 확인합니다 — "정확히 false인지"가 아니라 "true가 아닌지"를 보는 것이라 속성이 아예 없는 경우도 정확히 커버합니다.

```python
expect(reseller_field).not_to_have_attribute("aria-disabled", "true")
```

### 라벨 이름이 다름

등록 모달은 라벨이 "파트너"/"리셀러"였는데, 이 수정 모달은 **"파트너 선택"/"리셀러 선택"**입니다(글자 자체가 다름). `_get_edit_field`로 찾을 때 이 정확한 텍스트를 씁니다.

### 문제 3 — `_get_edit_field`가 모달 범위로 안 좁혀져 있던 잠재 버그 (TC-057 작업 중 발견)

TC-057/058(`test_vehicle_company_transfer.py`)에서 "업체" 필드를 찾으려다 strict mode 에러가 났습니다. 모달이 기존 목록 화면 **위에 겹쳐서** 뜨는 구조라, 뒤에 깔린 목록 화면 상단의 "업체" 필터(라벨이 똑같이 "업체")가 DOM에서 사라지지 않고 그대로 남아있었던 것입니다. "파트너 선택"/"리셀러 선택"은 목록 필터 쪽엔 없는 문구(필터는 그냥 "파트너"/"리셀러")라 지금까지는 우연히 안 걸렸던 것뿐이고, `_get_edit_field` 자체는 원래 모달 범위로 안 좁혀져 있던 잠재 버그였습니다.

```python
def _get_modal(page):
    """지금 열려있는 차량 수정 모달(section) 자체를 가리키는 Locator."""
    return page.locator("section").filter(has=page.locator('input[name="carNumber"]'))


def _get_edit_field(page, label_text):
    label = _get_modal(page).locator("label.form-label").filter(has_text=re.compile(f"^{re.escape(label_text)}$"))
    return label.locator("xpath=./following-sibling::*[1]")
```

`input[name="carNumber"]`는 모달 안에만 있는 요소라, 이걸 가진 `<section>`을 찾으면 지금 열린 모달만 정확히 골라낼 수 있습니다. TC-051~056은 이 변경 전에도 우연히 안 걸렸을 뿐이라 결과는 그대로지만, 앞으로 더 안전해졌습니다.

### 문제 4 — 1페이지에서 찾던 차량이 밀려났다

**2026-09-11 실측.** `pytest -k TC053 --allow-mutating -v` 가 첫 단계에서 30초 타임아웃으로 실패했습니다
(`035용1111` 행의 [수정] 버튼을 못 찾음). 저장 전 단계라 데이터는 안 바뀌었습니다.

원인은 목록 정렬입니다. 목록 API 는 `GET .../admin/fms/v1/car?size=10&sort=id,desc&page=0` —
**최근 등록순 10건씩**이고, 그날 958페이지였습니다. 헬퍼는 검색 없이 1페이지에서 행을 찾고 있었으니
테스트 차량보다 늦게 등록된 차량이 10대를 넘는 순간 못 찾습니다. 그날 1페이지에는 `대차00777`·`대차0001`
같은 새 차량이 있었고 `035용1111` 은 없었습니다.

| 차량 | 그날 1페이지에 있었나 | 쓰는 TC |
|---|---|---|
| 035용1111 · 054/055/056용1111 | 없음 | TC-051~056 |
| 900용1001~1004 | **있음 (7~10번째 행)** | TC-057~066 (`test_vehicle_company_transfer.py`) |

이관 TC 가 통과해온 것은 그 4대가 **가장 최근에 등록돼서**일 뿐입니다. 900용1001 이 이미 10번째 행이라
**한 대만 더 등록돼도** 밀려나고, 일곱 대면 넷 다 밀려납니다.
두 파일이 이 헬퍼를 같이 쓰므로 한 번 고치면 둘 다 고쳐집니다.

**고친 것** — 목록 위 검색창(`input[name="searchKeyword"]`, placeholder "차량번호/단말기번호/모델코드")에
차량번호를 넣고 Enter 로 조회한 뒤 행을 찾습니다. 실측에서 `searchKeyword=035용1111` 요청 1건에 결과 1행([수정]·[삭제])이 나왔습니다.

- **첫 목록 응답을 받은 뒤에 검색합니다** (`page.expect_response`). 로딩 중에 검색하면 두 응답의 도착 순서가 보장되지 않습니다.
- 행은 `_find_list_row` 로 찾습니다 — "차량번호" 컬럼 셀만 **정확 일치**로 봅니다. 전에 쓰던 행 전체 `has_text` 는
  부분 일치라 비슷한 번호나 다른 칸까지 걸립니다(CLAUDE.md `행 식별`). 저장 직후 목록 확인도 같은 함수를 씁니다 —
  같은 행을 읽는 방법이 둘이면 한쪽만 고쳐집니다.

**"조회 결과가 없습니다." 는 빈 목록의 신호가 아닙니다.** 같은 날 첫 실측에서 1~10페이지 전부 이 한 줄이 나왔는데,
데이터가 오기 **전에** 읽었기 때문이었습니다. 이 화면은 로딩 중에도 그 안내 행(colspan 한 칸)을 그려 두고, 기다리니
10행이 채워졌습니다. 이 화면에서 "`tbody tr` 이 보인다" 는 데이터 도착의 신호가 못 됩니다 — 그래서 응답을 기다립니다.

**아직 모르는 것** — 저장 뒤 목록을 다시 불러올 때 **검색어가 유지되는지.** 저장을 해야 볼 수 있어 실측하지 못했습니다.
유지되지 않으면 저장 직후 목록 확인이 차량을 못 찾아 **실패로** 드러납니다(조용히 통과하지는 않습니다). guard 의 원복도
같은 확인을 거치므로 teardown `ERROR` 가 날 수 있습니다 — 그때는 차량 값을 화면에서 직접 확인하고 이 절을 갱신합니다.

그날 `035용1111` 상태: 리셀러 LG U+ · 업체 LG업체입니다 (원래 값 그대로).

TC-053은 이 클러스터에서 유일하게 **읽기 전용이 아닌** TC입니다 — LG U+ ↔ 커넥트를 실제로 두 번 바꾸고 저장까지 확인합니다. 자동화하다가 저장이 조용히 실패하는 문제를 겪었고, 알고 보니 진짜 원인은 사이트 버그가 아니라 **놓친 확인 팝업**이었습니다.

### 2026-09-10 — 이 노트에 적어만 두고 장치는 안 걸려 있었음

"유일하게 읽기 전용이 아닌 TC" 라고 여기 적혀 있었는데, 정작 코드에는 `@pytest.mark.mutating` 이
없었습니다. 그래서 `pytest -v` 로 그냥 돌아갔고, 이관 TC(TC-059~066)에 걸어둔 안전장치
—옵트인 게이트(`--allow-mutating`)·접속처 화이트리스트—가 **하나도 안 걸렸습니다.**
`.env` 의 `STAFF_URL` 이 운영을 가리키고 있어도 막을 것이 없는 상태였습니다.

원복도 문제였습니다. 본문 2단계(커넥트 -> LG U+)가 원복을 겸하고 있었는데, 그건 **마지막 줄**이라
1단계 저장 뒤 목록 확인에서 깨지면 그 줄에 도달하지 못하고 차량이 커넥트인 채로 남습니다.
다음 실행은 `expect(reseller_text).to_have_text("LG U+")` 에서 전제 붕괴로 실패합니다.

고친 내용은 셋입니다.

| | |
|---|---|
| `@pytest.mark.mutating` 추가 | 게이트·화이트리스트 안으로 들어옴. mutating 이 8건 -> **9건** |
| `reseller_guard` fixture 추가 | 통과·실패·예외 무엇으로 끝나든 teardown 이 원래 값으로 되돌림 |
| 본문 2단계는 그대로 | 그건 정리가 아니라 **양방향 반영을 보는 검증 시나리오**라 지우면 안 됨. guard 는 그 위에 덧대는 안전망이고, 이미 원래 값이면 아무것도 하지 않음 |

**아는 것과 막는 것은 다릅니다.** 이 노트에 적어둔 것만으로는 아무것도 막히지 않았습니다 —
규칙은 문서가 아니라 실행 경로(마커·fixture·게이트)에 걸어야 합니다.

### 처음엔 진짜 버그인 줄 알았음

저장 버튼을 누르면 모달은 닫히는데, 목록을 다시 보면 값이 그대로였습니다. 네트워크 로그를 보니 저장 API 요청 자체가 안 나갔고, 브라우저 콘솔엔 이런 에러가 있었습니다.

```
[pageerror] Cannot read properties of undefined (reading 'helpers')
```

TC-049에서 봤던 것과 같은 에러 시그니처라 "또 같은 버그인가" 싶어서 일단 자동화 대상에서 뺐는데, **사용자가 실제 사이트에서 수동으로 해보니 저장 버튼을 누른 뒤 "수정확인" 팝업이 뜨고, 그 팝업의 [OK]를 눌러야 진짜 저장된다**는 걸 확인해줬습니다. 제 스크립트는 저장 버튼만 누르고 그 뒤에 뜨는 팝업을 안 눌렀던 것이었습니다 — 콘솔 에러는 이 문제와 무관한 잡음이었던 걸로 보입니다(React 개발 모드 경고들 사이에 섞여 있었음).

### 확인 팝업의 버튼은 한글 "확인"이 아니라 영문 "OK"

`page.get_by_role("button", name="확인")`으로 계속 찾다가 못 찾았던 것도 이것 때문이었습니다. 실제로는 `Cancel` / `OK`(영문)로 되어 있습니다. 네이티브 브라우저 `confirm()`도 아니라서(`page.on("dialog")`로도 안 잡힘), 그냥 화면 안에 그려지는 커스텀 팝업입니다.

```python
def _save_edit_modal(page):
    save_button = page.locator('button[id="2"]', has_text="수정")
    save_button.click()

    ok_button = page.get_by_role("button", name="OK", exact=True)
    expect(ok_button).to_be_visible(timeout=5_000)
    ok_button.click()
```

### 저장 직후 바로 재진입하면 옛날 값이 보임 — 목록에서 먼저 확인

`[OK]`까지 누르고 나서 곧바로 모달을 다시 열어 리셀러 값을 확인했더니, **5초 넘게 재시도(`expect`)해도 계속 바뀌기 전 값**이 나왔습니다. 그런데 같은 시점에 **목록(리스트) 화면의 리셀러 컬럼은 이미 정상적으로 바뀌어 있었습니다.** 즉 저장은 실제로 잘 됐는데, 상세 모달 쪽 데이터가 뭔가의 이유로(캐시 등으로 추정) 방금 그 저장을 바로 반영하지 못하는 것으로 보입니다.

그래서 저장 직후엔 **모달을 바로 재진입하지 않고, 먼저 목록에서 값이 바뀐 걸 확인**한 다음에 재진입하도록 순서를 바꿨습니다.

```python
_select_reseller(page, "커넥트")
_save_edit_modal(page)
```

### 최종 흐름

1. 035용1111(파트너·리셀러 모두 LG U+) 진입 → 파트너 LG U+, 리셀러 LG U+ 확인
2. 리셀러를 커넥트로 변경 + 저장(`[OK]` 포함) → 목록에서 커넥트로 바뀐 것 확인 → 재진입해서 파트너 LG U+ 유지·리셀러 커넥트 확인
3. 리셀러를 다시 LG U+로 변경 + 저장 → 목록에서 LG U+로 돌아온 것 확인 → 재진입해서 최종 확인

3번 단계까지 통과하면 035용1111은 원래 값(LG U+)으로 돌아옵니다. 중간에 깨졌을 때는 `reseller_guard` teardown 이 되돌립니다(위 "2026-09-10" 절) — 전에는 3번 단계 하나에 원복을 맡겨서 중간 실패 시 값이 바뀐 채 남았습니다.

**배운 것**: "콘솔에 에러가 있다"가 곧 "그게 원인이다"는 아닙니다. 겉보기엔 TC-049와 같은 에러 시그니처라 같은 버그로 단정할 뻔했는데, 실제로는 제가 놓친 단계(확인 팝업) 때문이었습니다. 사람이 직접 화면에서 재현해준 덕분에 진짜 원인을 찾을 수 있었습니다.

TC 문서가 "2. 리셀러 토글 클릭"이라는 단계를 명시하고 있어서, 실제로 `reseller_field.click()`을 그대로 재현합니다. 조사해보니 클릭 전에도 옵션 요소(`role="option"`) 자체는 이미 DOM에 존재했지만(`aria-expanded="false"`인 채로 숨어있는 상태), TC 문서의 실제 시나리오를 그대로 따라가는 게 맞다고 판단해 클릭 단계를 생략하지 않았습니다.
