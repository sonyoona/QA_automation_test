# 차량 수정 파트너/리셀러 테스트 노트

`test_vehicle_edit_reseller.py`에 짠 TC-051~056(전부)이 뭘 하는지 정리했습니다.

## 화면 진입 경로 & 테스트 데이터

**차량관리 > 차량관리** 목록에서, 각 행마다 있는 **[수정]** 버튼을 누르면 "상세보기"(실제로는 수정 가능한) 모달이 뜹니다. 등록 화면(`test_vehicle_register_reseller.py`)과는 별개의 화면·모달입니다.

이 클러스터는 TC마다 **특정 파트너를 가진 실제 차량**이 있어야 검증할 수 있어서, dev 환경 기존 데이터를 뒤지는 대신 사용자가 직접 테스트 전용 차량 4대를 새로 등록했습니다(`test_vehicle_register_reseller.py`에서 이미 검증해둔 업체 3개를 그대로 이용).

```python
CAR_PARTNER_CONNECT = "054용1111"       # IMS모빌리티 → 파트너 커넥트
CAR_PARTNER_LG_UPLUS = "055용1111"      # LG업체입니다 → 파트너 LG U+, 리셀러 커넥트로 등록됨
CAR_PARTNER_LG_UPLUS_RESELLER_LG = "035용1111"  # LG업체입니다 → 파트너 LG U+, 리셀러도 LG U+로 등록됨
CAR_PARTNER_SMALLTICKET = "056용1111"   # 스몰티켓(지입)2 → 파트너 스몰티켓
```

기존 데이터를 건드리지 않고 이 4대만으로 검증합니다.

## 모달 구조 — 등록 모달과 또 다름

`_open_carmgmt_edit_modal` / `_get_edit_field`:

```python
def _open_carmgmt_edit_modal(page, car_number):
    page.goto(STAFF_URL)
    page.locator("a").filter(has_text=re.compile(r"^차량관리$")).click()
    page.get_by_role("link", name="차량 관리", exact=True).click()

    row = page.locator("table").first.locator("tbody tr").filter(has_text=car_number)
    row.get_by_role("button", name="수정", exact=True).click()

    car_number_input = page.locator('input[name="carNumber"]')
    expect(car_number_input).to_have_value(car_number, timeout=15_000)
```

### 문제 1 — 업체/차량 데이터가 비동기로 늦게 채워짐 (레이스 컨디션)

처음 모달을 조사할 때 `page.wait_for_timeout(1500)`(고정 대기)으로 열고 바로 DOM을 읽었더니, **업체 필드가 "선택"(빈 값)으로 찍혔습니다.** 다른 차량으로 다시 확인하니 이번엔 업체명이 정상적으로 채워져 있었어요 — 즉 매번 다른 게 아니라, **모달이 열린 직후 서버에서 상세 데이터를 비동기로 받아오는 동안 잠깐 비어있는 순간**이 있고, 고정 대기시간이 그 타이밍을 우연히 걸치기도 안 걸치기도 했던 것입니다.

`자동화 테스트 노트`에 이미 있는 "assert는 그 순간 한 번만 본다" 문제와 같은 종류입니다. 그래서 고정 대기 대신, **"차량 번호 입력값이 실제로 그 차량 걸로 찼는지"를 `expect().to_have_value()`로 재확인**한 뒤에야 다른 필드를 읽도록 했습니다 — 차량 번호가 맞게 채워졌다는 건 그 차량의 상세 데이터 로딩이 끝났다는 신호로 쓸 수 있기 때문입니다.

```python
car_number_input = page.locator('input[name="carNumber"]')
expect(car_number_input).to_have_value(car_number, timeout=15_000)
```

### 문제 2 — 비활성 상태에서도 `role="combobox"` (등록 모달과 다름)

등록 모달에서는 파트너/리셀러가 비활성일 때 `role="listbox"`였는데, 이 수정 모달에서는 **비활성이어도 계속 `role="combobox"`**입니다.

```html
<!-- 수정 모달: 파트너 비활성 상태 -->
<div name="파트너 선택" role="combobox" aria-disabled="true" class="ui disabled search selection dropdown form-select">
  <div class="divider text">커넥트</div>
  ...
</div>
```

`aria-disabled` 속성으로 활성/비활성을 판단하는 로직(`_get_edit_field` + `to_have_attribute`)은 그대로 재사용했지만, **활성 상태일 땐 `aria-disabled` 속성 자체가 아예 없다**는 것도 새로 확인했습니다(등록 모달은 `aria-disabled="false"`로 명시했던 것과 다름). 그래서 TC-055에서는 `to_have_attribute("aria-disabled", "true")`가 아니라 `not_to_have_attribute("aria-disabled", "true")`로 확인합니다 — "정확히 false인지"가 아니라 "true가 아닌지"를 보는 것이라 속성이 아예 없는 경우도 정확히 커버합니다.

```python
expect(reseller_field).not_to_have_attribute("aria-disabled", "true")
```

### 라벨 이름이 다름

등록 모달은 라벨이 "파트너"/"리셀러"였는데, 이 수정 모달은 **"파트너 선택"/"리셀러 선택"**입니다(글자 자체가 다름). `_get_edit_field`로 찾을 때 이 정확한 텍스트를 씁니다.

## TC-053 — 리셀러 값 변경 + 저장 (유일하게 실제로 값을 바꾸는 TC)

TC-053은 이 클러스터에서 유일하게 **읽기 전용이 아닌** TC입니다 — LG U+ ↔ 커넥트를 실제로 두 번 바꾸고 저장까지 확인합니다. 자동화하다가 저장이 조용히 실패하는 문제를 겪었고, 알고 보니 진짜 원인은 사이트 버그가 아니라 **놓친 확인 팝업**이었습니다.

### 처음엔 진짜 버그인 줄 알았음

저장 버튼을 누르면 모달은 닫히는데, 목록을 다시 보면 값이 그대로였습니다. 네트워크 로그를 보니 저장 API 요청 자체가 안 나갔고, 브라우저 콘솔엔 이런 에러가 있었습니다.

```
[pageerror] Cannot read properties of undefined (reading 'helpers')
```

TC-049에서 봤던 것과 같은 에러 시그니처라 "또 같은 버그인가" 싶어서 일단 자동화 대상에서 뺐는데, **사용자가 실제 사이트에서 수동으로 해보니 저장 버튼을 누른 뒤 "수정확인" 팝업이 뜨고, 그 팝업의 [OK]를 눌러야 진짜 저장된다**는 걸 확인해줬습니다. 제 스크립트는 저장 버튼만 누르고 그 뒤에 뜨는 팝업을 안 눌렀던 것이었습니다 — 콘솔 에러는 이 문제와 무관한 잡음이었던 걸로 보입니다(React 개발 모드 경고들 사이에 섞여 있었음).

### 확인 팝업의 버튼은 한글 "확인"이 아니라 영문 "OK"

`page.get_by_role("button", name="확인")`으로 계속 찾다가 못 찾았던 것도 이것 때문이었습니다. 실제로는 `Cancel` / `OK`(영문)로 되어 있습니다. 네이티브 브라우저 `confirm()`도 아니라서(`page.on("dialog")`로도 안 잡힘), 그냥 화면 안에 그려지는 커스텀 팝업입니다.

```python
def _save_edit_modal(page):
    save_button = page.locator('button[id="2"]', has_text="수정")
    save_button.click()

    ok_button = page.get_by_role("button", name="OK", exact=True)
    expect(ok_button).to_be_visible(timeout=5_000)
    ok_button.click()
```

### 저장 직후 바로 재진입하면 옛날 값이 보임 — 목록에서 먼저 확인

`[OK]`까지 누르고 나서 곧바로 모달을 다시 열어 리셀러 값을 확인했더니, **5초 넘게 재시도(`expect`)해도 계속 바뀌기 전 값**이 나왔습니다. 그런데 같은 시점에 **목록(리스트) 화면의 리셀러 컬럼은 이미 정상적으로 바뀌어 있었습니다.** 즉 저장은 실제로 잘 됐는데, 상세 모달 쪽 데이터가 뭔가의 이유로(캐시 등으로 추정) 방금 그 저장을 바로 반영하지 못하는 것으로 보입니다.

그래서 저장 직후엔 **모달을 바로 재진입하지 않고, 먼저 목록에서 값이 바뀐 걸 확인**한 다음에 재진입하도록 순서를 바꿨습니다.

```python
_select_reseller(page, "커넥트")
_save_edit_modal(page)

reseller_col = _find_list_col_index(page, "리셀러")
row = page.locator("table").first.locator("tbody tr").filter(has_text=car)
expect(row.locator("td").nth(reseller_col)).to_have_text("커넥트", timeout=10_000)

_open_carmgmt_edit_modal(page, car)   # 이제서야 재진입
...
```

`_find_list_col_index`로 "리셀러" 컬럼 위치를 헤더에서 찾아냈습니다 — `CLAUDE.md`의 "컬럼 위치를 하드코딩하지 않는다" 원칙 그대로입니다.

### 최종 흐름

1. 035용1111(파트너·리셀러 모두 LG U+) 진입 → 파트너 LG U+, 리셀러 LG U+ 확인
2. 리셀러를 커넥트로 변경 + 저장(`[OK]` 포함) → 목록에서 커넥트로 바뀐 것 확인 → 재진입해서 파트너 LG U+ 유지·리셀러 커넥트 확인
3. 리셀러를 다시 LG U+로 변경 + 저장 → 목록에서 LG U+로 돌아온 것 확인 → 재진입해서 최종 확인

3번 단계가 있어서 **테스트가 끝나면 035용1111은 항상 원래 값(LG U+)으로 복원됩니다** — 이 TC 자체의 시나리오가 왕복이라, 별도 cleanup 없이도 테스트 독립성이 지켜집니다.

**배운 것**: "콘솔에 에러가 있다"가 곧 "그게 원인이다"는 아닙니다. 겉보기엔 TC-049와 같은 에러 시그니처라 같은 버그로 단정할 뻔했는데, 실제로는 제가 놓친 단계(확인 팝업) 때문이었습니다. 사람이 직접 화면에서 재현해준 덕분에 진짜 원인을 찾을 수 있었습니다.

## TC-054 / TC-056 — 파트너가 커넥트/스몰티켓인 경우

리셀러가 자동선택+비활성 상태인지 확인. 등록 모달 TC-047/050과 같은 패턴이고, 이 화면에서도 동일하게 성립하는지 재확인하는 성격입니다.

## TC-055 — 파트너가 LG U+인 경우 (리셀러 필수 선택)

```python
def test_TC055_vehicle_edit_reseller_required_when_partner_lg_uplus(logged_in_page):
    page = logged_in_page
    _open_carmgmt_edit_modal(page, CAR_PARTNER_LG_UPLUS)

    reseller_field = _get_edit_field(page, "리셀러 선택")
    expect(reseller_field).not_to_have_attribute("aria-disabled", "true")

    reseller_field.click()
    reseller_options = reseller_field.locator('[role="option"] .text')
    expect(reseller_options).to_have_count(2)
    assert set(reseller_options.all_inner_texts()) == {"커넥트", "LG U+"}, (...)
```

TC 문서가 "2. 리셀러 토글 클릭"이라는 단계를 명시하고 있어서, 실제로 `reseller_field.click()`을 그대로 재현합니다. 조사해보니 클릭 전에도 옵션 요소(`role="option"`) 자체는 이미 DOM에 존재했지만(`aria-expanded="false"`인 채로 숨어있는 상태), TC 문서의 실제 시나리오를 그대로 따라가는 게 맞다고 판단해 클릭 단계를 생략하지 않았습니다.

`expect(reseller_options).to_have_count(2)`처럼 **Locator 자체에 `expect`를 거는 것도 가능합니다** — 개수가 비동기로 안정될 때까지 재확인해주기 때문에, `.count() == 2`(그 순간 스냅샷)보다 안전합니다.
