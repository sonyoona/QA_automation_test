## 겪은 문제 — "업체" 라벨이 목록 필터 영역과 겹침

`_get_edit_field`로 "업체" 필드를 찾으려니 strict mode 에러가 났습니다.

```
resolved to 2 elements:
1) <div name="업체" ...>  (목록 화면 상단 필터의 "업체" 드롭다운)
2) <div name="업체" ...>  (지금 연 모달 안의 "업체" 필드)
```

모달은 기존 화면 위에 **겹쳐서** 뜨는 구조라, 뒤에 깔린 목록 화면의 "업체" 필터(라벨이 똑같이 "업체")가 DOM에서 사라지지 않고 그대로 남아있던 것입니다. "파트너 선택"/"리셀러 선택"은 목록 필터에 없는 문구(필터는 그냥 "파트너"/"리셀러")라 우연히 안 걸렸던 것뿐이고, `_get_edit_field` 자체는 원래 모달 범위로 안 좁혀져 있던 잠재 버그였습니다.

**해결**: `test_vehicle_edit_reseller.py`의 `_get_edit_field`를 아예 모달 범위로 좁히도록 고쳤습니다 (이 파일에서 새로 만들지 않고, 원본 헬퍼 자체를 더 안전하게 고쳐서 TC-051~056까지 다 같이 혜택을 보게 함).

```python
def _get_modal(page):
    """지금 열려있는 차량 수정 모달(section) 자체를 가리키는 Locator."""
    return page.locator("section").filter(has=page.locator('input[name="carNumber"]'))


def _get_edit_field(page, label_text):
    label = _get_modal(page).locator("label.form-label").filter(has_text=re.compile(f"^{re.escape(label_text)}$"))
    return label.locator("xpath=./following-sibling::*[1]")
```

`input[name="carNumber"]`는 모달 안에만 있는 요소라, 이걸 가진 `<section>`을 찾으면 정확히 지금 열린 모달만 골라낼 수 있습니다.

## TC-059~066 — 이관 가능/불가 조합 검증

인수 조건(리셀러·파트너 조합에 따라 이관 가능/불가)을 다루는 TC들입니다. TC-057/058에서 확인한
"업체 바꾸면 파트너 전환·리셀러는 유지"라는 기본 동작 위에서, "이 조합이면 저장이 되는지/막히는지"를
검증합니다.

### 이 8건에는 `@pytest.mark.mutating` 이 붙어 있다 (2026-09-09 추가)

**이 저장소에서 서버 데이터를 실제로 바꾸는 테스트는 지금 이 8건뿐입니다.** 그런데 그 사실이
코드 어디에도 표시돼 있지 않아서, `CLAUDE.md` 가 오랫동안 "지금 있는 테스트는 전부 읽기
전용이라 아직 위험이 없다" 고 적고 있었습니다. 그 문장을 믿고 전체 실행을 걸 수 있었습니다.

그래서 마커를 붙였습니다. 이제 골라 돌릴 수 있습니다.

```bash
pytest -v                                 # 61건 실행 + 이 8건은 게이트가 skip (기본값)
pytest -m "not mutating" -v               # 위와 같되 skip 조차 리포트에 안 남긴다
pytest -m mutating --allow-mutating -v    # 이 8건만 - 플래그가 있어야 실제로 돈다
```

**저장에 성공하는 넷(059·061·063·065)뿐 아니라 차단되는 넷(060·062·064·066)에도 붙였습니다.**
차단 케이스도 [수정] 저장을 **누르는 것까지는 같기** 때문입니다 — 막아주는 그것이 바로 검증
대상이라, 정책이 회귀해 있으면 그대로 데이터가 바뀝니다. "어차피 막히겠지" 를 근거로
안전하다고 분류하지 않습니다.

마커를 **파일 이름으로 빼는 것**(`pytest --ignore=...`)과 비교하면, 마커는 테스트 함수에 붙어
다녀서 파일을 옮기거나 이름을 바꿔도 안 떨어집니다. 다른 파일에 저장하는 TC 가 새로 생겼을 때
파일 목록 방식은 **아무 에러 없이 조용히 무력해집니다.**

### 옵트인 게이트를 넣었다 (2026-09-09)

위 "아직 안 한 것" 을 그날 바로 했습니다. `conftest.py` 에 `_mutating_gate` 라는
autouse fixture 를 두어, **`mutating` 마커가 붙은 테스트는 명시적으로 켜야만 돌게** 했습니다.

```python
@pytest.fixture(autouse=True)
def _mutating_gate(request):
    if request.node.get_closest_marker("mutating") is None:
        return                      # 읽기 전용 TC 는 그냥 통과
    if not _mutating_allowed():     # .env 의 ALLOW_MUTATING_TESTS
        pytest.skip("데이터를 바꾸는 TC 라 기본적으로 실행하지 않는다 - ...")
```

**마커와 게이트는 하는 일이 다릅니다.**

| | 하는 일 | 못 하는 일 |
|---|---|---|
| 마커 | 고를 수 있게 한다 (`-m` 으로 선택·제외) | 사람이 옵션을 안 붙이면 아무것도 안 막는다 |
| 게이트 | **기본값을 "안 함" 으로 만든다** | 켜둔 채 잊으면 없는 것과 같다 |

마커만으로 부족했던 이유는 `-m "not mutating"` 이 **안 붙는 경로가 많기** 때문입니다.

```
pytest -v          pytest --lf          pytest test_vehicle_company_transfer.py
PyCharm 의 실행 버튼          run_tests_and_report.bat          새로 온 사람
```

전부 그냥 돌면 저장하는 8건이 같이 돌았습니다. 그리고 이 종류의 사고는 조용합니다 —
테스트는 초록불로 통과하고 차량 4대의 소속 업체만 바뀐 채 남습니다.

**확인 (2026-09-09 실측)**

```
pytest -m mutating -v   ->   8 skipped in 0.87s
```

0.87초라는 것은 **브라우저도 안 뜨고 로그인도 안 했다**는 뜻입니다. 이 fixture 는 의존이
없어서 `logged_in_page` 보다 먼저 돌기 때문에, 차단될 때는 탭조차 열리지 않습니다.

**켜는 법 — 명령에 플래그를 붙입니다. 파일을 고칠 필요가 없습니다.**

```bash
pytest -m mutating --allow-mutating -v    # 저장하는 8건만
pytest --allow-mutating -v                # 69건 전부
```

### `-m mutating` 과 `--allow-mutating` 은 하는 일이 다릅니다

**`--allow-mutating` 은 "mutating 만 돌려라" 가 아닙니다.** 문을 열어줄 뿐이고, 범위를
좁히는 것은 `-m` 입니다. 둘은 별개의 단계라 조합이 넷 나옵니다.

| 옵션 | 하는 일 | 안 쓰면 |
|---|---|---|
| `-m` | 어떤 테스트를 **고를지** (선택) | 전부 고른다 |
| `--allow-mutating` | 고른 것 중 mutating 을 **돌려도 되는지** (허용) | mutating 은 skip 한다 |

| 명령 | 실제로 돌아가는 것 |
|---|---|
| `pytest -v` | **61 passed, 8 skipped** - 읽기 전용만 |
| `pytest --allow-mutating -v` | **69 전부** - 읽기 전용 61 + 저장하는 8이 같이 |
| `pytest -m mutating -v` | **8 skipped, 61 deselected** - 아무것도 안 돎 |
| `pytest -m mutating --allow-mutating -v` | **8만** - 저장하는 것만 |

`deselected` 와 `skipped` 가 다른 말인 것이 요점입니다.

- **`deselected`** - `-m` 이 안 골라서 애초에 후보에서 빠졌다
- **`skipped`** - 골라지긴 했는데 게이트가 문 앞에서 돌려보냈다

즉 `-m mutating` 만 붙이면 8건이 골라지기는 해도 **전부 skip 되어 하나도 안 돕니다.**
저장하는 8건만 실제로 돌리려면 **둘 다** 붙여야 합니다.

**실측 (2026-09-09)** - mutating 1건 + 읽기전용 1건짜리 임시 파일로 네 조합을 다 돌려
확인했습니다(확인 후 파일 삭제).

```
(옵션 없음)                       1 passed, 1 skipped
--allow-mutating                  2 passed
-m mutating                       1 skipped, 1 deselected
-m mutating --allow-mutating      1 passed, 1 deselected
```

처음에는 `.env` 에 적는 방식만 뒀는데, **한 번 돌리려고 파일을 열어 고치고 끝나고 다시
지우는 것**이 번거롭고 무엇보다 **지우는 걸 잊기 쉬웠습니다.** 켜둔 채 잊으면 게이트가
없는 것과 같아집니다. 그래서 켜는 방법을 셋으로 나누고, 기본은 플래그로 정했습니다.

| 방법 | 사는 범위 | 쓸 자리 |
|---|---|---|
| `pytest --allow-mutating` | **그 명령 한 줄** | 평소 (권장) |
| 셸 `$env:ALLOW_MUTATING_TESTS="true"` | 그 터미널 탭 | 여러 번 반복해서 돌릴 때 |
| `.env` 에 `ALLOW_MUTATING_TESTS=true` | **지울 때까지** | CI 등 매번 붙이기 어려운 자리 |

뒤로 갈수록 오래 살고, 그만큼 **끄는 것을 잊을 위험**이 커집니다. 플래그는 그 명령이
끝나면 사라지므로 잊을 것 자체가 없고, 무엇을 허용했는지가 명령에 그대로 보입니다.

`load_dotenv()` 가 기본 `override=False` 라 **셸 값이 `.env` 를 이깁니다**(2026-09-09 실측).
그래서 `.env` 에 뭐가 적혀 있든 그 탭에서만 잠깐 켤 수 있습니다.

**오타는 조용히 통과하지 않습니다.**

```
pytest --allow-mutatng   ->   error: unrecognized arguments: --allow-mutatng
```

`.env` 쪽 오타(`ALLOW_MUTATNG_TESTS`)는 그냥 "안 켜짐" 이 되어 skip 으로 나타납니다.
**둘 다 안전한 방향으로 틀립니다** - 실수했을 때 데이터가 바뀌는 쪽으로 가지 않습니다.

**아무것도 안 붙이면** `pytest -v` 는 **61 실행 + 8 skip** 입니다. skip 이 리포트에 뜨는 것도
싫으면 `-m "not mutating"` 을 붙입니다 - 그건 이제 안전을 위한 옵션이 아니라
**리포트를 깔끔하게 하는 옵션**입니다.

**아직 안 한 것 — 운영(prod) 하드 가드.** 옵트인은 "실수로 도는 것" 은 막지만,
`ALLOW_MUTATING_TESTS=true` 를 켜둔 채 `STAFF_URL` 만 운영 주소로 바꾼 경우는 못 막습니다.
운영 도메인 패턴을 아직 몰라서(`.env.example` 에 dev/prod 구분 값이 없음) 못 만들었습니다.

### "매번 수동으로 원복해야 하나?" — 아니다, 이번은 버그 때문이었다

1차 실행에서 데이터가 어긋난 채 남았던 건 **설계가 그런 게 아니라, 원복 코드가 실행되기 전에
예외로 죽었기 때문**입니다. TC-059/061/063/065는 전부 이런 구조입니다.

```python
_transfer_company_and_save(page, car, destination)   # 이관 + 저장
...검증...
_transfer_company_and_save(page, car, original_company)  # 원복 — 같은 TC 안에서 자동 실행
```

`_transfer_company_and_save` 안에서 `_find_list_col_index(page, "업체")`가 헤더를 못 찾아
`ValueError`를 던졌고, 그게 **첫 번째 호출(이관) 도중**이라 두 번째 호출(원복) 자체가 아예
실행되지 못했습니다. 즉 "원복 로직이 없어서"가 아니라 "원복 로직 앞에서 죽어서" 못 갔던
것입니다. 헤더명을 고쳤으니 다음 실행부터는 정상적으로 끝까지 가면 **매 TC가 종료될 때
자기 차량을 자동으로 원래 업체로 되돌립니다** — 사람이 매번 손으로 되돌릴 필요는 없습니다.

다만 앞으로도 **테스트가 원복 단계 전에 예외로 죽으면(새 버그, 네트워크 문제 등) 그 시점의
차량은 여전히 어긋난 채로 남습니다.** 이건 이 설계의 근본적인 한계입니다 — "성공하면 자동
원복"이지 "무슨 일이 있어도 반드시 원복"은 아닙니다.

★ **이 한계는 2026-09-09 에 없앴습니다** — 바로 아래 절 참고. 위 문단은 그때까지의 상태를
  기록으로 남겨 둡니다.

### 원복을 fixture teardown 으로 옮겼다 (2026-09-09)

위 문단이 "이 설계의 근본적인 한계" 라고 적어둔 그것을 없앴습니다. **원복이 더 이상 테스트
본문에 있지 않습니다.** `company_guard` fixture 가 맡습니다.

```python
# 전 - 본문 마지막 줄. 중간에서 죽으면 여기 못 온다
_transfer_company_and_save(page, car, destination)
...검증...
_transfer_company_and_save(page, car, original_company)
```
```python
# 후 - 원래 값을 읽은 직후에 등록만 해두고, 되돌리는 것은 teardown 이 한다
original_company = _read_settled(...)
company_guard(car, original_company)
_transfer_company_and_save(page, car, destination)
...검증...
```

**teardown 은 테스트가 어떻게 끝나든 돕니다** - 통과든, assert 실패든, 예상 못 한 예외든.
그래서 "성공하면 자동 원복" 이 "무슨 일이 있어도 원복" 이 됐습니다.

**차단(blocked) TC 4건(060·062·064·066)도 등록합니다.** 정상이라면 데이터가 안 바뀌지만,
막아주는 그것이 바로 검증 대상이라 **정책이 회귀해 있으면 저장이 실제로 통과합니다.** 전에는
그 경우 원복할 곳이 아예 없어서 데이터가 그대로 남았습니다.

**원복은 현재 값을 먼저 읽고, 이미 원래 값이면 아무것도 하지 않습니다.**

```python
current = _read_settled(_get_edit_field(page, "업체").locator(".text").first)
if current == original_company:
    return
```

차단 TC 에서 매번 저장을 한 번 더 누르는 것 자체가 위험하기 때문입니다 - 되돌릴 것이
없는데 [수정]을 누르는 것은 규칙이 막는 바로 그 동작입니다.

**리포트가 헷갈릴 거라던 걱정은 오히려 반대로 풀렸습니다.** 위 문단은 `finally` 로 감싸면
"검증 실패 원인" 과 "원복 실패" 가 뒤섞인다고 걱정했는데, fixture teardown 은 pytest 가
**단계를 나눠서** 보고합니다.

| 어디서 깨졌나 | pytest 표시 |
|---|---|
| 검증 (테스트 본문) | `FAILED` (call 단계) |
| 원복 (teardown) | `ERROR` (teardown 단계) |
| 둘 다 | **둘 다 나온다** - 하나가 다른 하나를 가리지 않는다 |

그래서 원복 실패를 **예외로 삼키지 않습니다.** CLAUDE.md 의 "정리(cleanup)에 실패하면 그
자체를 테스트 실패로 본다" 가 그대로 지켜집니다 - 조용히 넘어가면 "통과했는데 데이터는
바뀐 채" 라는 제일 나쁜 상태가 됩니다.

**한 가지 남는 전제** - teardown 도 화면을 써야 원복할 수 있습니다. 세션이 끊긴 상태로
끝났다면 원복도 실패하는데, 그때는 ERROR 로 드러나므로 **사람이 알 수 있습니다.** 전에는
그 경우 아무 표시 없이 데이터만 남았습니다.

### 실측으로 뒤집힌 것 두 가지 (2026-09-09, 프로브 2회)

TC-066 이 "지점을 선택해주세요" 로 깨진 것을 파다가, **원래 찾던 것보다 큰 문제**가 같이
나왔습니다. 둘 다 위양성입니다.

**위양성은 "통과했는데 실은 아무것도 확인하지 않은 테스트" 입니다.** 실패하는 테스트는 눈에
띄니 고치면 되지만, 위양성은 리포트가 초록불이라 아무도 열어보지 않습니다 - "여기는 확인됐다"
는 잘못된 안심만 남습니다. **통과율로는 영영 안 보입니다.** 그래서 화면을 직접 찍어보는
프로브를 따로 돌려서 잡았습니다.

판단 기준은 하나입니다 - **"검증 대상이 망가졌다고 가정하면, 이 테스트가 빨간불이 되나?"**
아래 둘은 전부 "아니오" 였습니다.

#### ① 차량 4대 중 3대가 원 소속이 아니었다 - 그 상태로 7건이 통과했다

목록 표에서 직접 읽은 값입니다(모달은 재진입 직후 값이 늦게 차서 근거가 약합니다).

```
!! 900용1001  원소속='IMS모빌리티'      현재='LG업체입니다'
!! 900용1002  원소속='LG업체입니다'     현재='IMS모빌리티'
OK 900용1003  원소속='LG업체입니다'     현재='LG업체입니다'
!! 900용1004  원소속='스몰티켓(지입)2'  현재='스몰티켓(테스트)'
```

**어긋난 세 대가 전부 자기 TC 의 목적지에 앉아 있습니다.**

| 차량 | 현재 | 담당 TC | 그 TC 의 목적지 |
|---|---|---|---|
| 900용1001 | LG업체입니다 | TC-059 | **LG업체입니다** |
| 900용1002 | IMS모빌리티 | TC-065 | **IMS모빌리티** |
| 900용1004 | 스몰티켓(테스트) | TC-063 | **스몰티켓(테스트)** |

그러면 이렇게 됩니다.

```python
destination = "LG업체입니다"                 # 하드코딩
original_company = _read_settled(...)       # 화면에서 읽는다 -> "LG업체입니다"
_transfer_company_and_save(page, car, destination)   # 같은 곳으로 "이관"
```

이관이 **제자리 저장**이 되기 때문에 세 단계가 전부 통과합니다.

| 단계 | 실제로 일어나는 일 | 결과 |
|---|---|---|
| 이관 | 지금 소속과 똑같은 업체를 다시 골라 저장 | 당연히 성공 |
| 검증 | 파트너·리셀러 값이 **원래부터 그 업체 것** | 당연히 일치 |
| teardown | `current == original` 이라 아무것도 안 함 | 조용히 통과 |

**전부 초록불인데 이관 정책을 하나도 검증하지 않습니다.** CLAUDE.md 위양성 장의
**"자기충족 - 탐색 조건 == 검증 조건"** 그 형태입니다. 목적지는 고정인데 원래 값은
화면에서 읽으니, 앞선 실행이 원복에 실패해 차량이 목적지에 눌러앉으면 그 순간부터
이 TC 들은 **영원히 아무것도 검증하지 않으면서 통과**합니다.

**`_assert_not_already_there()` 를 넣었습니다.** 이관 직전에 "이미 거기 있나" 를 보고,
그러면 fail 로 끊습니다. skip 이 아니라 fail 인 이유는 전제가 깨진 것을 노란불 뒤에
숨기지 않기 위해서입니다.

★ **"ERROR 가 없으니 원복됐다" 는 틀린 추론이었습니다.** `_restore_company` 는
  `current == original` 이면 **조용히 `return`** 합니다. 예외가 없다는 것은
  "teardown 이 안 터졌다" 이지 "되돌렸다" 가 아닙니다. 원복을 확인하려면
  **데이터를 직접 읽어야** 합니다.

#### ② 업체를 바꿔도 지점 드롭다운이 즉시 안 갈린다

스몰티켓(지입)2 로 바꾼 **직후, 클릭하기 전** DOM 입니다.

```html
<div class="divider text">본점</div>                    <- 라벨: 이전 업체(IMS)의 지점
<div role="listbox">
  <div role="option" aria-selected="true" class="active selected item">본점</div>
  <div role="option" aria-selected="false">지점1</div>
  <div role="option" aria-selected="false">유니크</div>   <- IMS모빌리티 목록 그대로
```

이전 업체의 **목록과 선택값을 그대로** 들고 있다가 나중에 교체됩니다. 그 사이에 첫 옵션을
고르면 다른 업체의 지점을 고른 셈이 되고, 저장할 때 "지점을 선택해주세요" 로 막힙니다.

**기존 가드는 실패할 수 없는 가드였습니다.**

```python
expect(branch_text).not_to_have_text("선택", timeout=3_000)
```

라벨은 클릭 **전부터** 이미 '본점' 이라 "선택" 이 아닙니다. 그러니 클릭이 씹혀도 통과합니다.
CLAUDE.md 위양성 장의 **"라벨만 확인"** 입니다 - 라벨은 값의 증거가 아닙니다.

`aria-selected="true"` 도 답이 아닙니다. **갈리기 전 옛 옵션에 이미 붙어 있습니다.**
모달 안에 지점 값을 담은 `input` 도 없습니다(프로브 [5] - `carNumber`·`memo` 등만 있음).
즉 **"값이 들어갔나" 를 알려주는 DOM 신호가 이 위젯에는 없습니다.**

남는 신호는 하나입니다 - **목록이 새 업체 것으로 갈렸나.** 그래서
`_wait_branch_options_refreshed()` 를 만들었습니다.

```python
before = _branch_options_fingerprint(page)   # 바꾸기 전 지점 목록
...업체 선택...
_wait_branch_options_refreshed(page, before) # 갈리고 + 안정될 때까지
```

조건이 둘인 이유가 `wait_table_settled` 과 같습니다 - `!= before` 만 보면 교체 도중의
빈 목록에 속고, `연속 2회 동일` 만 보면 **아직 안 갈린 이전 목록**이 두 번 연속 같아서
통과합니다.

지점 가드도 `not_to_have_text("선택")` 에서 **`to_have_text(picked)`**(방금 고른 그
지점이 찍혔나)로 좁혔습니다.

**한계 - 두 업체의 지점 이름 목록이 완전히 같으면 갈린 것을 알 수 없습니다.**
스몰티켓(테스트)와 스몰티켓(지입)2 가 둘 다 `['본사']` 하나뿐이라 실제로 여기 걸렸습니다.

★ **그때 실패시키지 않습니다** (2026-09-09 에 한 번 고쳤습니다 - 처음에는 실패시켰는데,
  그 때문에 900용1004 의 원복이 통째로 막혔습니다). 못 가리는 것을 실패로 만들면 멀쩡한
  이관까지 막힙니다. 대신 목록이 **안정되기만** 기다린 뒤 진행하고, 그래서 잘못 골랐다면
  저장할 때 "지점을 선택해주세요" 로 드러납니다 - `_save_with_branch_retry` 가 그걸 받아
  다시 고릅니다. **못 가리는 것은 조용히 넘기되, 틀린 결과는 반드시 드러나게** 한 것입니다.

#### 정리 - 깨져 있던 것은 셀렉터가 아니라 "무엇을 근거로 통과라고 볼 것인가" 였다

둘 다 셀렉터도 멀쩡하고 에러도 없었습니다. 같은 화면의 상태 탭 건(`현장서비스-테스트-노트.md`
"겪은 문제 ②")까지 셋을 나란히 놓으면 형태가 같습니다.

| 위양성 | 잘못된 근거 | 바꾼 근거 |
|---|---|---|
| 상태 탭 (다른 화면) | 표가 안 흔들린다 | **배지 숫자만큼 행이 왔다** |
| ① 이관 | 저장이 성공했다 | **저장 전 소속이 목적지와 달랐다** |
| ② 지점 가드 | 라벨이 채워져 있다 | **내가 고른 값이 들어갔다** |

셋 다 "화면이 조용하다" 를 통과의 근거로 삼고 있었습니다. **조용한 것은 아직
아무것도 안 온 것일 수도 있습니다.**

### 2차 실행에서 드러난 진짜 원인 — "업체" 필드가 비동기로 채워진다

1차 실행에서 dev 데이터가 어긋났던 근본 원인은 헤더명 하나가 아니라 **하나 더 있었습니다.**
`_open_carmgmt_edit_modal`은 `input[name="carNumber"]`에 값이 찼는지만 확인하고 돌아오는데,
"업체" 필드는 그보다 **늦게** 비동기로 채워집니다. 그 틈에 `.inner_text()`로 곧장 읽으면
플레이스홀더 `"선택"`을 "원래 업체명"으로 잘못 캡처합니다.

Playwright 스크립트로 직접 모달을 열어 확인한 실측값(900용1001):

```
'업체' -> 'LG업체입니다'   (제대로 로딩된 뒤의 실제 값)
'지점' -> '본사'
'파트너 선택' -> 'LG U+'
'리셀러 선택' -> '커넥트'
'이용 업체' -> '선택'      (이건 완전히 다른 필드 — 이관과 무관, 늘 비어있는 것으로 보임)
'이용 지점' -> '선택'
```

TC-065/066에서 실제로 이 문제가 터졌습니다: `original_company`가 `"선택"`으로 잘못
캡처되고 → 원복 시도가 `_select_transfer_company(page, "선택")`을 실행 → 그런 업체가
없으니 `"No results found"` → 예외. TC-058은 리셀러 값을 읽을 때 이미
`expect(reseller_text).not_to_have_text("-")`로 이 함정을 막아뒀는데, "업체"/"파트너 선택"을
읽는 새 코드에는 같은 가드가 빠져 있었습니다.

**고친 방법** — 공용 헬퍼 `_read_settled(field_text)`를 추가해, 값이 `"선택"`에서 벗어날
때까지 `expect(...).not_to_have_text("선택")`로 기다린 뒤에만 `inner_text()`로 읽습니다.
모든 `original_company`/`original_partner` 캡처 지점에 적용했습니다.

이 수정 이후 재실행하니 **8개 TC 전부 PASS** 했습니다.
