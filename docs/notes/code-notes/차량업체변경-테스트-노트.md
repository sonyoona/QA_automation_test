## TC-051/052와 뭐가 다른가

같은 "차량관리>차량관리(수정)" 모달을 다루지만, 검증하는 주장이 다릅니다.

| | TC-051/052 | TC-057/058 |
|---|---|---|
| 확인하는 것 | 모달을 그냥 열었을 때 파트너·리셀러 항목이 **존재하는지**(정적) | **업체(인수받을 업체)를 바꿨을 때** 파트너·리셀러가 어떻게 반응하는지(동적) |

TC-057 원문의 "◦예시: 모티스 주식회사 선택 시, 파트너 LG U+출력"이라는 문구가 힌트입니다 — "선택 시"라는 동작(업체를 실제로 바꾸는 액션)이 핵심이라, 그냥 모달을 여는 TC-051/052로는 커버되지 않습니다. TC-059 이후(이관 조건 충족/불충족)가 이 "업체 바꾸면 파트너는 전환되고 리셀러는 유지된다"는 전제 위에서 이어지므로, 미리 확인해둘 가치가 있다고 판단해 자동화했습니다.

## 겪은 문제 — "업체" 라벨이 목록 필터 영역과 겹침

`_get_edit_field`로 "업체" 필드를 찾으려니 strict mode 에러가 났습니다.

```
resolved to 2 elements:
1) <div name="업체" ...>  (목록 화면 상단 필터의 "업체" 드롭다운)
2) <div name="업체" ...>  (지금 연 모달 안의 "업체" 필드)
```

모달은 기존 화면 위에 **겹쳐서** 뜨는 구조라, 뒤에 깔린 목록 화면의 "업체" 필터(라벨이 똑같이 "업체")가 DOM에서 사라지지 않고 그대로 남아있던 것입니다. "파트너 선택"/"리셀러 선택"은 목록 필터에 없는 문구(필터는 그냥 "파트너"/"리셀러")라 우연히 안 걸렸던 것뿐이고, `_get_edit_field` 자체는 원래 모달 범위로 안 좁혀져 있던 잠재 버그였습니다.

**해결**: `test_vehicle_edit_reseller.py`의 `_get_edit_field`를 아예 모달 범위로 좁히도록 고쳤습니다 (이 파일에서 새로 만들지 않고, 원본 헬퍼 자체를 더 안전하게 고쳐서 TC-051~056까지 다 같이 혜택을 보게 함).

```python
def _get_modal(page):
    """지금 열려있는 차량 수정 모달(section) 자체를 가리키는 Locator."""
    return page.locator("section").filter(has=page.locator('input[name="carNumber"]'))


def _get_edit_field(page, label_text):
    label = _get_modal(page).locator("label.form-label").filter(has_text=re.compile(f"^{re.escape(label_text)}$"))
    return label.locator("xpath=./following-sibling::*[1]")
```

`input[name="carNumber"]`는 모달 안에만 있는 요소라, 이걸 가진 `<section>`을 찾으면 정확히 지금 열린 모달만 골라낼 수 있습니다.

054용1111(IMS모빌리티, 파트너 커넥트, 리셀러 커넥트)로 조사해봤습니다.

## TC-057 / TC-058

TC-058은 "안 바뀌어야 한다"를 검증하는 TC라, **변경 전 값도 먼저 확보**해뒀습니다 — 안 그러면 "원래도 저 값이었는지" vs "우연히 저 값으로 유지된 건지" 구분이 안 됩니다.

**"LG U+"를 `COMPANY_PARTNERS`로 가져온 이유 / 리셀러는 안 그런 이유**: TC-057의 파트너 값은 `COMPANY_PARTNERS[transfer_company]`로 가져오는 게 맞습니다 — `COMPANY_PARTNERS`가 정확히 "업체→파트너" 매핑이고, 파트너는 업체가 정해지면 하나로 고정되는 값이기 때문입니다.

TC-058은 처음에 리셀러 값도 `COMPANY_PARTNERS["IMS모빌리티"]`로 가져오려고 했었는데, **이건 잘못된 사용이었습니다.** `COMPANY_PARTNERS`는 "파트너"를 담은 딕셔너리지 "리셀러"를 담은 게 아닙니다. 054용1111의 경우 파트너=커넥트일 때 리셀러도 우연히 "커넥트"로 같아서 통과했을 뿐이고, 만약 파트너가 LG U+인 차량으로 이 TC를 확장했다면 리셀러가 [커넥트/LG U+] 둘 중 뭐가 될지 이 딕셔너리로는 알 수 없어서 바로 깨졌을 코드였습니다.

그래서 **애초에 리셀러 값이 뭔지 미리 알아야 할 필요 자체가 없다는 걸 깨닫고**, 지금 화면에 실제로 표시된 값을 `.inner_text()`로 그대로 읽어와 "변경 전 기준값"으로 삼는 방식으로 바꿨습니다. TC-058이 실제로 주장하는 건 "리셀러가 **어떤 값이든** 안 바뀐다"는 것이라, 그 값 자체를 외부에서 알아올 필요가 없었던 것입니다. 읽기 전에 `not_to_have_text("-")`로 값이 실제로 로딩됐는지부터 확인해서, placeholder를 "원래 값"으로 잘못 캡처하는 것도 막았습니다.

둘 다 저장(`[수정]` 버튼)까지는 안 가고 필드 값만 확인하는 **읽기 전용 TC**라, 데이터 변경 위험이 없습니다.

### 왜 전용 차량 4대(900용1001~1004)를 새로 만들었나

TC-057/058은 필드 값만 읽고 끝나는 읽기 전용 TC지만, TC-059~066은 실제로 [수정] 저장까지
실행합니다. 기존 `CAR_PARTNER_CONNECT`(054용1111) 등은 TC-051~058(그중 TC-053은 이미 저장까지
하는 TC)이 쓰고 있어서, 여기서 또 업체를 실제로 바꾸면 그 TC들의 전제 상태를 건드릴 위험이
있었습니다. 그래서 dev에 이관 테스트 전용 차량 4대를 새로 등록했습니다(사용자 확인, 2026-09-04).

| 차량 | 원 소속(파트너) | 리셀러 | 담당 TC |
|---|---|---|---|
| `900용1001` | IMS모빌리티(커넥트) | 커넥트 | TC-059, 060 |
| `900용1002` | LG업체입니다(LG U+) | 커넥트 | TC-065, 066 |
| `900용1003` | LG업체입니다(LG U+) | LG U+ | TC-061, 062 |
| `900용1004` | 스몰티켓(지입)2(스몰티켓) | 스몰티켓 | TC-063, 064 |

리셀러=커넥트인 차량이 두 대(1001, 1002)인 이유는 TC-059(커넥트→LG U+ 전환)와 TC-065(반대 방향
LG U+→커넥트 전환 + 재진입 확인)를 서로 다른 차량으로 분리해서, 두 TC가 같은 차량을 공유하며
생기는 순서 의존을 아예 없애기 위해서입니다. 대신 두 방향을 각각 검증해 커버리지가 더 좋아졌습니다.

파트너=LG U+/스몰티켓인 업체는 원래 `COMPANY_PARTNERS`에 각각 하나("LG업체입니다",
"스몰티켓(지입)2")뿐이었습니다. TC-061/063("같은 파트너의 **다른** 업체로 이관 성공")을 검증하려면
실제로 다른 업체로 이동하는 걸 보여줘야 하는데 목적지가 자기 자신뿐이라 불가능했습니다. 사용자가
"엘지테스트1"(파트너 LG U+), "스몰티켓(테스트)"(파트너 스몰티켓)를 추가로 확인해줘서
`TRANSFER_ONLY_COMPANY_PARTNERS`에 별도로 담았습니다(`COMPANY_PARTNERS`에 직접 추가하지 않은 이유:
TC-045/046이 `list(COMPANY_PARTNERS)`로 정확히 3개를 순회하는 전제라, 여기에 항목을 더하면 그
TC들의 parametrize가 깨집니다).

### 성공 케이스는 저장 후 원래 업체로 되돌린다

TC-059/061/063/065처럼 저장이 성공하는 TC는 검증 직후 같은 차량을 원래 업체로 다시 이관해
복원합니다(TC-053과 동일 패턴). "원래 업체"는 하드코딩하지 않고 모달 진입 시 실제 표시된 값을
읽어서 씁니다 — 그래야 이 TC가 어떤 순서로 실행되든, 심지어 중간에 실패해서 복원이 안 된 채로
남아있어도 다음 실행이 "지금 보이는 값"을 기준으로 다시 정상 동작합니다.

TC-060/062/064(차단 케이스)는 저장 자체가 안 되므로 복원이 필요 없습니다 — 다만 "정말 안 바뀌었는지"는
확인해야 해서, 시도 전 업체/파트너 값을 읽어뒀다가 시도 후 그대로인지 비교합니다.

### 팝업 처리 — TC-053과 다르게 두 단계일 수 있음

TC 문서 원문에 인용된 알럿이 두 종류입니다.

```
"수정작업을 변경할까요? CANCEL OK"                          <- 저장 버튼 클릭 직후 확인 팝업
"변경을 완료하였습니다. OK버튼을 눌러주세요 OK"                <- 이관 성공 시 완료 팝업
"업체를 변경할 수 없습니다. ... 시스템 알럿 노출"              <- 이관 차단 시 대신 뜨는 알럿
```

TC-053의 `_save_edit_modal`은 OK를 한 번만 클릭하는데, 그건 리셀러 값만 바꾸는 플로우라 완료
팝업이 없었거나 토스트로만 떴을 가능성이 있습니다(확인 안 함). 업체 이관은 문서에 완료 팝업이
명시돼 있어서, `_click_save_and_confirm`(확인 팝업)과 `_confirm_transfer_complete`(완료 팝업)을
분리했습니다. 차단 시에는 완료 팝업 대신 `_expect_transfer_blocked`가 에러 알럿 문구를 확인하고 닫습니다.

   팝업)이 실제로 정상 동작함을 확인했습니다.
3. **차단 시 모달은 닫히지 않지만, "업체" 필드 표시값은 자동으로 안 돌아온다** — TC-064 실행에서
   확인: 차단 알럿을 닫아도 모달의 "업체" 필드는 방금 시도했던(거부된) 값을 계속 보여줍니다.
   실제 저장된 값은 안 바뀌었지만 화면 표시가 그렇다는 뜻이라, TC-060/062/064를 전부 TC-066처럼
   "알럿 닫고 → 모달 재진입 → 그 때 값 확인"하는 방식으로 고쳤습니다. 그 자리에서 바로 확인하면
   방금 시도한 값과 비교하게 돼서 항상 실패하게 됩니다.

**해결됨 — 목록의 "업체" 컬럼 헤더 텍스트**

`_transfer_company_and_save`가 저장 후 `_find_list_col_index(page, "업체")`로 목록 컬럼을 찾다가
`ValueError: '업체' is not in list`로 실패했습니다. 실제 헤더는 "업체명"이라 문자열을 고쳤습니다
(사용자 확인, 2026-09-04). 이게 이번 1차 실행에서 유일하게 원복 단계까지 못 가게 막던 원인입니다.

### "매번 수동으로 원복해야 하나?" — 아니다, 이번은 버그 때문이었다

1차 실행에서 데이터가 어긋난 채 남았던 건 **설계가 그런 게 아니라, 원복 코드가 실행되기 전에
예외로 죽었기 때문**입니다. TC-059/061/063/065는 전부 이런 구조입니다.

```python
_transfer_company_and_save(page, car, destination)   # 이관 + 저장
...검증...
_transfer_company_and_save(page, car, original_company)  # 원복 — 같은 TC 안에서 자동 실행
```

`_transfer_company_and_save` 안에서 `_find_list_col_index(page, "업체")`가 헤더를 못 찾아
`ValueError`를 던졌고, 그게 **첫 번째 호출(이관) 도중**이라 두 번째 호출(원복) 자체가 아예
실행되지 못했습니다. 즉 "원복 로직이 없어서"가 아니라 "원복 로직 앞에서 죽어서" 못 갔던
것입니다. 헤더명을 고쳤으니 다음 실행부터는 정상적으로 끝까지 가면 **매 TC가 종료될 때
자기 차량을 자동으로 원래 업체로 되돌립니다** — 사람이 매번 손으로 되돌릴 필요는 없습니다.

다만 앞으로도 **테스트가 원복 단계 전에 예외로 죽으면(새 버그, 네트워크 문제 등) 그 시점의
차량은 여전히 어긋난 채로 남습니다.** 이건 이 설계의 근본적인 한계입니다 — "성공하면 자동
원복"이지 "무슨 일이 있어도 반드시 원복"은 아닙니다(더 강하게 하려면 `finally` 블록으로
원복을 감싸는 방법이 있는데, 그러면 검증 실패로 테스트가 fail한 원인과 원복 자체의 실패가
뒤섞여 리포트가 헷갈릴 수 있어 일단은 TC-053 때부터 써온 단순한 방식을 그대로 따랐습니다).
그래서 전체 실행 후 FAILED가 있으면, 그 TC가 성공 케이스(059/061/063/065)인지 먼저 보고
필요하면 그 차량만 수동으로 확인하는 습관을 들이는 게 좋습니다.

### 2차 실행에서 드러난 진짜 원인 — "업체" 필드가 비동기로 채워진다

1차 실행에서 dev 데이터가 어긋났던 근본 원인은 헤더명 하나가 아니라 **하나 더 있었습니다.**
`_open_carmgmt_edit_modal`은 `input[name="carNumber"]`에 값이 찼는지만 확인하고 돌아오는데,
"업체" 필드는 그보다 **늦게** 비동기로 채워집니다. 그 틈에 `.inner_text()`로 곧장 읽으면
플레이스홀더 `"선택"`을 "원래 업체명"으로 잘못 캡처합니다.

Playwright 스크립트로 직접 모달을 열어 확인한 실측값(900용1001):

```
'업체' -> 'LG업체입니다'   (제대로 로딩된 뒤의 실제 값)
'지점' -> '본사'
'파트너 선택' -> 'LG U+'
'리셀러 선택' -> '커넥트'
'이용 업체' -> '선택'      (이건 완전히 다른 필드 — 이관과 무관, 늘 비어있는 것으로 보임)
'이용 지점' -> '선택'
```

TC-065/066에서 실제로 이 문제가 터졌습니다: `original_company`가 `"선택"`으로 잘못
캡처되고 → 원복 시도가 `_select_transfer_company(page, "선택")`을 실행 → 그런 업체가
없으니 `"No results found"` → 예외. TC-058은 리셀러 값을 읽을 때 이미
`expect(reseller_text).not_to_have_text("-")`로 이 함정을 막아뒀는데, "업체"/"파트너 선택"을
읽는 새 코드에는 같은 가드가 빠져 있었습니다.

**고친 방법** — 공용 헬퍼 `_read_settled(field_text)`를 추가해, 값이 `"선택"`에서 벗어날
때까지 `expect(...).not_to_have_text("선택")`로 기다린 뒤에만 `inner_text()`로 읽습니다.
모든 `original_company`/`original_partner` 캡처 지점에 적용했습니다.

이 수정 이후 재실행하니 **8개 TC 전부 PASS** 했습니다.

### 참고 — 1차 실행의 부분 실패로 원래 소속이 문서와 달라진 차량들

1차 실행에서 TC-059/061/063/065가 저장에는 성공했지만 원복 단계 전에 예외로 죽는 바람에,
"왜 전용 차량 4대를 새로 만들었나" 표에 적어둔 **원래 소속과 지금 실제 소속이 다른 차량이
3대** 있습니다(2차 실행 후 재확인한 값):

| 차량 | 문서상 원래 소속 | 지금 실제 소속 (2026-09-04 확인) |
|---|---|---|
| 900용1001 | IMS모빌리티 | **LG업체입니다** |
| 900용1002 | LG업체입니다 | **IMS모빌리티** |
| 900용1003 | LG업체입니다 | LG업체입니다 (일치) |
| 900용1004 | 스몰티켓(지입)2 | **스몰티켓(테스트)** |

**테스트 통과에는 영향 없습니다** — 각 TC는 "지금 실제 값"을 기준으로 왕복하도록 짜여 있어서

다만 위 문서의 "원 소속" 설명과 실제가 어긋난 채로 남아있다는 점만 알아두면 됩니다 — 정말
원래 소속으로 맞춰두고 싶으면 dev에서 수동으로 한 번 옮기면 되고, 안 옮겨도 자동화에는
문제가 없습니다.
