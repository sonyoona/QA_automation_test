# 차량 등록 파트너/리셀러 테스트 노트

`test_vehicle_register_reseller.py`에 짠 TC-043~046, TC-048, TC-050이 뭘 하는지 정리했습니다. (TC-047은 이후 추가 예정 — TC-045 1번 단계와 겹쳐서 우선순위상 뒤로 미룸)

## 왜 이 TC부터 시작했나

리셀러 TC 스프레드시트를 "구현 난이도" 기준이 아니라 "중요도/효율성" 기준으로 다시 훑다가, 처음엔 TC-053(차량 **수정** 시)을 클러스터의 시작으로 잘못 짚었습니다. 실제로는 **TC-043(차량 **등록** 시)이 파트너/리셀러 제약 로직의 진짜 시작**이고, TC-051부터가 그 로직을 수정 화면에서 반복 검증하는 부분이었습니다.

이 클러스터를 살펴보다가 **TC-049가 FAIL 상태의 실제 버그**라는 것도 확인했습니다 — 파트너가 LG U+인데 리셀러를 선택 안 하면 등록이 막혀야 하는데, 실제로는 알럿도 안 뜨고 콘솔에 에러만 남고, 재시도하면 등록이 성공해버리는 비일관적 동작입니다. TC-088(모니터 리셀러 필터 쪽에서 이미 발견한 버그)과 같은 패턴이라, **자동화하지 않고 버그 리포트 대상으로만 남겨뒀습니다.** 동작 자체가 오락가락하면 뭘 "정답"으로 삼아 assert할지가 없어서, 자동화해봤자 flaky한 테스트만 만들게 됩니다.

## 화면 진입 경로

**차량관리 > 차스펙관리** 목록에서, 각 행(카코드)마다 있는 **[등록]** 버튼을 누르면 "차량 등록" 모달이 뜹니다. TC 문서의 "등록버튼 클릭"이 정확히 이 버튼입니다.

```python
def _open_carspec_register_modal(page):
    page.goto(STAFF_URL)
    page.locator("a").filter(has_text=re.compile(r"^차량관리$")).click()
    page.get_by_role("link", name="차스펙관리", exact=True).click()
    page.locator(".spinner").first.wait_for(state="hidden", timeout=60_000)
    page.get_by_role("button", name="등록", exact=True).first.click()
```

> **`exact=True`가 왜 필요했나**
>
> 이 목록 페이지엔 "카코드 등록", "카코드 일괄등록", "차량 일괄등록" 버튼도 있고, 그 아래 매 행마다 "등록" 버튼이 하나씩 있습니다. `exact=True` 없이 `name="등록"`으로 찾으면 문자열에 "등록"이 들어간 모든 버튼(카코드 등록 포함)이 다 걸려서 strict mode 에러가 납니다. `exact=True`를 주면 텍스트가 정확히 "등록"인 버튼만 골라지고, `.first`로 첫 행 것을 클릭합니다.

## 모달 DOM 구조 — 모니터 화면과 다른 점

실제로 모달을 열어 DOM을 까봤습니다(`docs/notes/자동화-테스트-노트.md`에 정리된 "표준 조사 방법"과 동일하게, `storage_state`로 auth.json을 불러오는 독립 스크립트로 확인). 모니터 화면의 필터들은 전부 `div.column`이라는 감싸는 클래스가 있어서 `page.locator("div.column", has_text="...")`로 한 번에 스코프를 좁힐 수 있었는데, 이 모달은 그런 감싸는 클래스가 없습니다:

```html
<div style="flex: 1 1 0%;">
  <label class="form-label">파트너</label>
  <div role="listbox" aria-disabled="true" class="ui disabled selection dropdown form-select">
    ...
  </div>
</div>
```

`label`과 실제 필드(드롭다운)가 그냥 **형제(sibling) 관계**로만 붙어있어서, "라벨 텍스트로 찾은 다음 → 바로 다음 형제를 가져오는" 방식이 필요했습니다. 그래서 이번에 처음으로 **xpath**를 썼습니다.

```python
def _get_form_field(page, label_text):
    label = page.locator("label.form-label").filter(has_text=re.compile(f"^{re.escape(label_text)}$"))
    return label.locator("xpath=./following-sibling::*[1]")
```

> **`xpath=./following-sibling::*[1]`가 뭐하는 코드인가**
>
> Playwright locator는 기본적으로 CSS 셀렉터를 쓰지만, `xpath=`를 붙이면 **XPath 문법**으로 찾을 수 있습니다. CSS는 "부모 → 자식" 방향으로만 찾기 쉬운데, "이 요소의 형제 요소"처럼 **옆으로 이동**하는 건 CSS만으로는 어렵습니다(가능은 하지만 제한적). XPath의 `following-sibling::*[1]`은 "지금 위치(`.`)에서, 뒤따라오는 형제 요소들 중 첫 번째"라는 뜻입니다. 즉 `<label>파트너</label>` 바로 다음에 오는 `<div role="listbox">...</div>`를 가져오는 겁니다.

> **업체를 선택하기 전엔 파트너/리셀러가 비활성 상태**
>
> 모달을 처음 열면 파트너/리셀러 필드의 role이 `combobox`가 아니라 `listbox`이고, `aria-disabled="true"`가 붙어 있습니다. 업체를 선택하면 파트너/리셀러가 활성화되고 값이 자동으로 채워지는데, 이 전환 로직은 TC-045~048에서 다룰 부분이라 TC-043/044에서는 "노출 여부(+ 파트너는 수정 불가 상태인지)"까지만 확인합니다.

## 테스트 설명

### TC-043 — 파트너 항목 출력 확인

```python
def test_TC043_vehicle_register_partner_field_visible(logged_in_page):
    page = logged_in_page
    _open_carspec_register_modal(page)

    partner_label = page.locator("label.form-label").filter(has_text=re.compile(r"^파트너$"))
    expect(partner_label).to_be_visible()

    partner_field = _get_form_field(page, "파트너")
    expect(partner_field).to_be_visible()
    expect(partner_field).to_have_attribute("aria-disabled", "true")
```

TC 문서의 기대 결과는 "**수정 불가능한** 파트너 항목이 노출되어야 한다"입니다. 그래서 라벨/필드가 보이는지뿐 아니라, `aria-disabled="true"`인지도 같이 확인합니다 — 이게 빠지면 "노출은 됐지만 수정 가능한 상태"인 회귀(regression)를 못 잡습니다.

> **`assert get_attribute(...)` 대신 `expect(...).to_have_attribute(...)`로 바꾼 이유**
>
> 원래는 `assert partner_field.get_attribute("aria-disabled") == "true"`로 짰었습니다. 동작은 하지만 `get_attribute`는 그 순간 딱 1번만 읽고 재시도가 없어서, `CLAUDE.md`의 "DOM 요소 상태는 항상 `expect`" 원칙과는 어긋난 방식이었습니다. 바로 위에서 `to_be_visible()`로 먼저 안정화시켜서 실제로 깨질 위험은 낮았지만, 원칙을 일관되게 지키고 이후 TC-045처럼 같은 속성을 반복 검증하는 코드와 스타일을 맞추기 위해 `expect(...).to_have_attribute(...)`로 교체했습니다.

### TC-045 — 업체 선택 변경에 따른 파트너·리셀러 상태 전환 확인

TC-043/044가 "노출 여부"만 봤다면, TC-045는 실제로 **업체를 바꿔가며** 파트너·리셀러가 기대대로 자동전환되는지 확인합니다. TC 문서 기대 결과는 업체가 어느 파트너에 속하느냐에 따라 3갈래로 갈립니다.

| 업체의 파트너가... | 파트너 필드 | 리셀러 필드 |
|---|---|---|
| 커넥트 | 커넥트로 자동 선택(비활성) | 커넥트로 자동 선택(비활성) |
| LG U+ | LG U+로 자동 선택(비활성) | **활성화**되어 [커넥트/LG U+] 중 직접 선택해야 함 |
| 스몰티켓 | 스몰티켓으로 자동 선택(비활성) | 스몰티켓으로 자동 선택(비활성) |

**문제 — "이 업체의 파트너가 뭔지" 이름만 보고는 알 수 없었음**

TC 문서는 "파트너가 [커넥트]인 업체", "[LG U+]인 업체"라고만 적혀 있지, 실제 dev 환경에서 어떤 업체 이름이 어느 파트너에 매핑되는지는 안 나와 있습니다. 업체 이름으로 짐작하는 건 위험했습니다 — 실제로 "유플러스", "유플러스2"라는 이름의 업체를 선택해봤더니 **파트너는 LG U+가 아니라 커넥트**였습니다(이름과 실제 매핑이 다름). 그래서 후보 업체 여러 개를 직접 선택해보고 파트너 필드에 뭐가 뜨는지 하나씩 확인하는 조사 스크립트를 먼저 돌려서, 실제로 검증된 업체만 테스트에 썼습니다.

```python
candidates = ["IMS모빌리티", "유플러스", "유플러스2", "스몰티켓(지입)2", "아이엠에스커넥트", "커넥트에요", "LG업체입니다"]
# 결과: IMS모빌리티/유플러스/유플러스2/아이엠에스커넥트/커넥트에요 → 커넥트
#       스몰티켓(지입)2 → 스몰티켓
#       LG업체입니다 → LG U+  (리셀러 옵션: ['커넥트', 'LG U+'], 초기 표시값 "선택"으로 미선택 상태)
```

이렇게 확인한 3개(`IMS모빌리티`, `LG업체입니다`, `스몰티켓(지입)2`)를 실제 테스트에 그대로 사용했습니다.

**업체 선택 헬퍼 — 검색형 드롭다운**

```python
def _select_company(page, company_name):
    company_field = _get_form_field(page, "업체")
    company_field.click()
    company_field.locator("input.search").fill(company_name)

    option = company_field.get_by_role("option", name=company_name, exact=True).first
    expect(option).to_be_visible()
    option.click()
```

"업체"는 TC-085(모니터 리셀러 필터)에서 봤던 것과 같은 **검색형** combobox라서, 그냥 클릭만 하면 안 되고 `input.search`에 이름을 직접 타이핑해서 후보를 좁힌 다음 옵션을 클릭해야 합니다. `expect(option).to_be_visible()`로 "검색 결과가 실제로 필터링될 때까지" 기다린 뒤 클릭하는 게 핵심입니다.

**겪은 문제 — 클릭 직후 읽으면 아직 이전 값("-")이 보임**

처음엔 업체를 선택한 직후 바로 `partner_field.get_attribute(...)` 같은 일반 파이썬 값 읽기로 파트너 텍스트를 확인했는데, 가끔 방금 바뀐 값이 아니라 **바뀌기 전 값("-")**이 잡혔습니다. 업체를 선택하면 파트너/리셀러 값이 자동으로 채워지는 게 **비동기로 한 박자 늦게** 일어나기 때문입니다 — `자동화 테스트 노트`의 "assert는 그 순간 한 번만 보고 재시도가 없다"는 내용과 정확히 같은 상황입니다.

```python
# 문제가 됐던 방식 — 그 순간 스냅샷만 읽음, 재시도 없음
assert _read_field_text(partner_field) == "커넥트"   # 가끔 "-"로 실패

# 고친 방식 — 값이 실제로 바뀔 때까지 최대 5초 재확인
expect(partner_text).to_have_text("커넥트")
```

`assert`를 `expect().to_have_text(...)`로 바꾸기만 하면 되는 문제였습니다. `_read_field_text`라는 별도 헬퍼까지 만들었다가, `expect`로 대체되면서 필요 없어져 지웠습니다 — 안 쓰는 코드를 남겨두지 않았습니다.

### TC-046 — 업체 선택 시 파트너 자동선택 확인

TC-045가 "업체 종류별로 정확히 어떤 값이 뜨는지"를 봤다면, TC-046은 그보다 일반적인 주장을 검증합니다 — **"어떤 업체를 고르든" 파트너는 자동으로 채워지고 수정 불가 상태여야 한다**는 것입니다. TC 문서 원문도 "1. 임의의 업체 선택"이라고만 되어 있어서, 특정 업체·특정 파트너값을 지정하지 않습니다.

```python
@pytest.mark.parametrize(
    "company_name",
    list(COMPANY_PARTNERS),
    ids=["connect_company", "lg_uplus_company", "smallticket_company"],
)
def test_TC046_vehicle_register_partner_auto_selected_on_company(logged_in_page, company_name):
    page = logged_in_page
    _open_carspec_register_modal(page)

    _select_company(page, company_name)

    partner_field = _get_form_field(page, "파트너")
    partner_text = partner_field.locator(".text").first
    expect(partner_text).not_to_have_text("-")
    expect(partner_field).to_have_attribute("aria-disabled", "true")
```

> **처음엔 업체 1개(`IMS모빌리티`)만으로 짰었습니다**
>
> "임의의 업체"라는 주장을 업체 딱 하나로만 확인하면, 사실은 "IMS모빌리티라는 그 업체에서만 성립하는 동작"일 수도 있는데 그걸 구분할 방법이 없습니다 — 우연히 그 업체만 특별 취급됐을 가능성을 못 잡아냅니다. 그래서 TC-045에서 이미 파트너별로 검증해둔 업체 3개(`COMPANY_PARTNERS` — 커넥트/LG U+/스몰티켓 소속 각 1개)를 그대로 재사용해 `parametrize`로 반복 검증하도록 바꿨습니다. 새 업체를 더 찾지 않고 **이미 검증된 데이터를 재사용**한 것도 `CLAUDE.md`의 "테스트 데이터" 원칙과 맞습니다.
>
> `COMPANY_PARTNERS` 딕셔너리를 파일 위쪽에 모듈 레벨로 빼서, TC-045(각 업체의 정확한 파트너값 확인)와 TC-046(파트너가 자동 채워지는지만 확인) 둘 다 같은 매핑을 참조하게 했습니다 — 같은 값을 두 곳에 따로 하드코딩해두면 나중에 한쪽만 고치고 다른 쪽을 깜빡하는 식으로 어긋날 수 있어서입니다.

**TC-045와 뭐가 다른가**: TC-045의 1번 단계(`IMS모빌리티` 선택 → 파트너 "커넥트" 확인)와 액션 자체는 겹치지만, **검증하는 주장이 다릅니다.**

| | TC-045 | TC-046 |
|---|---|---|
| 확인하는 것 | 그 업체의 파트너가 **정확히 어떤 값**인지(커넥트/LG U+/스몰티켓별로 다름) | 값이 뭐가 됐든 "**자동으로 채워졌고**(placeholder "-"가 아님) **수정 불가**"라는 사실 자체 |
| 특정 업체에 의존하나 | 예 — 업체별 매핑이 TC 검증의 핵심 | 아니요 — "임의의 업체"라 어떤 업체를 써도 성립해야 함 |

그래서 TC-046은 정확한 파트너 값(`to_have_text("커넥트")`)을 확인하는 대신, **"초기 placeholder였던 `-`가 아니게 됐다"**(`not_to_have_text("-")`)는 더 느슨한 조건으로 검증합니다 — TC 문서가 실제로 요구하는 것("자동 선택됨")보다 더 강하게(예: 특정 값까지) 단정하지 않기 위해서입니다. `CLAUDE.md`의 "TC/기획서에 명시되지 않은 정책을 임의로 추가하지 않는다" 원칙에 맞춘 선택입니다.

> TC 문서 비고에 "기획서에 미명시된 동작이지만 실제 웹에서는 기대결과와 같이 동작함"이라고 적혀 있습니다 — 즉 공식 기획 문서에는 없는 동작인데 QA가 실제 화면에서 확인해서 PASS 처리한 케이스입니다. docstring에도 이 사실을 그대로 남겨뒀습니다.

### TC-048 — 파트너 기준 [리셀러 선택 제한] 확인 (파트너가 LG U+인 경우)

```python
def test_TC048_vehicle_register_reseller_required_when_partner_lg_uplus(logged_in_page):
    page = logged_in_page
    _open_carspec_register_modal(page)

    _select_company(page, "LG업체입니다")

    reseller_field = _get_form_field(page, "리셀러")
    reseller_text = reseller_field.locator(".text").first
    expect(reseller_field).to_have_attribute("aria-disabled", "false")
    expect(reseller_text).to_have_text("선택")

    reseller_options = reseller_field.locator('[role="option"] .text').all_inner_texts()
    assert set(reseller_options) == {"커넥트", "LG U+"}, (
        f"[FAIL] 리셀러 선택지가 [커넥트/LG U+]가 아닙니다: {reseller_options}"
    )
```

TC-045의 2번 단계와 액션은 같지만(LG U+ 업체 선택), TC-048은 TC 문서가 명시한 "**필수 선택**"이라는 조건을 별도로 검증합니다. 리셀러가 활성화됐다는 것과 "아직 아무것도 안 골랐다(필수로 남아있다)"는 것은 다른 주장이라, `reseller_text`가 실제 리셀러 이름이 아니라 여전히 placeholder `"선택"`인지를 명시적으로 확인합니다 — 만약 활성화되자마자 뭔가 하나가 기본값으로 미리 골라져 있다면, 그건 "필수 선택"이 아니라 "자동선택+수정가능"이 되어 TC 기대 결과와 달라집니다.

### TC-050 — 파트너 기준 [리셀러 선택 제한] 확인 (파트너가 스몰티켓인 경우)

def test_TC050_vehicle_register_reseller_auto_selected_when_partner_smallticket(logged_in_page):

## 겪은 문제 — 로컬엔 "신선"한데 서버는 이미 로그아웃시킨 세션

TC-048/050을 추가하고 전체를 돌렸더니, **이미 통과하던 TC-043~046까지 전부** 같은 지점(GNB "차량관리" 클릭)에서 30초 타임아웃으로 실패했습니다. 코드를 건드리지 않은 테스트까지 한꺼번에 깨진 거라, 코드 문제가 아니라 **환경 문제**라고 판단하고 조사했습니다.

`auth.json`을 직접 열어 쿠키 만료 시각을 확인해보니 아직 55분 가까이 남아있었는데, 그 쿠키를 그대로 들고 실제 사이트에 들어가보니 **로그인 화면**이 떴습니다. 즉 **서버 쪽에서 이미 이 세션을 무효화**시켰는데, `conftest.py`의 `_auth_state_is_fresh()`는 로컬 쿠키의 만료 "시각"만 보기 때문에 이걸 감지하지 못하고 계속 "신선하다"고 오판한 것입니다.

원인으로 의심되는 건 **동시 로그인 제한 정책**입니다 — 사용자가 다른 세션(다른 브라우저·다른 실행)으로 같은 계정에 로그인하면, 기존 세션이 서버에서 강제로 밀려나는 방식으로 보입니다. TC-049 조사 때도 비슷한 낌새가 있었던 부분이라, 이 사이트 전반의 특성일 가능성이 있습니다.

**당장의 해결**: `auth.json`을 지우고 사람이 직접 재로그인해서 새로 발급받았습니다. `_auth_state_is_fresh()`를 "로컬 쿠키 시각"이 아니라 "서버에 실제로 물어봐서 확인"하는 방식으로 바꾸면 이런 오판을 막을 수 있겠지만, 지금 당장 필요한 조치는 아니라서 손대지 않았습니다 — 나중에 이 문제가 반복되면 그때 고려할 부분으로 남겨둡니다.
