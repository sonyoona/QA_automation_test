# QA Automation Test

Playwright + pytest 기반 웹 관리자 시스템 UI 자동화 테스트입니다.
인턴 근무 중 수동으로 반복하던 회귀 테스트를 코드로 옮기며 작성했습니다.

<br>

## 해결하려던 문제

관리자 시스템의 기능이 변경될 때마다 기존 화면이 정상 동작하는지 사람이 직접 눌러 확인해야 했습니다.
특히 두 가지가 반복 작업의 병목이었습니다.

1. **2단계 인증(OTP)** — 테스트를 실행할 때마다 로그인부터 다시 해야 함
2. **전수 확인** — 여러 탭·여러 행을 눈으로 하나씩 대조해야 함

이 두 가지를 자동화하는 것이 목표였습니다.

<br>

## 기술 스택

| 구분 | 사용 기술 |
|---|---|
| 언어 | Python |

## 핵심 구현

### 1. 인증 세션 저장·재사용 (`conftest.py`)

OTP는 자동화할 수 없기 때문에, **로그인을 없애는 대신 한 번만 하도록** 구조를 바꿨습니다.

- `auth_state` — session 스코프 픽스처. 테스트 세션당 최대 1회만 로그인
- 로그인 성공 시 브라우저 storage state를 `auth.json`으로 저장
- 재실행 시 `_auth_state_is_fresh()`로 **쿠키 만료 시각을 검사**해 유효하면 그대로 재사용
  (만료값이 `-1`인 세션 쿠키는 판정에서 제외)
- 만료된 경우에만 headed 브라우저를 띄워 OTP 입력을 대기 (대기 시간은 `OTP_WAIT_SEC`로 조정)
- `logged_in_page` — 각 테스트는 저장된 세션으로 **새 탭만 열어** 실행

그 결과 테스트를 여러 번 돌려도 로그인은 한 번이면 충분해졌습니다.

### 2. 기능 변경에 대한 회귀 테스트 (`test_monitor_reseller_filter.py`)

필터 항목이 교체되는 변경이 있었고, 변경 이후 기존 화면이 의도대로 동작하는지 검증했습니다.

- 전체 탭에서 신규 필터가 노출되고 기존 필터는 사라졌는지 확인
- 드롭다운 선택 항목이 기대한 목록과 일치하는지 확인
- 필터 적용 후 **조회 결과의 모든 행**이 선택한 값과 일치하는지 전수 검증
  (`_assert_all_rows_have_reseller`)
- 테이블 컬럼이 의도대로 추가·제거되었는지 확인

컬럼 위치는 하드코딩하지 않고 `_find_reseller_col_index()`로 헤더에서 찾아내도록 해,
컬럼 순서가 바뀌어도 테스트가 깨지지 않도록 했습니다.

### 3. 등록 시점 제약 로직 검증 (`test_vehicle_register_reseller.py`)

파트너·리셀러 제약 로직은 "차량 수정" 화면이 아니라 "차량 등록" 화면(차량관리>차스펙관리>등록)에서 먼저 정해집니다.

- 등록 모달에 파트너·리셀러 항목이 노출되고, 파트너는 수정 불가 상태인지 확인
- 업체를 바꿔가며 파트너·리셀러가 업체의 소속 파트너(커넥트/LG U+/스몰티켓)에 맞게 자동전환되는지 확인
  (파트너가 LG U+인 업체는 리셀러가 자동선택 대신 선택 가능 상태로 활성화됨)
- 업체 선택 시 파트너가 항상 자동선택+비활성화되는지 확인 (특정 업체에 의존하지 않는 일반 동작)

dev 환경에서 업체 이름만으로는 소속 파트너를 알 수 없어서(이름과 실제 매핑이 다른 경우 있음),
후보 업체를 직접 선택해보고 파트너 필드에 뜨는 값을 확인하는 조사 스크립트로 먼저 검증한 뒤 테스트에 반영했습니다.

### 4. 수정 시점 제약 로직 검증 (`test_vehicle_edit_reseller.py`)

같은 파트너·리셀러 제약 로직이 "차량 수정" 화면(차량관리>차량관리>수정)에서도 동일하게 성립하는지 검증합니다. 검증 대상 파트너별 차량은 테스트 전용으로 직접 등록해둔 차량을 씁니다(기존 데이터는 건드리지 않음).

- 수정 모달에 파트너·리셀러 항목이 노출되고, 파트너는 수정 불가 상태인지 확인
- 파트너가 커넥트/스몰티켓인 차량은 리셀러가 자동선택+비활성 상태인지 확인
- 파트너가 LG U+인 차량은 리셀러가 [커넥트/LG U+] 중 선택 가능한 필수 항목인지 확인

리셀러 값을 실제로 변경·저장하는 TC(업체 선택 변경에 따른 리셀러 값 초기화/재설정)는 저장 후 뜨는 확인 팝업(`[OK]`)을 눌러야 실제로 반영되는 걸 확인해 자동화에 반영했습니다.

### 5. 업체 변경(이관) 시 파트너/리셀러 반응 검증 (`test_vehicle_company_transfer.py`)

같은 수정 모달 안의 "업체"(인수받을 업체) 필드를 바꿨을 때 파트너·리셀러가 어떻게 반응하는지 검증합니다 — TC-051/052(정적 노출 확인)와 달리 실제 동작(선택 액션에 따른 변화)을 봅니다.

- 업체를 변경하면 파트너가 그 업체 기준으로 전환되는지 확인
- 업체를 변경해도 리셀러 값 자체는 바뀌지 않고 유지되는지 확인 (활성/비활성 상태만 파트너 규칙에 따라 바뀜)

같은 모달을 다루기 때문에 `test_vehicle_edit_reseller.py`의 모달 진입·필드 탐색 헬퍼를 그대로 import해서 재사용합니다.

## Allure 3 리포트

Allure 3는 pytest 실행 결과를 테스트 제목, 단계, 실패 스크린샷·콘솔 로그 등으로 정리해 주는 테스트 리포트 도구입니다.
이 프로젝트에서는 실패한 테스트의 증적을 자동으로 첨부하며, 실행 결과는 HTML 리포트로 확인할 수 있습니다.

```bash
# Python 연동 패키지 설치
pip install allure-pytest

# Allure 3 CLI 설치 (Node.js/npm 필요)
npm install -g allure
```

리포트를 생성하려면 테스트 실행 시 결과 폴더를 지정한 뒤 Allure를 실행합니다.

```bash
pytest -v --alluredir=allure-results --clean-alluredir
allure generate -o allure-report allure-results
allure open allure-report
```

## 실행 방법

```bash
# 1. 의존성 설치
pip install pytest playwright python-dotenv
playwright install chromium

# 2. 환경변수 설정
cp .env.example .env
# .env 파일을 열어 대상 URL과 계정 정보를 입력

# 3. 테스트 실행
pytest -v

# 특정 파일만 실행
pytest test_monitor_reseller_filter.py -v
```

최초 실행 시에는 OTP 입력을 위해 브라우저 창이 열립니다.
인증번호를 입력하면 세션이 `auth.json`에 저장되고, 이후 실행에서는 재사용됩니다.

<br>

## 배운 점

- **반복되는 확인 작업은 사람이 아니라 코드가 맡아야 한다**는 것을 실무에서 확인했습니다.
- 자동화가 불가능한 구간(OTP)이 있을 때, 그 구간을 없애려 하기보다
  **실행 횟수를 줄이는 구조**로 우회하는 접근을 배웠습니다.
- 화면 구조에 강하게 의존하는 테스트는 쉽게 깨지기 때문에,
  선택자와 인덱스를 **동적으로 찾도록** 작성하는 것이 유지보수에 유리하다는 점을 배웠습니다.
